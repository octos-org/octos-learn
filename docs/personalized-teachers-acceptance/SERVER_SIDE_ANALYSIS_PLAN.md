# 知识点分析改为服务端执行：方案

日期：2026-10-24。来源：真实环境验收第一天。用户选择方案 B（“我更倾向于B”）。

## 1. 为什么要改

知识点分析负责判断一节课的提问、每段讲解和每道练习对应哪个知识点。学习地图点亮和成就颁发都依赖它。

现在的做法是：浏览器在课堂空闲时，以学生的身份请 Octos 开一个一次性分析会话，由页面回答模型的“知识点目录查询”，再把结果交给学习记录服务。验收中发现三个问题：

1. **页面一关就中止。** Octos 关闭连接时，会中止这个连接发起的轮次，并取消它承担的工具（`ui_protocol_transport.rs` 的 `abort_connection_turns`、`host_tools::drop_routes_for_connection`）。学生下课马上关掉应用，这节课就要等到下次打开才分析。
2. **课堂一忙就让路。** 播放讲解、练习动画开始时，页面会主动中断分析。第一天 4 次分析失败 3 次，很可能就是这两种中断造成的。
3. **反馈来得晚。** 分析要等到课后空闲才开始，地图和成就也就跟着晚到。这与“尽快给学生正反馈”的产品方向相反。

## 2. 可以借用的现成能力

Learning Coach 生成课程，用的就是 Octos 的**后台技能动作**（manifest 里 `"execution": "background"`，例如 `learning.lesson.generate`）：

- 由 Octos 的任务监管器在服务端运行，不依赖页面连接；
- 技能程序自己调用模型，使用 Octos 为这个账号配置的模型 Key（和上课生成课程是同一个 Key、同一笔费用）；
- 任务状态和结果保存在 Octos，Octos 重启后能识别中断的任务。

所以不需要在 Octos 里另建后台系统，也不需要让学习记录服务保存任何人的登录凭证或模型 Key。

## 3. 方案

### 3.1 流程

1. **触发时机提前**：课程送达（`course_delivered`）或学生提问（`question_submitted`）记录上传后，学习记录服务照常建立分析任务。页面在同一次同步里请 Octos 启动后台分析动作。学生这时正在上课，页面一定是开着的。
2. **Octos 后台执行**：新的后台动作 `learning.topics.analyze`（放在 Learning Coach 里）：
   - 输入：学习记录服务冻结的分析材料（和现在的 `input_json` 相同，含 `input_sha256`）；
   - 在技能内部查询随技能打包的知识点目录，不再需要页面回答目录查询；
   - 调用模型，按现有规则做格式检查，输出结果 JSON。
3. **结果直接交回学习记录服务**：学习记录服务在建立任务时，为这个任务签发一次性的写入凭证，随输入一起交给后台动作。动作完成后，凭这个凭证把结果提交给学习记录服务。服务照常做完整校验（引文、目录编号、输入哈希），然后写入地图。这一步不经过页面，所以学生关掉应用也不影响。
4. **页面只负责显示**：下次同步时读取地图和成就。学生如果还在应用里，分析完成后会收到颁发提示。

### 3.2 不变的部分

- 每天最多 10 次分析的上限、学生可以在设置里关闭分析；
- 服务端对结果的全部校验规则；
- 学习记录服务仍然只保存事实，不保存登录凭证或模型 Key；
- 记忆仍然只由 Octos 处理。这个分析不是记忆，也不写入记忆。

### 3.3 失败处理

- 后台动作失败（模型服务出错、超时）：Octos 任务状态是“失败”，学习记录服务把任务标成“轮次失败”，按现有规则自动重试一次，计入每日上限；
- 结果没通过校验：记下校验信息，不重试；
- Octos 重启导致任务中断：同“后台动作失败”；
- 一次性凭证只能用于这一个任务的这一次提交，过期或重复使用都会被拒绝。

### 3.4 要改的地方

| 仓库 | 改动 |
|---|---|
| learning-coach | 新的后台动作和工具 `oll_analyze_topics`：打包知识点目录，调用模型，提交结果。复用现有的模型调用和 JSON 解析代码 |
| octos-learn 服务端 | 签发一次性写入凭证；新增凭证提交结果的接口；任务状态和 Octos 后台任务对应 |
| octos-learn 页面 | 用“启动后台动作”取代现在的“开会话、回答目录查询、等待回复”。现有的会话分析流程保留到新流程验证通过后再删除 |
| octos | 预计不用改。实施前先用测试确认两件事：后台动作在页面关闭后继续运行；技能程序能访问学习记录服务的地址 |

## 4. 需要确认或核实的问题

1. **结果交回方式**：推荐按 3.1 第 3 步，由后台动作直接提交，做到真正不依赖页面。另一种做法是结果先留在 Octos，下次打开页面时再取，改动更小，但关掉应用后仍然要等到下次打开。
2. **网络可达**：技能程序要能访问学习记录服务。本机开发环境用的是 mkcert 证书，需要让技能进程信任它；正式环境里学习记录服务在 Nginx 之后。实施前先核实。
3. **知识点目录的大小**：os-taxonomy 有几千个节点。打包进技能会增大技能体积，需要确认对安装和更新没有影响。
4. **费用**：每次分析的模型调用和现在相同，约 0.06 美元一节课。触发时机提前，但次数不变。实施后的真实模型验证需要另行批准预算。

## 4.1 核实结果（2026-10-24）

用户确认第 1 项：由后台动作直接交回结果。其余各项的核实情况：

| 问题 | 结论 | 依据 |
|---|---|---|
| 后台动作在页面关闭后是否继续运行 | 已实测确认会继续（见下方实测记录） | 后台动作由 `tokio::spawn(run_background_skill_action_batch(...))` 启动，只持有工具注册表，不持有页面连接（`ui_protocol_transport.rs`）。连接关闭时的清理只涉及：中止这个连接发起的轮次、取消它承担的工具、释放客户端命令、停止转发，都不涉及后台动作任务。Octos 测试里没有直接覆盖“断开连接后后台动作完成”的用例 |
| 技能能否拿到模型 Key | 能 | 技能工具在 manifest 的 `env` 里声明需要的变量，Octos 按账号配置传入（`OCTOS_PROFILE_LLM_*`、`GEMINI_API_KEY` 等）。Learning Coach 的 `oll_generate_lesson` 就是这样调用模型的 |
| 技能能否访问学习记录服务 | 能，但地址要由服务端配置 | 沙箱的网络权限是全开或全关（`(allow network*)`），Learning Coach 声明了 `requires_network: true`。本机开发时，学习记录服务跑在 Vite 的 HTTPS（mkcert 证书）里，技能进程默认不信任这个证书。为防止任意地址请求，提交地址不能来自动作输入，要由 Octos 侧的环境变量配置（例如 `OCTOS_LEARN_HISTORY_URL`）；开发环境可以用学习记录服务的 HTTP 端口 |
| 知识点目录打包进技能 | 可以接受 | `catalog.json` 1.4 MB（压缩后约 0.35 MB），只需要它和 `metadata.json`，前置关系表不需要。现在安装后的 Learning Coach 是 2.7 MB，打包后约 4 MB |

实测记录（2026-10-24，用户自己的 Key，一次课程生成）：用户提问“什么是函数的定义域？”，看到“正在搭建这节课”后关闭标签页。Octos 后台任务 `oll_generate_lesson` 在 16:49:44 开始；开发服务器记录页面连接在 16:49:45 断开；任务在 16:50:01 完成（状态 completed，两次模型调用，没有错误）。用户重新打开后看到完整课程。这节课只有一个小节，是因为模型在大纲阶段（第 11.5 秒）就规划成一个小节，与关闭页面无关；前一节课在大纲阶段规划的是两个小节。

## 4.2 实现说明

- **两次模型调用**：第一次让模型给出至多 8 个英文检索词；技能用与学习记录服务相同的词法检索查本地目录，最多取 48 个候选；第二次让模型只在候选中分类每个单元。原先由页面回答的多轮目录查询，改成固定的两步。
- **一次性凭证**：学习记录服务在派发时生成 32 字节随机凭证，只保存它的 SHA-256；凭证只能用于这一个任务、只能用一次、10 分钟内有效。回报接口 `POST /api/learn/history/analysis/callback/<job>` 不经过 Octos 登录，也不向回报方透露账号。格式不对的失败回报会在消耗凭证之前被拒绝。
- **超时和旧任务**：10 分钟内没有回报，记为“轮次失败”（自动重试一次）。旧版由页面运行、尚未结束的分析，也按“轮次失败”处理，用后台方式重试一次，不再重新连接旧会话。
- **启动失败**：Octos 明确拒绝启动（例如 Learning Coach 还是旧版本）时，任务退回队列，不计入每日上限；只是没收到回复时保持已派发，由 10 分钟窗口决定。
- **页面何时知道完成**：服务端最新结果编号变大时，页面重新检查成就；派发后 30 秒左右再同步一次。页面重新打开后的第一次同步也检查一次，以颁发关闭期间完成的分析带来的成就。
- **触发时机**：仍在课堂空闲时（通常是讲解播完、开始练习时）派发，因为学习记录上传本身也在空闲时进行。派发之后就和页面无关。
