## 最新用户要求与结论

用户已否定 DeepAR 角色以及后续 VRM/Live2D 外观候选，要求重新研究此前发来的抖音特效，并补充：在其他平台也见过类似效果，可以用截图以图搜图。

本次建议将**实时神经卡通化 / portrait video stylization**作为独立验证路线。它从真人输入帧生成卡通画面，不要求先手工制作完整角色绑定。它与单图肖像驱动、现成三维角色捕捉是不同问题，不应混称。

**尚未确认截图的确切特效。** 查到的重点比对对象是 Snapchat 官方 `Cartoon 3D Style`，以及抖音官方 `卡通脸`。存在相近技术与视觉路线，不等于截图一定来自这两个具体版本。

用户此前仍要求效果与匿名优先，不能因改成卡通化就默认取消匿名要求。身份保留与角色统一性是本路线的重要限制。

## 截图检索实际做了什么

- 查看用户原始截图，路径为系统临时目录中的 `codex-clipboard-ab2b12f0-0d47-4d0c-9d8f-364aa33d1971.png`。看到短棕发、大眼、柔和三维卡通风格的人脸及室内背景；单帧本身不足以区分生成式人脸转换和完整三维动画。
- 搜索截图字幕与造型线索，扩展到 Snapchat / TikTok / Douyin。字幕线索没有定位原视频或特效 ID。
- 按用户明确请求，通过 Google Lens 图片上传入口**提交了这张截图**，服务器返回 200 并跳转到图片搜索页。结果 HTML 是需要运行 JavaScript 的页面，没有读到视觉匹配条目。没有尝试绕过验证或执行反自动化脚本。
- 因此应表述为“已提交以图搜图，但未取得可核验的匹配结果”，不能声称以图搜图已经识别出 Snapchat，也不能把没有读到结果说成没有匹配。
- 工具内的图片检索只支持文字查询；后续文本/图片结果是跨平台线索比对，不是成功的逆向图片匹配。

## 技术上值得继续的三个方向

### A. 用成熟创作工具生成我们自己的卡通化效果

[Snap Lens Studio Face Generator](https://developers.snap.com/lens-studio/features/genai-suite/face-ml-generation)支持参考图与文字提示，生成脸部转换效果。该文档还专门讨论设计一致性、头部转动时耳朵闪烁及裁切边界。这与用户关心的外观和头部边缘问题直接相关，但并不保证自动解决。

可验证问题：以自有星狐的正面参考画风，能否生成稳定、一致、表情清楚的头部转换。要测试不同人的外观一致性、耳朵边缘、眼睛和嘴巴、头部活动范围，而不能只看一张生成预览。

[Camera Kit](https://developers.snap.com/camera-kit/home)提供 Web/iOS/Android 接入；[官方 FAQ](https://developers.snap.com/camera-kit/getting-started/faq)同时明确，除了测试特效外，应用需要自己创建或取得内容，不能随意调用 Snapchat 全部公开特效。**不能拿一个 Snapchat 特效 ID 就承诺已可放进 Octos Learn。**

尚未确认：本项目可用的生成工具权限与费用、所生成效果在 Camera Kit Web 上的具体兼容性、运行时数据流、无摄像头回放、离线行为和课程最终配音支持。[版本与功能兼容表](https://developers.snap.com/camera-kit/ar-content/lens-studio-compatibility)只能用于预检，不能代替特效实测。

### B. 自托管神经卡通化模型：先验证画面，再考虑实时

| 项目 | 一手资料已确认 | 本项目用途与限制 |
|---|---|---|
| [DCT-Net](https://github.com/menyifang/DCT-Net) | 作者提供多种预训练风格，包含 3d；支持视频逐帧处理、自有风格训练；代码 Apache-2.0 | 适合首轮三维卡通风格参考；逐帧能力不等于稳定视频。权重及依赖许可仍需逐项核对；旧 TensorFlow 环境需要评估，不应破坏当前工程 |
| [VToonify](https://github.com/williamyang1991/VToonify) | 作者专门研究高分辨率人像视频风格化与时间一致性 | 用于研究运动与风格保真；[S-Lab 许可](https://github.com/williamyang1991/VToonify/blob/main/LICENSE.md)限制非商业用途，不能作为免费商用产品方案 |

两者都不是“已经开源的抖音同款”。先比较公开样例、代码/权重条件和短片输出，不能承诺在当前 Mac 或安卓大屏上实时达到同等效果。不把 NVIDIA 实验成绩作为本机/网页帧率。

## 为什么该路线可能改善问题，也有什么代价

对于张嘴和转头，视频卡通化直接利用每个输入帧的动作与可见区域，不受现有星狐仅少量五官素材的限制，也不必把一张正面立绘的耳朵直接拉向侧面。**这是路线差异，不是效果保证**；模型仍可能丢失细小表情、改变牙齿、闪烁、扭曲耳朵或在大角度失败。

相应代价：

- 可能保留真人脸型、发型、服装和环境，不能自动视为匿名；要实现固定角色与纯虚拟背景，需要另行验证。
- 直接卡通化通常依赖原始图像流；现有仅存表情参数的轨迹不足以重建其输出。
- 录制时的真人嘴型不能直接配到时长变化的最终合成语音。发布阶段需要额外的重配口型或独立参数驱动，不可忽略。
- 如果必须依赖云 GPU，会改变当前相机不上传的设计和成本；本轮没有上传原始真人视频、启用摄像头或调用云推理。上传的仅是用户明确要求用于以图搜图的既有卡通截图。
- 以匿名渲染视频存课也需要设计课程格式和体积限制，不能简单放开 MP4 上传白名单。

## 建议的下一轮最小实验

先做一个短的技术验证，不先改正式录课流程，也不再花一轮生成角色静态概念图。

1. 以公开的三维卡通风格模型/作者样例确定视觉方向与许可边界；Snap 创作工具路线与可自托管模型分开记录。
2. 使用受许可的成人或合成输入，测试自然、闭眼、大张嘴、圆唇、眉毛、小幅转头和返回正面；如输入需要外传或有费用，先把实际方案与数据范围准备好再确认。
3. 在同一连续短片检查嘴部行程、头发耳朵轮廓、闪烁、风格一致性和身份保留。现有失败的 LivePortrait 不能不改条件再跑一次后当新方案。
4. 记录当前设备实际耗时、内存和运行方式；画面通过后，再评估本地实时/网页转换和最终配音，不预先承诺安卓大屏实时。
