用户提供了第三方报告《第二阶段计划审查结论》，结论为“修改后可实施”。本次按实际源码核对，采纳明确遗漏，也修正部分建议中不足以解决问题的办法。审查报告是独立证据，不是用户对产品选择的批准。

## 1. 总体判断

存储职责和整体实施顺序保留：产品保存可核查的学习事实，Octos 统一处理长期记忆；当前仍建议服务端 SQLite、设备 IndexedDB，以及分别统计提问、讲解播放、整课完成和练习。

报告指出的路由、备份、播放依据和练习日志问题成立。它们需要提前落实到字段与改动清单，不应等到最终验收再发现。

有四处不能照搬原建议：只增加消息字段不能解决旧消息重试；不能断言同步 SQLite 一定不影响语音；不能用最远进度代替继续位置；reset 保留日志不等于每次重学都会撞号，仅增加学习编号也不覆盖所有日志重建和跨设备情况。

## 3. 几处不同判断的理由

### 增加消息字段只能帮助观察，不能单独解决重复

反例：请求实际已写入，回复在网络中丢失；很久以后，消息不在加载窗口中。即使追加回复新增了 appended 标志，客户端仍没有收到这份回复。重试若再次写入，返回 appended=true 也不能撤销已经发生的重复。

查询增加 client_message_id/seq 能帮助匹配当前可见记录，但不能让窗口外的旧记录自动可见；先查后写还可能与其他请求并发。计划改为在 Octos 追加入口处理窗口外的重复，并让核对与写入共同受到保护。具体比较持久接收登记和完整历史核对等最小办法，不把新增两个字段当作完成验收。

报告“load_full 只有测试使用”的表述也过强。源码中的 ensure_full_history 调用 load_full，rollback_last_n_user_turns 又在生产路径调用 ensure_full_history。它不意味着现在就有适合应用的完整历史核对接口，但也不能说该能力完全未用于生产代码。结论限定为：本计划要用的接口不足，不能通过回滚等副作用操作来解决查询。

### 同进程同步数据库是否足够，要测量

历史 hosted-tts 使用 DatabaseSync，是可参考的实现先例；它设置的 busy_timeout 为 5000 毫秒。发生锁争用时，同步等待可能远长于普通小事务；历史查询和备份也不能假定一直很短。当前语音回复整块返回，仍需要事件循环处理请求和响应，因此不能据此推导它不受影响。

反过来，没有实测也不能预定必须增加 worker。修订后的计划先限制查询与批量，测量等待和请求响应，再选择必要的隔离。旧代码不恢复为当前服务，也不直接复制其业务逻辑。

### 最远进度与继续位置解决不同问题

学生已经播放第四节，后来主动回到第一节复习。最远实际进度仍在第四节，但希望继续的位置可能是第一节。另一台设备还可能停在第三节。

这几个位置可以同时成立。用其中最大的值覆盖其他位置会破坏复习；只看最远位置也不知道中间是否跳过。计划保留两类位置和实际覆盖片段，可据此展示进展，不替学生选择继续点。

### reset 保留日志，不代表每次都撞号

现有 reset 不清理操作和练习日志；运行中的序号继续递增，重新加载也从已有日志最后一项继续，因此不是每次重播都会重复 operation_id。

但旧成功会保留，新一遍如果直接复用状态就可能无需新作答而显示成功。日志清空后或另一设备创建同一课程，序号又可能从 1 开始；只加一个学习编号，仍不能区分同一次学习内两台设备各自产生的操作。

修订方案要求明确新一遍的存储范围，并给操作日志分配可持久恢复的编号。学习、日志、任务与操作共同标识一次尝试；重建日志不能覆盖旧编号，也不能把旧日志整体重标成新学习。

## 4. 对播放采集建议的补充

“在前端动作发生时记录”方向正确，但点击 play 仅是意图。Runtime 的 advanceBeat 会连续执行操作，跳转也会造成相似状态，所以还要知道实际推进发生的原因和片段是否真正完成。

先验证产品动作层和存储适配能否可靠完成；不足时，在 OLL 增加最小通用通知是允许的。不能为了坚持“不改 OLL”，使用最终游标或脆弱的 UI 推测替代真实依据，也不把每一帧和所有鼠标移动全量保存。

## 5. 补充明确的交付边界

本次还将问答交付的身份问题写明：产品服务可持久保存待交付任务，但不保存用户登录 token 供无人在线时继续代表用户操作。首版建议由本人在线设备领取任务，通过已有认证连接交付；认证失效或应用关闭时等待下次登录。多设备领取与上游重复保护一起验证。

这项建议不会新增后台记忆处理模型，也不自动启动新的定时任务。原来的“保存了交付任务”不能被理解为“服务端已经具备永久替用户调用 Octos 的身份”。
