## 2. 实际实现了什么

`memory/request` 接收用户明确提出的记住、纠正和按编号遗忘。应用只能操作认证连接所属账号的记忆，不能填写别人的身份或自行声明材料来源。纠正需要旧记忆编号和新要求；遗忘只接收编号，不接收模糊文字。

同一请求编号、同一内容重复发送，只接收一次；换了内容却沿用旧编号会报冲突。后台已经处理过、甚至原记忆已经被删除后，重试仍能返回接收结果。这个结果始终只是“已接收”，不宣称记忆已经改变。

为了处理保存途中退出的情况，程序先把完整笔记保存到后台不会读取的私有位置，再保存接收登记，里面只有用于比较请求是否相同的散列值和随机笔记编号，最后把笔记交给已有后台。重试发现登记后只恢复尚未发出的笔记；已经发出并被处理的笔记不会重新创建。登记长期保留，但不另外保存原文副本。

`memory/promote` 复用已有资料挑选流程。来源筛选发生在数量截取之前，只处理本人资料，仍要求资料实际被读取过。返回的是成功交给后台的资料编号和数量。没有新增资料整理定时器，产品仍需在接入时落实调用时机。

两者都不在请求中调用模型。理解、合并、纠正和删除继续交给 Octos 已有后台执行。协议未协商相应功能时拒绝调用；只限某个会话的凭据、受限外部连接不能借新接口操作整个账号。没有认证身份的 stdio 连接不声明支持它们。

## 5. 有意保留的边界

1. 第一版纠正、遗忘的目标是本人 `MEMORY.md` 中当前存在的条目，不直接操作仅存于归档中的编号；已有 CLI 能力未改动。
2. 接收登记不提供某次操作的最终完成查询；`refresh_enabled` 表示配置是否开启，不代表后台当前健康或必定按时完成。
3. 资料挑选仍只提交标题、摘要及来源，不包含正文；已经挑选过的资料更新后也不会再次挑选。
4. 并发调用已按顺序处理，但挑选流程中“写笔记”和“标记挑选过”仍是已有的两次写入。进程恰好在中间退出时，不承诺绝不重复。内容检查拒绝的挑选材料按现有逻辑跳过，不计入成功数量。
5. 删除后遇到旧提炼结果重新写回的情况，没有建立复杂保护机制，遵循用户此前允许暂缓的约定。没有新增永久学习账本，也没有决定老师之间的记忆共享规则。

调查依据见[应用记忆接入方案](APP_MEMORY_ACCESS.md)，上一轮文档审查见[审查收尾记录](REVIEW_CLOSEOUT.md)。后续需要先审计这批上游代码，再推进前端问答记录和课程上下文接入。

## 6. 独立审查结果与追加修复

用户提供的独立审查结论是“可以提出 PR”。审查实际重跑了上表全部测试与检查，并核对了权限和代码改动，未发现阻止原候选提交的问题。

审查另外指出：用户纠正一条记忆后又将它删除，纠正请求可能仍留在队列里。后续模型如果继续尝试更新这个已经不存在的编号，整批整理会失败，旧纠正又被保留，可能反复消耗模型额度。

这项问题已经在 f41c9e59 中处理。后台在调用模型前检查明确指定旧条目的用户纠正：只有目标在当前记忆、归档和待确认记录中都不存在，才撤销该纠正，并在内部处理结果中记录原因。有机会恢复目标的记录、其他用户要求以及模型来源的笔记继续保留。接收登记不删除，因此重试已被撤销的纠正也不会重新入队。

新增四项测试验证：

- 删除目标后撤销旧纠正，其他条目的纠正仍能正常完成；原请求重试不会重新出现。
- 前一轮已经删除目标、只剩纠正请求时，不调用模型就能清理。
- 目标还在归档时保留纠正。
- 普通记住要求、没有指定旧条目的纠正和模型来源的纠正保持原行为。

第一项新回归在原代码上失败；修复后链路测试 11 项、记忆相关测试 245 项全部通过，严格 Clippy 零警告，格式与差异检查通过。另按审查建议补充了一行辅助方法说明：has_staging_request 可能恢复并发布尚未发出的笔记，调用者不能把它当成纯读取操作。没有改方法名或请求格式。

代码入口是 [run_consolidation](../../../octos/crates/octos-cli/src/memory_consolidate/mod.rs) 和[链路测试](../../../octos/crates/octos-cli/src/memory_consolidate/app_pipeline_tests.rs)。原审查结论对应 b0acfe04；f41c9e59 是单独的审查跟进提交，目前只有实施方自动验证。本机检查记录也仍对应 b0acfe04，后续人工验收应先运行最新候选代码。

这里修复的是已经失去目标的旧纠正，不是此前允许暂缓的所有在途任务写回问题。接收登记保留方式、资料挑选规则及其他已披露边界保持原样。
