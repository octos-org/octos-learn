## 2. 当前链路具体断在哪里

### 一次直调问题：课程生成了，历史和背景没有自动补齐

以学生问“斜率为什么有正有负”为例，当前 `startDirectLessonGeneration` 直接调用 `skill/action/invoke`，发送问题、turn_id、输入方式及时间数据。没有发送 tutor_context 或 learner_context，也没有调用 session/append_message 保存这次问答。

课程通过后台任务和课程文件交付，播放进度另存在设备。这几部分各自能工作，但“有课程文件”“有消息历史”“确实上过这节课”是三种不同事实。目前不能从课程生成成功推导出后两种。

已存在的普通 turn 路径仍会按 Octos 原机制保存消息；接入时须按实际请求路径去重，不能对所有提问一律再追加一次。

### 一次预制课：设备有进度，Octos 还没有统一学习账本

CoursePack 身份包含 packId、version 等信息；播放器有 step、beat、学生操作和课后任务状态。前端使用 IndexedDB 保存播放位置、学生操作、任务进度，课程包也有独立缓存。

这些状态足以支持本机继续播放，尚不足以让老师跨课程回答“这个学生过去两周接触斜率几次”。现有诊断时间线又是内存数据，不能作为长期记录。

### 记忆已存在，也不会自动进入直调课程

本机的 memory/overview 可以成功读取；其他记忆接口也存在。但 frontend 需要明确读取哪些内容、用多大篇幅传入。Learning Coach 的三个直调 action 对上下文字段支持不一致，相关系统提示也未明确解释如何使用这些字段。

因此，当前阻碍不是“再加一句老师人格提示”就能解决，而是记录、检索和课程输入三处尚未接通。

依据：[直调课程](../../src/learning/learning-workspace.tsx)、[技能调用封装](../../src/api/skill-actions.ts)、[本地学习存储](../../src/learning/learning-document-store.ts)、[技能入口定义](../../../learning-coach/manifest.json)、[课程输入构造](../../../learning-coach/src/lesson-plan-generation.ts)。

## 3. 学习事实应该保存在哪里

这里要保存的是能核查的原始记录，例如“同一次学习的第二节播放完成”“某个任务提交了一个答案”。Octos 负责保存、查询、去重和删除；Octos Learn 定义课堂事件并提交。自然语言中哪些内容应该成为偏好或共同经历，仍只由 Octos 判断。

本次按四项条件比较现有候选：能否精确查找、能否稳定计数、怎样处理旧操作、能否与删除联动。

| 候选 | 精确查找与计数 | 去重和旧操作 | 删除及长期保留 | 判断 |
|---|---|---|---|---|
| session/append_message | 适合原话、回复及问答对应；没有按知识点筛选的事件查询 | 已加载历史窗口内可去重，窗口外重试不保证 | 消息保留与记忆遗忘不同，删除后的衍生内容需另处理 | 继续用于真实问答，不充当所有学习事件的账本 |
| memory/ingest + search/load | 有种类、来源、时间过滤，但结果是相关性排序，最多返回 50 条，不是完整枚举 | 内容指纹帮助跳过相同记录，不是持久事件幂等或条件更新 | Recall 有容量和冷记录清理策略，不保证永久保留全部事实 | 用于检索投影，不能直接作为次数统计的真源 |
| 已认证的文件接口 | 可以上传、读取、列出文件；文件变更入口仅删除或重命名，没有通用记录查询 | 没有现成的记录编号冲突、追加事务或条件更新契约 | 删除文件不自动撤销衍生记忆；每条事件拆文件会把扫描和协调推给应用 | 可保存课程正文等附件，现成接口不足以承担账本 |
| memory_namespace | 提供隔离存储，不提供上述记录查询 | 不解决事件去重和更新规则 | namespace 自动提炼当前关闭，通用 memory 接口又按认证 profile 取存储 | 不能靠命名空间直接实现成长；老师范围规则仍待定 |

新增发现：Recall 默认每来源最多保留 20,000 条记录，age 会按冷度处理超额记录。即使补一个“列出全部检索记录”的接口，仍不能保证多年学习次数不变。因此不能只围绕搜索接口补一层前端统计。

**当前工程建议：在 Octos 内增加最小的通用事实记录能力，Recall 保留为它的检索投影。**两者都由 Octos 管理，同一条处理链路负责衍生和删除；不在 Octos Learn 或 Learning Coach 建第二套记忆服务。无需在第一阶段建设课程专用数据库或大规模分析系统，底层是否复用现有 redb 实现由 Octos 评审后决定。

依据：[Recall 过滤与保留策略](../../../octos/crates/octos-memory/src/recall.rs)、[记忆协议](../../../octos/crates/octos-core/src/ui_protocol.rs)、[应用记录接收检查](../../../octos/crates/octos-cli/src/api/ui_protocol_transport.rs)、[文件接口](../../../octos/crates/octos-cli/src/api/handlers.rs)、[namespace 行为](../../../octos/crates/octos-cli/src/runtime/memory_namespace.rs)。

## 4. 建议给 Octos 补什么，做到哪里为止

以下是待实施、待协议评审的最小契约，**名称仅为草案，当前服务端不支持这些新方法**。这是本阶段的设计产出，不表示新 API 已定稿或已上线。

### 4.1 通用事实记录

建议提供三种操作，产品自己的课程字段放在记录数据里，不把斜率、徽章或老师性格写进通用 Rust 协议。

| 操作草案 | 最少需要保证什么 |
|---|---|
| app/records/append | 按已认证的归属保存有稳定编号的不可变记录；同编号同内容返回原结果，同编号不同内容明确冲突；不调用模型 |
| app/records/query | 按来源、事实类型、关联对象、标签和时间精确查询；支持稳定游标及查询上界，能够取完同一批数据；不使用相关性排名代替完整结果 |
| app/records/retract | 撤销指定记录并返回可查状态；同步让统计不再使用，通知 Octos 清理或重算检索和记忆投影；不靠物理删掉一个文件就宣布全部完成 |

追加结果至少包含持久编号、服务端提交顺序、是否重试命中。查询应返回使用的数据上界，让报告能够说明“统计到哪一批记录”。时间同时保留发生时间和收到时间：离线补传不能伪装成刚发生，也不能仅凭客户端时间决定偏好新旧。

幂等编号在服务端保留期必须与有效记录的重试和撤销规则一致。撤销后迟到重试不能重新创建同一条记录；删除时怎样保留必要的非内容拒绝标记，要在 Octos 删除设计中说明。

授权归属由 Octos 从连接和账号推导，客户端声称的 student_id 不能覆盖它。认证说明是谁提交，不自动证明提交的内容真实；从浏览器提交的观察也不能因此成为数学掌握证明。若需要区分产品服务与普通客户端的来源能力，应在 admission 和协议权限中落实，不能信任一段 source 字符串。

建议字段如下，尚未作为运行代码启用：

| 字段 | 作用 |
|---|---|
| record_id、schema_version、kind | 稳定编号、格式版本与事件种类 |
| occurred_at、device_id、device_sequence | 离线排序线索；均不替代服务端提交顺序 |
| session_id、request_id、learning_run_id | 区分白板、一次问题及一次实际学习；恢复学习沿用 run，新一遍学习使用新 run |
| course_ref | 预制课为课程编号、版本、内容 hash；实时课为实际课程文件及内容版本 |
| step_id、beat_id 或 task_ref | 播放片段和练习分别关联，不要求课后任务绑定一个正在播放的 beat |
| topic_refs、mapping_revision | 使用哪份课程映射得出的关联；未知就保留未知，不强行猜节点 |
| evidence_type、payload | 区分学生原话、应用观察和老师实际回应；保留所提交事实，不填“喜欢”“掌握”等推断 |
| teacher_ref（若已知） | 记录参与者线索；不据此决定其他老师能否读取或声称亲历 |

先记录 question_submitted、course_presented、playback_progress、task_attempt 等可观察事实。暂停、回放和重复提交不自行解释为困惑、喜欢或一次新学习。重复学习的最终计数阈值仍是待定产品规则，第一版存储不把它固化。

### 4.2 由 Octos 把事实和消息转为记忆

真实学生原话可继续通过 append_message 保存为 user。真实老师回复可保存为 assistant，并显式携带原问题对应的 thread_id。两者都使用独立的生产者编号，不能与已有 turn 行共用一个 client_message_id。

程序事件走事实入口，不伪装成 user，也不伪造 tool 角色。Octos 应能向提炼流程提供“这是应用报告的观察、这是学生说的话”的区别。是否设置新的证据种类、不同情形如何比较权威，由 Octos 语义设计进一步确定；此处不把程序事件一律排在用户陈述之上或之下。

记录落盘、进入提炼、完成整合、可读取，是不同状态。Octos Learn 只能展示已经得到确认的状态。希望“下一堂课采用偏好”时，要先确定时效目标，再由 Octos 提供相应触发与处理；Learning Coach 不补一个自己的快速归纳器。

### 4.3 遗忘和旧任务保护

建议提供应用可调用的遗忘请求及操作状态入口，区分提交、停止用于回答、清理完成和失败。普通硬删除已经能清理匹配副本，但网页入口和完整的迟到任务保护还缺少明确契约。

删除需覆盖原记录或记忆的检索投影、衍生记忆以及已开始的后台任务。建议 Octos 在处理任务时记住读取的数据版本，提交前检查相关撤销状态；过期产物重新判断或拒绝，不能无条件写回。衍生内容需保留依据关系，否则无法准确知道哪些结果需要清理或重算。

原对话是否保留、同义内容的遗忘范围及完成时限仍需决定。技术设计先列清能力和状态，不擅自将“忘记一个偏好”等同于“删除学生全部学习记录”。

### 4.4 给老师准备可用背景

客观进展通过精确记录查询得到，核心偏好与相关经历通过 Octos 记忆接口得到。它们在 Octos 内拥有共同归属和删除关系；课程输入不是另一份可独立更新的学生画像。

当前 memory/overview 是面板接口，可能包含无关内容和截断标记，不应原样全塞给课程。第一版需要明确限制选取内容、总量、依据编号及截断说明；相关经历采用 search 后按需 load。搜索可能调用嵌入模型，也要计入成本和等待时间。

已有 memory API 按认证 profile 取存储，不具备完整的老师参与者与适用范围语义。第一阶段记录这个缺口；没有确定共享规则之前，不给每位老师私建一个 namespace 当作最终方案。

## 5. 两个完整接入例子

### 直调问题的目标流程

1. 学生提交问题时生成一次稳定 request_id，同时冻结本次老师基础设定的版本。读取已经准备好的 Octos 背景；记忆暂不可用时正常生成课程，不编造回忆。
2. 原问题的消息写入和课程生成可以并行。可靠提交队列处理失败重试，课程不能等一次记忆提炼才开始。队列仅保存待交付的数据和确认状态，不负责解释偏好。
3. Learning Coach 接收当前问题、基础设定与 Octos 返回的相关内容，使用既有生成调用。后台调用次数不因人格分析增加；新增上下文的实际耗时仍需以后测量。
4. 真实交付的老师文字按稳定编号记录，并明确绑定原问题。生成文件、向设备交付、实际播放分别记录，未播放的部分不能算学生学过。
5. Octos 接收并处理消息与事实。之后再开课时，Octos 返回已生效的记忆和能核查的进展，Learning Coach 只负责使用。

如果问题 A、B 同时生成，A 的回答不能默认挂到最近的 B 下。写入成功但响应丢失时重发同编号；很久后的重试不能只依赖 append_message 的加载窗口。消息交付队列的长期去重保证与事实入口需要协调设计，不能因新增账本就误称原消息接口的限制已经消失。

### 《斜率和截距》的目标流程

本地课程 `slope-and-intercept@0.1.8` 包含 4 节、13 个 beat、3 个课后任务。本阶段逐一核对了实际 ID 和课程文件 hash，并制作了[映射草案](topic-mapping.draft.json)。它还需教研审阅，未写入课程包，也未用于点亮地图。

| 实际章节 | 关联的上游节点 | 能说明什么 |
|---|---|---|
| section-01：认识 m 与 b | mt_WBdHkc2HTf | 接触解析式参数 |
| section-02：斜率的方向与陡缓 | mt_WBdHkc2HTf | 接触该节点中的斜率部分 |
| section-03：纵截距 | mt_WBdHkc2HTf | 接触该节点中的截距部分 |
| section-04：变化量之比 | mt_-3udyo6VyB | 接触由两点理解斜率的部分 |

前三节关联同一个上游节点，但保留不同教学目标，不伪造新的 taxonomy ID。第四节也没有覆盖该节点全部内容。三个任务只是滑块目标验证，不能证明学生独立掌握了整个知识点。

设备离线学到第二节时，先保存实际完成的 beat 事实；联网后原编号补交。此时只能说接触了斜率部分，第三节的截距没有因此获得进度。课后任务单独提交 task_ref、尝试及提示使用情况；重复提交同一次作答只算一次。上游前置边只用于提出学习建议，不能因学了后继节点就倒推前置节点已经掌握。

taxonomy 来源：[固定提交的数据](https://github.com/withmarbleapp/os-taxonomy/tree/533bab591b24c4024f0d70f9296aa4ee560fdd01/data)。映射只保留节点 ID 和本项目教学目标；后续课程发布继续沿用课程库现有的来源和许可处理。

## 6. Learning Coach 后续最小改动清单

这次没有修改技能仓库或本机安装副本。下一次实施应在 Learning Coach 最新 main 新建分支，完成以下改动：

- 给三个课程 action 统一声明 tutor_context 和 learner_context，检查工具入参解析、文字/摄像头/选区调用及各阶段传播。当前工具解析器已有这两个字段，主要缺口在 action schema 和提示说明。
- 明确 tutor_context 提供老师基础教学规则，learner_context 提供 Octos 返回的有依据背景；背景文本按资料使用，不能覆盖当前请求或数学与输出约束。适用于已有 bootstrap、outline 和 section 路径，不加一轮人格模型调用。
- 改写 SKILL.md 的跨会话记忆提升章节，以及 session-state.md 的 Learning Profile promotion。新说明应要求使用 Octos 已提供的背景，真实事件交由 Octos 处理；不要自行生成或维护跨课画像。
- 保留 study/state.json 等当次计划、恢复、编译与任务状态；不能把课程恢复能力一起删除。任何最终模型建议都不能绕过事实依据替 Octos 写长期偏好。
- 完成技能构建及测试后按正式安装器更新现有本机账号，再核对安装态。当前安装副本的上述 SKILL.md 与源码一致，三个 action 的字段缺口也一致。

Octos Learn 接入和这些改动分别测试。不能先传不被 schema 接受的字段，也不能先把静态设定卡称为已经稳定生效的人格。
