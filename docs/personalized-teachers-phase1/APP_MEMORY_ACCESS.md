# Octos 应用记忆接入：现有流程验证与最小接口方案

日期：2026-10-20

本轮只处理两个问题：应用怎样使用 Octos 现有的记忆操作，以及应用记录能否经现有流程变成长久记忆。旧任务偶尔把已删除内容重新写回的处理按复杂度另行评估，不作为本轮完成条件。没有恢复永久业务账本方案，也没有让 Learning Coach 处理长期记忆。

**本轮完成的是源码核对、新增链路测试和接口方案。正式接口代码尚未实现，当前服务不支持本文提出的新方法。**

## 1. 先说结论

Octos 已有可复用的处理能力，不需要重写记忆系统。应用可以直接提交消息或可检索资料；明确的“记住、纠正、忘记”请求目前主要通过命令行和内部能力处理，尚未形成完整的应用接口。

现有应用资料流程能工作，但有四个具体限制：不会在提交后自动开始整理；至少要读过记录才可能被挑选；整理材料主要是短摘要；同一条已被挑选的记录更新后不会再次被挑选。因此，这条流程能够帮助老师找到过去的资料，不能单独承担所有偏好更新。

建议先增加两个通用入口：一个接收用户明确提出的记忆要求，一个让应用请求 Octos 按既有规则挑选资料。继续由 Octos 判断、合并和保存长期记忆。业务应用不负责生成“这个学生长期喜欢什么”的结论。

## 2. 现在提交一条应用记录，会发生什么

下面用“阅读应用记录了一次阅读经历”举例，说明这些能力与课程业务无关。

| 步骤 | 现有行为 | 对应用的意义 |
|---|---|---|
| 提交资料 | memory/ingest 保存记录的编号、来源、标题、摘要及可选正文 | 可以让 Octos 搜到这份资料；不等于形成了长期偏好 |
| 查找与读取 | search 查找相关记录；load 读取记录并增加读取次数 | search 命中本身不算一次读取，不能为了凑次数假装读取 |
| 挑选资料 | CLI memory promote 挑选被读取达到条件、尚未挑选过的 Document | 默认条件是读取至少 2 次；即使设置为 0，程序仍要求至少 1 次 |
| 等待整理 | 被挑中的记录会变成一张带来源的待整理笔记 | 此时原始记录已标记为挑选过，长期记忆还没有更新 |
| 整理并保存 | 已有后台流程调用模型提出修改，Octos 检查后保存 | 模型可以保留、合并或忽略；提交成功不能显示为“已经记住” |

当前没有找到提交后自动调用 promote 的服务调度；可确认的正式触发点是 CLI。处理后台日记或会话的定时流程，不等于它也会自动挑选这些应用资料。

资料被挑选并写成 host 来源的待整理笔记后，已有后台会自动接手，并使用较快的检查节拍，默认每 90 秒检查一次，不必固定等到下一轮 30 分钟会话扫描。这不是完成时间保证：后台必须已经开启，处理还会受额度、排队和错误影响。当前准确的说法是“挑选需要主动触发，挑选后的整理已有后台接手”。

### 哪些内容会被漏掉

资料的标题最多保留 120 字节，摘要最多保留 300 字节，可选正文最多保留 16 KiB；中文通常占多个字节。**超过这些长度时，现有程序会直接截掉尾部，保持文字编码完整，但不会因此拒绝请求，也不会返回截短提示。**应用应自行控制资料长度，不能靠等待报错来发现关键内容丢失。

即使正文保存成功，现有挑选函数主要把标题、摘要和来源放进待整理笔记，不会完整携带正文。

例如，摘要只有“完成一次阅读”，正文里才写“用户希望以后先看图”。即使记录被挑中，整理模型也看不到正文里的这项要求。本轮测试已经复现这一点。这说明不能为了省事，只传一个空泛摘要，再期待 Octos 从未收到的材料中理解偏好。

这里有两种合理接入方式，不需要上层再调用模型：真实对话继续通过 append_message 原样保存，由 Octos 提炼；结构化应用事件则按真实字段和已有文本组成资料，供检索。对于用户明确要求记住的内容，使用下面的记忆请求入口。

### 修改同一条资料，会不会更新长期记忆

目前不会保证。既有程序保留“这条记录已挑选过”的标记，内容和指纹更新也不会清除它。本轮测试确认，新内容进入了检索记录，待整理材料仍可能只有旧内容。

这不表示所有内容更新都应该重新整理；文件不断变化时，无限制重复整理也会带来开销。第一版保留现有规则：一次新发生的事件使用自己的稳定编号；用户明确的偏好纠正走记忆请求。是否需要让修改后的应用资料重新进入整理，以后按具体用途再决定。

## 3. 现有流程是否满足个性化老师的需要

| 我们需要的能力 | 当前判断 | 接入方式 |
|---|---|---|
| 记录学生真实说过的话和老师实际回复 | 可以复用，但前端尚未接通 | append_message；保持真实角色和问答对应 |
| 找到过去某次学习的资料 | 可以复用，查找结果不保证完整统计 | ingest、search、load；准确次数仍依据业务记录 |
| 从完整对话提炼偏好和共同经历 | 可复用已有会话提炼，生效时间仍需明确 | 不让 Learning Coach 额外归纳，遵循 Octos 的后台处理 |
| 用户明确要求“以后先看图” | 内部机制已有，应用缺正式入口 | 请求入口接收原话，由 Octos 整理，不能只等资料被读够次数 |
| 用户明确纠正一个已保存偏好 | 已有纠正笔记和整合能力 | 请求带上旧条目编号及用户的新要求 |
| 用户在界面删除某个记忆条目 | 按编号遗忘及副本清理已有 | 请求入口授权本人操作，返回“已接收，等待处理” |
| 应用资料提交后立即改变下一课 | 当前不能承诺 | 先确定需要多快，再评估 Octos 的处理时机；不加业务侧记忆模型 |

## 4. 建议的最小应用接口

以下方法名和字段是待实现草案。正式实现时需同步 Octos 的协议、类型、可用方法声明、权限检查和对应客户端，并补真实请求测试。这里没有给服务增加一个绕过权限的快捷入口。

### 第一个入口：提交用户的明确要求

建议方法名：memory/request。

| 要求 | 应用提供什么 | Octos 复用什么 |
|---|---|---|
| remember：请记住 | 用户希望记住的原话 | host 来源的 user_request 笔记及现有整合 |
| correct：请纠正 | 旧记忆条目编号和用户的新要求 | 复用 correction 的处理机制与 replaces_id，新增用户请求对应的 host 来源写入 |
| forget：请忘记 | 用户选中的记忆条目编号 | 已有按编号遗忘；首版不增加模糊内容确认界面 |

这个入口用于用户明确提出的要求，不是让业务程序自行判断并宣布“学生长期喜欢什么”。一句普通学习问题是否包含长期偏好，仍可由 Octos 从真实对话中判断。

当前 CLI 没有 correction 子命令；模型工具已有该类笔记，写入时标为 model 来源。此处新增的是应用代表用户提交 host 来源纠正的入口，底层处理组合已由链路测试验证，不应把它描述成直接包装一个已有 CLI 子命令。

请求建议包含一个由客户端生成、重试时保持不变的 request_id。Octos 在本人的范围内识别重试：同编号同内容复用原结果，同编号不同内容报冲突。具体保留方式在实现时选最小方案，不扩展为业务事件数据库。

实现前要明确请求编号在处理结束后如何保留，不能只在待整理文件仍存在时识别重试。correct 和 forget 还要明确目标条目不存在时的返回结果，加入不存在条目及其他账号条目的测试；这些接口行为尚未实现，不能由已有链路测试代替。

初次成功只返回：请求编号、已接收的操作、后台整理是否开启，以及“已接收，等待处理”。不要返回内部文件路径，不允许调用者自己填写 origin 或冒充其他账号。传入的编号与文本必须校验，继续复用已有的内容检查。

第一版不把“已接收”包装成“记忆已修改”。应用仍可用已有读取接口核对内容。若之后需要向用户报告某次操作最终完成、被忽略或失败，再增加可查询的处理结果；不能用“暂存文件消失了”直接推断操作成功。

### 第二个入口：请求 Octos 挑选应用资料

建议方法名：memory/promote，对应已有 CLI 操作。它只将符合条件的资料交给现有后台整理，本次调用不增加一轮模型生成。

首版建议沿用读取条件与数量上限，并允许限制资料来源。例如阅读应用可只申请处理 reader 来源，学习应用可只处理自己的来源。按来源过滤应发生在截取数量之前，避免其他来源占满名额。这只是限定本次处理材料，不代表来源标签提供了额外权限。

当前 CLI promote 没有按来源筛选的参数，因此 sources 是本次需要新增并测试的行为，不是现成包装。它不应改变读取门槛。接口完成后，还需明确由应用在哪个操作或后台流程中调用；提供接口本身不会自动完成这个接入。

返回被挑中的记录编号和数量，以及“已交给后台整理”。没有符合条件的记录时，返回零条的明确结果；不要伪造读取次数，或暗中强制把所有新记录提升成长久记忆。

这项接口足以把已有命令行能力提供给应用。是否自动调用、多久调用、预算多少，是后续运行策略；本次不新增一个业务侧定时任务去调用模型。

### 开发时的请求示例

下面只是协议草案示例，当前不能向服务发送这些方法并期待成功。应用的账号来自 Octos 已认证的连接，例子中没有可切换他人身份的字段。

```json
{
  "method": "memory/request",
  "params": {
    "request_id": "reader-remember-001",
    "operation": "remember",
    "content": "以后介绍新概念时，请先给我看图。"
  }
}
```

纠正时 operation 使用 correct，增加 entry_id 并携带用户的新要求；遗忘时 operation 使用 forget，只提供选中的 entry_id。entry_id 使用已有长期记忆条目的编号形式，例如 ^maaaaaa，不接受文件路径。

成功回执建议为：

```json
{
  "request_id": "reader-remember-001",
  "status": "accepted",
  "refresh_enabled": true
}
```

这里的 accepted 只表示请求已保存，界面对应“已收到，等待整理”；refresh_enabled=false 时，还要说明当前后台整理没有开启。不能根据这份回执宣布下一堂课一定已经采用新偏好。

资料挑选示例：

```json
{
  "method": "memory/promote",
  "params": {
    "sources": ["reader"],
    "min_visits": 2,
    "limit": 20
  }
}
```

返回的记录编号表示“已交给后台整理”，不是“已经写进长期记忆”。sources 限定提交者本人范围内的资料，不能扩展到其他账号。正式实现需限制文本长度、来源数量、单次处理数量，并复用已有的调用权限检查。

两个入口只接收请求或生成待整理材料，不直接另起一个模型去改写记忆文件。实际修改继续交给持有该账号处理锁的现有后台流程，避免为了增加接口又创建一个同时改写记忆的处理者。

### 哪些内容留待以后

本轮不要求新增永久业务账本、不重排证据等级、不决定老师共享规则，不建设防止所有旧任务写回的复杂机制。按用户要求，如果现有处理顺序能简单避免旧任务写回，就顺手处理；需要大幅改造时可以暂不支持，但如实说明。

## 5. 本轮新增测试证明了什么

Octos 分支：codex/app-memory-access，基于同步后的 main ed92309a，测试提交为 29471385。新增[链路测试](../../../octos/crates/octos-cli/src/memory_consolidate/app_pipeline_tests.rs)，目前 7 项通过；cargo fmt --all -- --check 和 cargo check -p octos-cli --features api 也已通过：

1. 未被读取的资料不能通过挑选条件，阈值设为 0 也一样。
2. 符合条件的应用资料能够经过待整理笔记，最终由现有引擎保存为长期记忆，全程不需要 agent turn。
3. 资料正文里的独有细节不会自动出现在挑选后的整理材料中。
4. 已挑选资料更新后仍保留旧标记，不会再次被挑选。
5. 应用资料不能授权删除已有记忆；整理失败后材料保留，之后可以正常重试。
6. 用户的纠正笔记能够更新指定偏好，并保留无关记忆。
7. 现有引擎在关闭模型合并的情况下，仍能执行按编号授权的遗忘，并保留无关记忆。

这些测试使用真实的本地记录存储、笔记生成、权限规则和写入逻辑，但模型回复由测试预先给定。它们证明流程能否走通，不证明真实模型一定会正确理解所有课堂内容；没有调用付费模型，也没有修改本机账号的记忆。

测试从 memory/ingest 使用的记录存储步骤开始，没有通过网络调用新接口。既有 ingest 的输入检查此前已验证，本轮没有把它称作新接口验收。正式应用接口仍需实现并验证账号归属、请求重试及返回状态。

复现：在 Octos 仓库运行 cargo test -p octos-cli --features api --lib app_pipeline_tests。

## 6. 后续实施顺序

先实现 memory/request，使应用能够复用现有的记住、纠正和按编号遗忘能力；返回内容明确停留在“已接收”。再提供 memory/promote，复用现有资料挑选和后台整理，不改变“被读过才参与”的规则。

完成这两个入口后，用自动测试覆盖本人与其他账号、参数错误、重复请求及已有处理流程，再在正常本机环境检查方法是否可调用。用户原始对话的 append_message 接入可以随后独立推进，不必等一个新的记忆系统建成。
