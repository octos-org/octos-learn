**第一阶段已完成：现有流程调查、能力验证、课程知识点映射草案和最小接口方案均有产出，审查发现的文档问题也已修正。**

记忆提炼、纠正和遗忘继续统一由 Octos 处理。老师之间怎样共享记忆、偏好多快生效，以及原始业务记录存在哪里，仍按已有约定留待确定。本次没有替这些问题选默认答案。

## 3. 证据及其边界

独立审查重新运行了 Octos 新增的 7 项链路测试和格式检查，均通过。审查还核对了源码、课程包及固定提交的 taxonomy 文件，确认课程映射中的文件散列一致。本次收尾针对这些发现核对源码并修改文档，没有改生产代码，也没有重新运行上述测试。

这 7 项测试使用真实记录存储、资料挑选、待整理笔记及整合逻辑，模型回复由测试预设。它们证明现有处理流程能走通，也证明正文遗漏、更新后不再挑选等限制；不证明新网络接口、跨账号权限或真实模型理解质量已经通过验收。

诊断脚本对 `taxonomy_commit` 字段只作记录，文件散列能验证传入文件是否与草案一致，不能独自证明它来自哪个上游提交。本次独立审查另行核对了上游固定提交；以后更换版本时仍需重新核对。

没有新增真实账号的记忆写入、付费模型调用或部署。原始测试与接口核查结果见[第一阶段报告](REPORT.md)和[应用记忆接入方案](APP_MEMORY_ACCESS.md)。

## 4. 下一步实现必须落实什么

1. 在 Octos 实现 `memory/request`。请求处理结束后仍需识别重试，不能只靠尚未删除的待整理文件去重；明确纠正、遗忘目标不存在时的结果，并测试其他账号不能操作本人的记忆。首次回执仅表示“已接收”。
2. 实现 `memory/promote`，补来源过滤测试，并落实谁在什么操作后调用。只有接口而没有调用方，应用资料仍不会自动进入挑选流程。
3. 前端真实问答的 `append_message` 接入可以独立推进，不依赖新增永久事实库。保留真实角色、问答对应关系和重试处理。
4. 接通课程上下文后，再验证“真实学习 → Octos 处理 → 下一课采用”的完整体验和生成速度。通过底层测试不能代替这项验收。

单次遗忘的完成查询留待以后；旧后台任务偶尔重新写回已删除内容的问题，遵循用户约定：容易修复就做，需要大幅改造时可以暂不处理。这两项不阻止第一阶段收尾。
