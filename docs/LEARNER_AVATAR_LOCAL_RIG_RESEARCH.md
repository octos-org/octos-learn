# 耳朵、头发与嘴巴：局部绑定方案再评估

日期：2026-11-03。用户要求先研究方案；本轮只读现有代码与 PR、核查官方资料并记录建议，未修改运行代码、生成新素材、提交推送、合并或部署。核查基线为 `e20c489e`，工作区原本干净。

## 结论

建议保留 MediaPipe 捕捉、四角色设计、已认可眉眼和现有录课/配音/课包链路，**先给星狐的一只耳朵和一撮头发制作独立局部素材与绑定，和当前绘制器做同输入对照**。嘴巴保留第三轮的光滑下唇，随后分别处理口腔素材分辨率和多口型。

真正需要改变的是资产和绑定结构。把整图网格加密、换成 WebGL 或继续调弹簧，不会自动补出被挡住的毛发、耳朵背面或新的发音形状。成熟的 Live2D / Spine 也使用纹理网格；区别在于按部件准备素材、局部拓扑、明确支点、预先设计形状、遮挡与运动范围。

这是建议与待验证假设，**本轮未证明新方案已达到用户期望**。不把小型自定义绑定称为完整 Live2D，也不承诺单张图自动生成专业模型。

最近 `c8419c85` 已改过耳部朝向/滞后、头发世界坐标弹簧和下唇抗锯齿，见[第三轮修正](LEARNER_AVATAR_HEAD_FOLLOW_MOUTH.md)。用户最新反馈是嘴巴有所改善，耳发仍不满意；优先于旧文档中“用户尚未看过”的说明。

### 从代码能确定的限制

- `painted-fox.ts`：704px 完整画面使用 22×22 规则网格，间距 32px，所有部位共享同一张不透明立绘；面部先单独绘制后放回。存在眼/眉/口的内部素材，但**没有独立的完整发束和耳前/后层**。
- `painted-secondary-motion.ts`：耳部局部投影/旋转后，以空间权重混入整图顶点；头发只有侧发/前发的大范围权重和少量位移通道。权重按坐标定义，不识别实际每撮头发的边界。给模型加惯性不能改变这一点。
- 一个共享连续网格难以表达“耳朵从前发后面露出来”或“发束移开，露出下面的另一束毛”。边界附近还会随权重混合而挤压；增加网格密度能减少粗糙折线，不能产生新表面或改变遮挡结构。
- 最近报告的最小三角形面积指标约 41.5，原网格对应指标 1024。正值只排除翻折，**不能排除严重压缩或拉伸**；约 4% 的比例不应解释为视觉合格。这是既有模拟极值报告，不是本轮实机测量。
- 嘴巴使用平滑上/下边界与口腔重采样，已改善锯齿；有效口腔取样区域仍很小，三款新角色共用星狐口腔。高清画布或更高阶插值不能恢复未画出的细节。
- `lip-sync.ts` 的 `envelopeLipSync` 目前只产出 `jawOpen`：声能不能区分同音量下的不同发音。读取 `aligned-visemes-v1` 的能力不代表已有对齐口型的生产者。

这些是代码与报告诊断。本轮查看了保留的耳部对照静态图，没有重开摄像头或进行新的浏览器/电视验收。

## 2. 成熟方案有哪些可借鉴的地方

### Live2D Cubism：最相关的制作参照

官方[素材分离说明](https://docs.live2d.com/en/cubism-editor-manual/divide-the-material/)要求分离部件，并补画动作后会露出的区域。[网格准备教程](https://docs.live2d.com/en/cubism-editor-tutorials/import/)强调按部件形状布点，嘴唇、睫毛、眉毛等需要有针对性的网格。

[物理设置教程](https://docs.live2d.com/en/cubism-editor-manual/physical-operation-setting/)先要求准备摇摆的参数形状，再通过单级/多级摆控制参数。它说明物理模拟负责驱动设计好的运动，不会替代素材和形状制作。[官方口型教程](https://docs.live2d.com/en/cubism-editor-tutorials/mouth-aiueo/)提供五种元音口型的制作示例。

直接采用 Cubism 的优势是已有建模、形状插值、物理、遮罩与运行框架，[官方支持 Web 和 Android 等平台](https://docs.live2d.com/en/cubism-sdk-manual/platform/)。但仍要制作本角色的模型；换 SDK 不会把平面 PNG 自动变成合格角色。正式发行的授权需要按产品用途确认，不能承诺免费，依据[官方 SDK 许可](https://www.live2d.com/en/sdk/license/)。本轮没有购买、安装或集成 SDK，也没有判断本产品必然属于哪项许可。

### Spine / Inochi2D：可参考，暂不另开迁移

Spine 的[纹理网格](https://en.esotericsoftware.com/spine-meshes)支持骨骼权重和形状关键帧；[物理约束](https://en.esotericsoftware.com/spine-physics-constraints)适合头发等二级动作。它是可用的制作框架，但仍要分层素材和绑定，不能据此保证人脸优于 Cubism。

Inochi2D 的[官方说明](https://docs.inochi2d.com/en/latest/inochi2d/about.html)同样基于分层画稿和参数驱动网格。其[参考实现](https://github.com/Inochi2D/inochi2d)列出 WebAssembly 工具链条件，[TypeScript 实现](https://github.com/Inochi2D/inochi2d-ts)也存在，但不是已在本项目通过验收的替代品。当前先验证素材与局部绑定，比同时引入另一套运行时更能直接回答质量问题。

## 3. 三个部位分别怎么做

| 部位 | 当前问题根源 | 建议的局部升级 | 首个可判断的结果 |
|---|---|---|---|
| 头发 | 按画面区域推顶点，没有明确发束；相邻毛发和背景一起被拖动 | 从当前原画保留纹理，分离少量主要发束、补出下面的底画，按发根到发尖建立局部骨链/网格 | 发根随头，发梢有限滞后；相邻发束不被连带拉长，移开后没有洞或重复残影 |
| 耳朵 | 只有正面耳纹理，缩窄无法显示背面、耳缘和真实遮挡变化 | 每耳独立支点；准备对齐的正面/有限侧转形状、必要的后侧毛面与根部遮挡 | 单耳能转向并保持，内耳可见面积和轮廓合理变化，另一耳和头发保持稳定 |
| 嘴巴 | 小口腔放大；轮廓模型有限；最终配音只有音量开合 | 保留新下唇；补高清口腔/唇部，设计少量兼容的口型形状；以后再接音素/视素时间 | 微开、大开、圆唇、横向开口之间清楚且连续；闭口回到原画，配音时不乱猜发音 |

### 头发：先一撮，再扩展

先选择和脸/耳朵少交叉的一撮侧发，制作透明边缘与底画；静止重组必须与当前画面吻合，不能先接受明显拼接，再用运动掩盖。

候选制作参数是每撮 2–3 段骨链、固定发根、近似保持段长并限制弯曲角度；沿纹理方向布点，发梢保留形状。先制作左右有限摆动的合理端点，再让惯性驱动它们或用带长度约束的骨链驱动局部网格。数字是试验设计，不是已经验证的最佳配置。

通过单束后再考虑刘海/两侧/后发约 6–8 组。不要逐根毛发模拟，也不要给短毛连续吹风。服饰、脸、耳朵不得被发束权重带动；头动停止后有限收敛，不持续漂浮。

### 耳朵：先解决画面，再解决时间

先做一耳“正面—侧转—回正”静态关键形状，确认耳根、外轮廓、内耳毛、耳缘，以及与前发的遮挡。随后再加入左右独立的转向/保持事件和有限随头运动。自然动作不能简单固定成头朝哪边耳朵就必须朝哪边；角色表演和头部带动分开设计，具体参考已有[动物研究](LEARNER_AVATAR_ANIMAL_EAR_RESEARCH.md)。

不同关键形状需要对齐支点和兼容拓扑。优先插值对应顶点、控制遮罩与绘制顺序；不能将两张未配准的耳朵直接交叉淡入，那会出现双耳尖/透明叠影。如果背面素材尚不能一致，应限制转角，不用正面纹理硬扭出背面。第一版不尝试全角度压耳或侧脸。

这些内部图层最终应组成一张无接缝的完整插画；不会恢复此前用户否定的可见头/身体/手臂拼接。

### 嘴巴：画面与配音数据分开

先保留 `c8419c85` 的光滑下唇，补更清晰、与画风一致的口腔和唇部。以现有 `jawOpen`、`mouthPucker/Funnel`、笑/撇嘴等通道设计少量形状；闭口、小开、大开、圆唇、横向开口先作为验收姿态，不代表五张 PNG 直接切换。上下唇、口腔/舌头按遮罩组合，拓扑兼容地过渡；不无故增加大面积真人牙齿。

若要正式配音呈现发音差异，还需最终 TTS 的可靠音素/视素时间信息或对最终音频做对齐。纯音量继续作为后备，不能从文本或振幅伪造精确时间。不能把原摄像头嘴型直接套到合成声音上。此项可能涉及提供商能力、课包验证与格式协作，应由整体接入 agent 配合，局部美术试验不直接改服务端格式。

## 4. 路线选择与验证顺序

| 路线 | 改善空间 | 工作量和主要风险 | 当前建议 |
|---|---|---|---|
| 整图网格加密、继续调权重 | 能缓解局部折线、幅度和时间问题 | 无法补遮挡/背面，容易继续循环调参 | 仅作小修，不作为主要路线 |
| 同一原画的局部素材 + 定制局部绑定 | 可保留现有脸和系统，针对三处逐步解决 | 分层/补画/形状制作是主要工作；代码成本也存在，需严格限制范围 | **先做星狐局部对照** |
| 正式 Cubism 模型 + Web SDK | 成熟制作与运行工具，适合插画脸部表演 | 仍需模型制作与编辑器操作，发行许可待确认，当前没有现成四角色模型 | 若局部试验暴露出需大量自建工具，再评估迁移；不能承诺换引擎即提升 |
| 全新 3D / 每帧生成式动画 | 可能支持更大角度或新表面 | 会重开用户已反复否定的画风/质量/设备适配问题 | 本轮不推荐；既有失败实测不重复冒充新候选成果 |

具体顺序：

1. 从当前提交保留旧绘制器作为可回退对照；后续运行代码在独立分支/worktree 修改，避免直接改变 PR #119 和整体接入 agent 的工作。
2. **资产关**：只做星狐一耳、一束头发和它们移开后露出的区域；先验证自然重组没有白边、色差、双影，不重生成整张脸。不合格就修素材，不靠增大网格位移。
3. **形状关**：手动滑杆查看正负摆动及中间态，检查轮廓、层间遮挡和毛纹密度。新旧同输入并排，不用不同动作速度制造改善印象。
4. **动态关**：同一段合成头姿和既有参数回放，比较慢转、快速往返、突然停下与静止。待机转耳和头部跟随分开开关。先控制自然度，再扩到双耳、其余发束，最后才是另外三角色。
5. **嘴部关**：保持已改好的轮廓，分别验证高清素材与形状插值；不把口型数据缺失归咎于画稿。先不修改音频时钟与课包。
6. **整合关**：接入共享舞台适配层，保留 `FaceFrame`、角色 ID、捕捉/录制/最终音频和现有服务器校验。模拟采样、暂停、跳转和恢复要处理二级动作状态；不能只在预览里好看，课包播放却漂移。

## 5. 验收依据与协作边界

自动验证需要从“网格不翻折”扩展为局部长度/面积畸变、发根固定、遮挡/重组、无重复纹理和复位。阈值先按美术允许的运动范围制定，不用单一像素差或网格面积作审美评分。

视觉验收必须看实际绘制结果：耳朵是不是同一个结构在转、发束是不是从固定根部动、嘴巴是不是连续而清楚；用户此前的认可不延伸到新素材。高清静态图不等于连续动画合格，离线编码帧率不等于摄像头实时帧率。

暂不承诺新的 FPS。独立图层和 GPU 绘制可能减少整幅 CPU 像素重采样，但层数、遮罩、填充率和设备都会影响结果。WebGL 是可选的绘制实现，不能解决素材缺失。安卓大屏需后续与摄像头、语音识别、白板并行实测。
