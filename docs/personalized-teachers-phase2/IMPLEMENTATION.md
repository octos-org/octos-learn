## 现在能够做什么

学生的原问题、实际交付的课程和老师文字、连续播放完成的片段、每次作答和查看提示，已接入真实课堂入口。记录先在设备保存，再通过 Octos 确认的本人账号上传。课堂生成和播放不等待记录写入，也不增加用于整理记忆的模型调用。

“全部学习记录”中新增“学习经过”，可以查看各遍学习的不同片段数、作答数和原记录。生成课程不等于学完；跳到最后不能补齐中间片段；回放不增加一遍，明确重新开始课程才创建新的学习实例和练习状态。旧数据只保留能够证明的恢复位置，不补造过去的学习次数。

长期记忆仍只由 Octos 处理。产品数据库保存原始事实和机械传递任务，不生成学生画像、不理解偏好、不调用模型做摘要。Learning Coach 在生成新课时主动读取这些事实，属于后续接入，本次不把“查询接口存在”说成“老师已经会使用这些经历”。

### 记录与计数规则

- 问题提交、请求路由、老师实际交付、课程交付是不同事实。纯文字、语音、选区直调均接入；图片及普通 turn 路径保留事实但不再复制同一份会话消息。
- 同一遍的同一片段在不同日志中回放，只算一个不同片段；原始回放记录仍保留。作答以学习、日志、题目、操作编号识别；重新打开不导入旧尝试，新一遍不继承旧成功与提示。
- 生成课程以原问题标识本次生成，另保存实际交付的解析后事件数组的 SHA-256 和事件数。流式内容变化，即使文件路径和事件数相同，也有不同的交付记录。这个哈希不是课程包 ZIP 哈希，也不把一次生成的问题编号称为内容哈希。
- 课程包身份同时包含包名、版本和归档 SHA-256。知识点只使用与已审核对应表完全一致的内容，不按标题相近推断。
- 查询按原发生时间提供 UTC 半开区间 `from <= occurred_at < until`，接收顺序另存。设备时间不是可信考试时钟；迟到补传在下一批查询纳入。没有掌握度或独立理解的推断。
- 单条文字上限 64 KiB；提交最多 100 条、HTTP 1 MiB；设备按更小的字节预算分批。首次认证无法确认归属、本机配额不足或记录格式错误时，只能保留尚未提交的内存任务并提示未保存，不承诺关闭页面仍可恢复。

### 问答怎样进入 Octos

SQLite 持久保存待交付原文，不保存登录 token。持有本人认证的在线设备领取 30 秒任务，使用确定的 `client_message_id` 追加原文，核对 Octos 的序号和原线程绑定后登记回执。用户消息成功后才发送对应老师回应；过期或取消的领取结果不能确认新任务。

旧 Octos 不支持可靠的长历史重试时，不领取这些副本任务，界面显示仍待交付。新能力通过 `session.append_message.full_history_retry.v1` 明确协商；没有该声明，不能推断可靠重试。辅助连接本身没有会话能力确认，因此先打开待交付任务实际所属的会话，确认声明后才领取任务；不为探测创建虚构会话。关闭应用时任务保留，下次登录继续；不承诺无人在线时产品进程能自行代表用户写入。

Octos PR #2854 用现有会话写入锁保护“重新读取当前历史、查重、追加”，同时保留原线程和序号。长历史可能需要临时读取完整内容，增加该追加操作的时间和内存，之后仍保持原有受限的常驻历史。没有建立永久业务回执库；回滚或删除后的编号不承诺永久不可再用；不新增跨进程写锁。

### 删除的确切范围

“删除这次学习记录”移除产品正文与统计依据，取消尚未交付的对话副本，保留必要编号拒绝旧设备补传。它不会删除 Octos 已保存的对话或长期记忆。

现有白板卡片的删除先持久保存整块白板的清理请求，再移除卡片；请求没保存成功就保留卡片。其他设备不仅拒绝已知子记录，也拒绝这个会话下此前从未上传过的新学习编号。清理 Octos 的请求单独领取和重试，不保存凭据。

Octos `session/delete` 当前成功响应只证明接口接受并执行了删除处理，其内部部分文件清理仍是尽力而为，不能据此承诺全部副本已物理消失。已经发出的追加请求与另一个系统同时删除之间也没有跨系统原子保证。本阶段不提供“老师彻底忘记”的按钮。

## 性能与正常环境

本机 Node 24.16.0，10,000 条记录、1,000 遍学习的合成测量：写入约 699 ms；列表 p50 约 6.02 ms，最大 11.79 ms；持有写锁时约 0.13 ms 返回繁忙。同步 SQLite 仍占用事件循环，不能声称没有任何影响。

同进程语音转发另用 21 组交错的本地替身测量：固定供应商延迟 5 ms；无历史并发时 p50 6.19 ms，同时进行历史查询和繁忙写入时 p50 12.42 ms，最大 13.90 ms；恰好 42 次替身供应商请求。数据库没有等待写锁数秒，但查询仍增加约 6 ms。因此客户端已将后台同步推迟到课堂空闲。脚本分别是 [存储测量](../../scripts/benchmark-learning-history.mjs)和[共享语音进程测量](../../scripts/benchmark-learning-history-relay.mjs)。这些都不能代替真实课程首片段速度或生产容量验收。

正常环境为 `https://127.0.0.1:5173/` 和 `127.0.0.1:50080`，沿用默认 `~/.octos`。已用候选 Octos `110be993`、正常默认功能构建并启动；正式安装的 Learning Coach 为 0.15.0。用户明确授权的 6 次真实课程生成已全部完成，未增加第 7 次。基线为 main `4973499` 的完整前端，候选包含 `a4eb939`；两者通过同一正常 HTTPS 地址、同一候选后端、同一本机账号和相同模型 `gemini-3.6-flash` 运行。顺序为基线、候选、候选、基线、基线、候选。

计时从提交问题到 DOM 出现第一个实际 OLL 板书节点；测试阻止了 TTS 供应商调用，所以这不是首段音频耗时。每次前端只有一次课程 action，普通 turn 为零。供应商请求已从各次持久生成日志逐条核对：每个请求都只执行一次，数量差异来自原有的课程分节生成，未发生 HTTP 重试，也没有新增整理记忆的模型请求。

这组首画面中位数未变慢，但各次模型选择的章节数不同，不能视为等工作量的成本对照或一般性能保证。第一次基线的收集器等待了旧的结束信号，随后使用已保存的成功任务和原始日志确认结束及请求数，保留原首画面时间，没有重复生成。自动化浏览器的本地网络权限问题在付费调用前解决；之后完整的 6 门都生成成功。

## 电视实机验收

用户明确同意安装后，在 M3G2（Android API 33 / WebView 101.0.4951.61）使用 `adb install -r` 更新，沿用原账号和设置，未卸载或清空数据。安装前只备份本地学习文档，没有导出凭据或 Cookie。本地库从版本 1 升为版本 2，原有 112 条文档在升级和全部验收后仍逐条一致。旧应用不能直接读取升级后的库，回退 APK 时必须先处理这项兼容限制。

第一次安装的 `b0e83a6` 暴露了真实兼容问题：WebView 101 没有 `AbortSignal.timeout`，导致核对账号前失败。已在独立提交 `ec5b28d` 中对本次新增的历史请求统一提供 `AbortController` 回退，保留超时保护，并测试了账号核对和请求超时。重新打包、覆盖安装后，已从设备内 APK 核对源码为 `ec5b28d144af9c2a1db77bba1ae6e8887385f08d`。构建元数据的 dirty 标记来自尚未提交的文档及其他任务文件，应用源码修正已提交。

实际验收使用内置《一次函数 y = mx + b 的图像与性质》0.1.8，不再调用课程生成模型，也不调用付费语音供应商：

- 原有课程能够继续，原笔迹和滑块值恢复；“重新开始”另建一遍，原记录保留，新一遍没有继承旧练习成功状态。
- 正常播放保存了 5 个有音频正常结束依据的讲解片段；随后用“下一片段”跳到结尾，没有把未播放的其余片段补成完成。最终记录只有 1 次开始，不因重开增加遍数。
- 对斜率滑块发送 20 次真实 WebView 方向键输入，从 -2 到 -3，每次操作记录作答，最后一次满足程序条件并开放下一题。这是 20 次滑块操作记录，不能解释为学生认真答错了 19 次。
- 仅将当前应用 WebView 模拟断网，设备 Wi-Fi 和其他应用不受影响。146 条待同步记录在第一次断网重开后编号、内容不变；断网时对下一题再操作一次，第二次断网重开后该作答及滑块值仍保留。最终 149 条记录包含 21 次操作作答、5 个完成片段和 1 次开始。
- 恢复 WebView 网络后，完整停止并启动应用进程，149 条记录仍逐条一致。练习成功状态与参数恢复另外核对。测试产生的这一遍本机记录保留，没有自动删除。

脱敏的检查结果与 APK 校验值见 [DEVICE_ACCEPTANCE.json](DEVICE_ACCEPTANCE.json)。公网尚未发布历史接口，因此电视显示“已保存在本机，等待同步”或同步重试提示；这次只验收电视本地保存、恢复和真实操作采集，不能称为公网同步已经通过。同步服务和丢回执重试由前述本机服务与浏览器测试覆盖。最终只读检查曾因自动审批服务额度不足而未执行，用户要求继续后恢复检查成功，没有绕过审批。
