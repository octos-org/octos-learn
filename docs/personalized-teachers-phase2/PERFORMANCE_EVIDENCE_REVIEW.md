# 第二阶段免费性能证据复核

对应全阶段 N-05、第二阶段 P2-08。付费供应商对照继续按用户决定暂缓；本轮只使用隔离账号、固定课程和本地音频，不修改本人配置或公网。

## 这次复核做了什么

复核的目标是判断新增学习记录会不会耽误学生开始听课。AGENTS.md 要求首段可播放速度不回退、交错对照 p50、零新增模型往返，没有要求必须重新付费生成课程。合并判断应依据实际证据和覆盖范围。

沿着“提交问题 → 发起课程 action → 取得首份课程 → 编译画面 → 播放旁白”核对代码，发现两个有具体证据的问题，并完成修正：

| 问题 | 旧行为及复现 | 修正 |
|---|---|---|
| 同步开始后没有重新检查课堂状态 | 先让删除信息查询或第一批上传停在等待响应，随后将课堂设为忙碌。旧代码仍上传下一批，并查询问答交付；两项测试在旧代码上失败 | 每批查询、上传，以及每项问答交付/删除清理开始前重新检查课堂状态；已发出的操作仍保存有效回执，未处理的记录保留，空闲后继续 |
| 首份课程到达前被当成空闲 | 第一项修正后，完整前端预检仍观察到 6 次上传和 1 次交付状态查询。原因是课程任务已被接受、提交等待状态已结束，但播放器尚不存在，原忙碌判断没有覆盖这段时间 | 为记录维护单独计入“本课堂的生成任务仍在进行”，不依赖播放器是否已创建，不改原有音频所有权逻辑 |

第一项提交为 `867f468`；新增完整前端检查为 `e9639c4`；第二项修正为 `f28cda2`。最终完整单元 1227 项通过（原 1222 项加 5 项），类型检查和 public 构建通过；记录相关 23 项及隔离浏览器 2 项通过。完整 lint 无错误，保留原有 37 个警告；随后更改的工作区文件单独 lint 无错误、2 个原有警告。详细日志散列与失败复现摘要另存复核 JSON，不把重复运行的数量相加。

已发请求没有被假装取消。记录上传响应会先核对并保存，已经开始的一项追加/删除会完成其回执；下一项才暂停。已领取而尚未处理的任务仍在服务端，按原租期与重试规则恢复。因此这里保证的是停止继续发送一串维护工作，不保证能够中断已经在服务端执行的 SQL 或撤回已发送的请求。

## 现有证据覆盖哪些代码

| 路径 | 核对结果 | 依据与限制 |
|---|---|---|
| 提问和课程交付记录 | 调用 record/stage 后继续原课程流程，未 await 网络或身份核对。后台写入会等待本人身份和 IndexedDB | `recorder.ts`、`learning-workspace.tsx`、`delivered-material.ts`。stage 内仍有同步复制，课程快照仍有 JSON 序列化，不能仅凭“后台”二字说没有开销；完整前端测量包含这些实际代码 |
| Runtime 保存播放证据 | 原先的三份播放数据读取仍保留；后续检查点与事实共同提交，不在同步 Runtime 回调中等待 HTTP | `learning-document-store.ts`、`playback-recorder.ts`、`use-oll-lesson-runtime.ts`；固定课程实际编译、绘制和播放，并非跳过记录模块 |
| 记录上传和问答交付 | 课堂忙碌时本机保存继续，维护在下一批/下一项前暂停；空闲后恢复 | 本轮两项先失败后通过的协调器测试，以及追加/删除的三项新测试；完整前端新场景检查原 500 条待传事实全部保留 |
| 模型请求 | 原课程 action 的选择、请求参数和既有 turn 回退保留；记录代码不发起模型 action 或 turn | 前端逐处差异核对；免费完整前端每次只允许 1 次课程 action、0 次普通 turn。这是产品不新增课程模型往返的依据，不是宣称测试实际运行了真实课程模型 |
| 问答进入 Octos | 使用 `session/append_message` 写入原文，不通过 `turn/start` 生成回复 | Octos `413b4b68` 的实际记录路径及既有 [真实进程验收](OCTOS_INTEGRATION_ACCEPTANCE.json)：实际交付客户端、两端重启及丢回执重试，模型请求 0 次。Octos 未来后台整理长期记忆可能用模型，不在这里声称所有后续记忆处理都没有费用 |
| 语音服务 | 相比基线，BYOK 供应商实现和前端 providers 文件未变；本次只增加维护暂停判断 | 原[同进程 relay 对照](RELAY_BENCHMARK.json)必须保留其发现：连续历史查询/忙写时，模拟语音 p50 从约 6.31 ms 增至 11.75 ms，存在共享进程争用。本轮减少本课堂自身的连续维护，不把它说成消除了其他客户端的争用 |

真实供应商的延迟、其他设备或标签页持续读写、任意大小课程快照、Android 原生音频输出，不在这套固定响应结果里得到全面保证。它测的是相同课程/音频下本次产品改动的实际开销。测试结果不能转写成“真实 Google/火山响应速度已验证”。

## 新增的完整前端场景

除原少量历史、大量历史、上传失败三种情况外，增加“同步已经在进行”一组：

1. 候选本机保存 500 条合成待传记录，页面打开后先真正发出同步查询。
2. 只将该查询响应暂留，允许学生从正常输入框提交问题；基线仍运行其原有完整前端。
3. 在课程 action 发出 100 ms 后，将已在途查询交给实际产品/历史处理器处理；首份课程仍固定在 200 ms 到达。
4. 检查学生已开始等待生成后没有新的历史请求，原 500 条记录仍是 pending，同时首段画面和非静音音频正常播放。

这是模拟一次慢响应的自动化场景，不是阻塞数据库或改本人网络。它既检查是否暂停下一次请求，也把真实记录代码和产品服务放进完整前端速度对照。第一轮预检失败的原始结果保留，最终修正后预检通过；不把失败轮次的时间混进正式统计。

正式测量沿用完整 main `4973499` 对比完整 `f28cda2`，四种情况各 10 对、顺序交替，额外一对预热不计入统计。原计时器、200/900 ms 的课程交付、50 ms 的本地音频替身延迟、逐帧可见检查与真实 Web Audio 信号检查均保留；旧静音和缺课反向检查及其适用边界仍见原性能计划。新统计与最终判断在测量完成后补入下节。

## 测量结果与当前判断

四种情况各 10 对已完成，另有一对预热。所有 80 次测量都有本次课程画面与实际非静音音频；每次 1 次课程 action、0 次普通 turn、1 次本地语音替身请求。新增场景的 10 次候选都没有后续历史请求，500 条原待传事实全部保留。原始数据见 [40 对结果](FREE_PLAYABLE_BENCHMARK_F28CDA2.json)，复现摘要及验证日志散列见[复核记录](PERFORMANCE_EVIDENCE_REVIEW.json)。

| 情况 | 基线首段可播放 p50 | 候选 p50 | 候选减基线 |
|---|---:|---:|---:|
| 少量历史 | 613.2 ms | 613.2 ms | 0 ms |
| 大量历史 | 609.5 ms | 613.2 ms | +3.7 ms |
| 上传失败等待重试 | 613.3 ms | 613.2 ms | -0.1 ms |
| 同步已在途时开始生成 | 612.1 ms | 613.2 ms | +1.1 ms |

**结论：代码路径与覆盖复核已完成，发现的两处问题已修复；速度验收仍未确定。** 两组候选 p50 较高，不能直接按“不高于基线”宣布通过。检查以动画帧观测画面和声音，相邻采样可以相差一帧；正式数据的配对差值 p95 最高约 17 ms，存在采样时刻的影响。但这不足以证明上述正差异只是噪声，也不足以直接归因于新增记录。

因此保留全部样本与未确定结论，下一步用免费方法区分计时采样和实现开销。有了具体原因再决定补测方式，不筛掉不利样本、不反复跑到中位数变小为止，也不自行改宽速度要求。付费供应商调用不能替代这项判断，继续暂缓。
