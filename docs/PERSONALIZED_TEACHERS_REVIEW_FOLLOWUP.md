## 3. 几处必须讲准确的区别

### 写入历史，会影响后续记忆

append_message 本身不调用模型，但后台可以读取这些消息并提炼。当前处理依据消息角色认定证据，不能靠写一个 source 标签就解决来源问题。

例如，学生说“我已经学过斜率”，与程序记录“播放到了斜率课第二节”，是两种不同证据。两者都值得保留，但不能把后者伪装成学生原话；也不能直接规定程序记录永远更可信。学生的感受应尊重学生陈述，播放次数则应依照实际事件。第一阶段需要在 Octos 内确定这种表达与使用方式。

这确认了接入时的风险，没有证明尚未实施的课堂记录管道已经发生误归因。

依据：[提炼输入](../../octos/crates/octos-cli/src/memory_refresh/input.rs)、[证据处理](../../octos/crates/octos-cli/src/memory_refresh/extract.rs)。

### 普通遗忘也有清理，但不能承诺所有相关信息永不重现

CLI forget 先提交请求笔记，再等待整合处理。目前缺少应用可调用的正式遗忘接口，这个缺口成立。

但按 ID 执行 hard_delete 时，即使没有 sensitive 标记，也会构造清理目标，处理备份、归档、记忆页面、日记和匹配的暂存文件。因此，报告中的“仅 sensitive 清理”“普通删除不清理暂存产物”需要修正。

已有清理依据 ID 和匹配文本等条件工作。这不能直接保证另一种措辞、仍在计算的任务或稍后提交的结果都不会带回相同含义。应分别验证这些情况，并决定遗忘完成意味着什么；既不能说现有代码完全不清理，也不能说已经完整保证永不重现。

依据：[CLI 请求入口](../../octos/crates/octos-cli/src/commands/memory.rs)、[硬删除计划](../../octos/crates/octos-cli/src/memory_consolidate/mod.rs)、[应用与清理](../../octos/crates/octos-cli/src/memory_consolidate/apply.rs)。

### 缺少条件更新能力，不等于已经证明多设备覆盖

Recall 的 schema_version 表示格式版本，fingerprint 用于识别内容；它们不是“只有当前版本仍为 X 才允许修改”的保护。相关外部接口缺少这种能力，是已知缺口。

但报告引用的 write_long_term 在当前代码中注明没有生产调用者；后台流程另有单实例锁等保护。仅凭文件整体替换，无法证明手机和电视正在直接竞争写入同一偏好。产品的跨设备写入路径也还没实现。

方案要求解决旧操作覆盖新结果的问题；具体采用条件更新、追加操作记录还是其他 Octos 内部方案，要结合选定的事实存储和更新流程决定。

依据：[记录结构](../../octos/crates/octos-memory/src/record.rs)、[记忆存储](../../octos/crates/octos-memory/src/memory_store.rs)、[后台刷新服务](../../octos/crates/octos-cli/src/memory_refresh/service.rs)。

### 技能指令需要改，当前课程状态仍然需要保留

Learning Coach 仓库及本机安装副本仍包含跨会话记忆提升指令，需要与已确认的架构对齐。session-state.md 中的 Learning Profile 又被描述为依托既有长期记忆的逻辑视图，不能仅凭这些文字认定已经运行着一份独立数据库。

后续改写应取消 Learning Coach 自行判断、提升和维护跨课记忆的职责，保留课程恢复、当次计划、编译结果等会话状态。普通 agent 路径与技能直调路径要分别检查，不能假定每次直调都会执行 SKILL.md 的全部指令。

依据：[技能说明](../../learning-coach/SKILL.md)、[会话状态约定](../../learning-coach/references/session-state.md)。

### 补查缓存和延迟，避免把风险写成现存故障

前端旁白短期预取缓存的键包含 narrationId 和文本，不含音色；当前全局 TTS 配置变更另有清缓存处理。今后若按请求选择老师音色，必须让缓存区分该选择或可靠失效。这是已确认的改造注意事项，还不是已复现的换老师串音故障，也不代表已审查所有原生缓存。

后台提炼默认要求会话空闲至少 30 分钟，扫描间隔也是 30 分钟，每轮最多 2 个会话，每天最多 20 次提取调用。逐会话失败上限为 3 次；服务级退避从 5 分钟递增到最高 80 分钟，两者不能写成“失败三次就退避 80 分钟”。另有 host/user_request 笔记的快速整合路径，但 append_message 不会自动生成这种笔记。因此，偏好多久能影响下一堂课仍需要明确体验要求并验证，不能从默认参数推导出固定时限。

依据：[旁白缓存](../src/learning/oll/use-oll-narration-tts.ts)、[默认配置](../../octos/crates/octos-cli/src/config.rs)、[后台刷新服务](../../octos/crates/octos-cli/src/memory_refresh/service.rs)。

## 4. 下一步的范围

第一阶段应交付具体的链路说明、能力缺口和最小扩展设计，重点是：记录来源如何表达，精确学习事实放在哪里，怎样准确统计和删除，技能旧指令如何对齐，以及三个课程入口怎样使用教学上下文。已知缺口不能再被写成笼统的“以后验证”。

仍需后续决定：老师之间共享什么、记忆何时生效、遗忘的完成标准、预制课声音策略。知识点与课程的基本对应必须在学习记录阶段确定，不能等知识地图界面开始后再补。

本次已将上述内容、课后任务与声音验收、实际供应商请求数的性能口径写回主方案。没有因此新增老师范围规则，没有启用定时任务，也没有将源码核对当作运行验收。
