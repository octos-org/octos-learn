这份方案要解决的是：学生选了一位老师以后，这位老师既有自己的性格，又能通过一次次相处，逐渐学会怎样教好这个学生。学生下次回来时，面对的是一位记得过去、了解自己，而且仍然认得出来的老师。

老师还需要知道学生的实际学习经历：上过哪些课程、讲到哪里、某个知识点问过几次、做过哪些练习。这些信息将同时支撑老师的讲解、知识地图和成就，也为以后的复习建议、阶段报告和试卷提供依据。

以下先说明学生会得到什么，再解释记忆和成长如何工作，最后说明开发顺序、验收方法，以及 Octos 目前能做和还不能做的部分。

**本文提到的学习应用是 Octos Learn，即当前 octos-learn 仓库对应的应用；Octos 是它使用的通用服务端底座。**两者共同组成当前学习系统。区分它们，是为了说明代码应该改在哪里，不表示另建一个产品、另一套账号或另一套长期记忆服务。

**已确认的架构原则：记忆只在 Octos 中处理。**自然语言中的长期偏好、师生经历和后续人格成长所需的记忆，由 Octos 统一提炼、更新、合并、检索、纠正和遗忘。Octos Learn 提交真实课堂记录并显示结果；Learning Coach 使用相关记忆生成课程，不额外承担记忆处理，也不启动定时记忆任务。

这项原则不要求把每次播放都写成一段模型总结。软件可以准确记录发生过的行为、按明确规则计算次数；这些事实怎样保存到 Octos、怎样提供给老师，需要验证接口。不要把客观记录和语义记忆的区别，误解成在不同仓库各自运行一套记忆判断流程。

## 1. 先用一段真实使用过程说明目标

下面的“小林”“阿澜老师”“豆豆老师”都是用于说明方案的虚构名字。

小林第一次打开产品，看到几位老师。他选择了阿澜老师：形象安静，声音柔和，喜欢从直观例子开始，讲解时耐心地拆步骤。这些是系统为阿澜设计好的初始特点，刚认识小林时就应该表现出来。

第一堂课讲负数。小林说：“先别给我公式，画一下电梯吧。”老师用上下楼解释正负数。

这句话首先是一个当前请求。它还不足以说明“小林以后学所有内容都必须先看图”。系统可以记下：他们这次用过电梯的例子，以及小林在这次讲解中提出了什么要求。

后来，小林明确说：“以后讲新东西，也先给我看图吧。”Octos 收到完整记录后，负责提炼和保存这条偏好。在相关记忆已经可读取的后续课程中，阿澜可以先展示直观画面；需要连接旧知识时，也可以提起上次的电梯例子。多久生效是后续需要确认的体验要求，不假定写入原话后就已完成长期记忆更新。

过了一段时间，小林对这些内容已经熟悉，说：“这部分不用画了，直接推吧。”本次教学应当尊重新的要求；是否需要改变长期记忆，由 Octos 根据新旧信息处理。记住一个学生，也包括发现他已经变化了。

小林下次又问斜率。系统发现，他之前学过一节相关预制课，也曾向老师问过两次“向右走一步是什么意思”。老师可以说：“你接触过斜率了，这次我们先找找，是变化量还是比值这一步没连起来。”它不必每次都从头讲同一门课，也不能因为问过几次，就断言小林学不会。

小林偶尔改选活泼的豆豆老师。希望豆豆也能了解必要的学习进展，但共享哪些细节、哪些偏好适用，留待后续确定。无论采用什么规则，豆豆不能把阿澜与小林的经历说成自己亲历的事情。

同时，另一个学生选择阿澜时，得到的是同一位预设老师的另一个独立成长过程。小林的经历和习惯不会跟过去。

**第一版需要做成的，就是这段跨越几次课程的连续体验。**我们先把它做实，再增加老师数量和更复杂的成长方式。

## 2. 老师的哪些地方稳定，哪些地方会成长

我们已经确认：每个学生的老师分别成长。老师的成长既需要稳定的身份，也需要允许变化的空间。

| 部分 | 举例 | 谁决定，怎样变化 |
|---|---|---|
| 基础身份 | 名字、形象、基础音色 | 由产品设计；学生一次反馈不会让老师突然换脸或换声音 |
| 初始性格 | 风趣、严谨、亲切、喜欢适当延伸 | 由产品设计；帮助学生一开始就选择适合自己的老师 |
| 对学生的理解 | 学习目标、熟悉的例子、明确表达的偏好 | 由 Octos 根据交互更新，需要能说明依据 |
| 对这个学生的教学习惯 | 先举例还是先推导、步骤拆多细、多久提一次问 | 使用 Octos 提供的适用记忆进行教学；成长范围另行确定 |
| 两人的共同经历 | 一起想出的比喻、解决过的难题、双方的约定 | 由 Octos 从真实记录中处理，查看和遗忘经 Octos 执行 |
| 当前课堂的安排 | 今天赶时间、这一段慢讲、这次不要开玩笑 | 优先响应当前要求，不自动变成永久习惯 |

例如，严谨型老师仍然注重推理的条件和依据。但熟悉小林以后，他可能更懂得在哪一步停下来、怎样鼓励小林自己说出理由。风趣型老师也会逐渐知道，什么例子适合这个学生，以及什么时候应该收起玩笑、直接解释。

这些变化能够形成学生感受到的“人格成长”：老师有越来越连贯的回应方式，有两人独有的经历，也会根据学生的变化调整自己。第一版不需要训练新模型；主要通过使用 Octos 处理的相关记忆来实现，不在 Learning Coach 中另行生成并维护一份人格记忆。

### 让风格真正体现在课程里

只给模型一句“你是幽默老师”，不足以形成稳定的教学风格。每位老师需要简短的行为规则和具体旁白范例。

以风趣型老师为例，可以约定：

- 用一个主要比喻帮助解释一个知识点，避免多个比喻混在一起。
- 玩笑简短，讲完要回到数学问题。
- 学生连续卡住时，优先说明关键步骤和给予具体鼓励。
- 学生要求直接推导时，采用直接讲解。
- 避免每堂课重复同一句口头禅。

同样讲斜率，风趣型老师可以说：“把这条直线想成一段山路：向右走一步，会往上升多少？”严谨型老师可以说：“先比较两个变化量：横坐标增加多少，纵坐标增加多少。”

我们允许表达和教学安排不同，但互动图形表达式、任务条件等程序能够检查的部分，仍要经过既有 OLL 校验。旁白推理和 math 类型板书中的公式还需另做数学质量检查：当前这类板书内容是可扩展对象，不能指望既有校验器检查 LaTeX 语法或公式的数学正确性。文件通过校验不代表每句话、每个公式都正确。老师不能为了表现个性而省略必要条件，或把一个好听的比喻当成证明。

### 把性格写成一份基础设定卡

名字、形象、音色和讲课风格以外，老师还可以在关注点、相处角色和反应习惯上形成区别。每位老师用一份简短的设定卡说明这些特点，并配上少量情境范例。

例如，阿澜的草案可以是：

| 项目 | 具体设定示例 |
|---|---|
| 最看重什么 | 学生找到理由，而不只是得到答案 |
| 怎样与学生相处 | 认真听取意见的讨论伙伴 |
| 遇到错误 | 先找第一处发生分歧的步骤 |
| 遇到质疑 | 先检查自己的解释，允许修正结论 |
| 怎样认可学生 | 指出具体做对的事情，不只说“真棒” |
| 对什么容易表现出兴趣 | 简洁的解法、意外的反例 |
| 小习惯 | 偶尔把好问题称为“值得收藏的问题” |
| 情绪和动作节奏 | 平静，庆祝简短而认真 |

这里的阿澜仍然只是示例，不代表已经选定的老师。每位老师先选清楚一个主要关注点、一种相处角色、两三个典型反应和一个小习惯，再补细节，避免堆出一长串无法一致表现的性格词。

基础设定属于大家都能选择的预设老师，放在 octos-learn 的版本化配置中。它不是某个学生的记忆，不随一次课堂反馈自动改写。每个学生与老师形成的长期经历和习惯，仍由 Octos 处理；生成时组合基础设定与 Octos 返回的适用记忆。

老师的兴趣可以影响例子和表达，但不限制他能够教授的知识范围。例如喜欢天文的老师，也必须能直接回答普通代数问题，不必每次绕到星球上。

### 不同表现，交给适合它的实现方式

| 要表现的特点 | 怎样实现 | 例子 |
|---|---|---|
| 在乎什么、怎样回应质疑 | 基础设定和范例进入 Learning Coach 现有课程生成请求 | 面对反例先检查是否成立，再决定怎样回应 |
| 怎样组织讲解、提问和鼓励 | 在生成目录和旁白时体现，而非事后替换几个形容词 | 看重独立思考的老师，在适合的环节邀请学生先作判断 |
| 开始、被打断、任务完成等固定反应 | 用程序已经知道的课堂状态，选择老师对应的简短台词 | 同一任务完成，阿澜平静认可，豆豆轻松庆祝 |
| 点头、庆祝、等待等动作 | 明确课堂事件触发已支持的动画或轻量视觉效果 | 任务经程序验证成功后，播放一次短促庆祝 |
| 声音与表达节奏 | 绑定老师音色，通过措辞、句长和标点配合；更细参数另行验证 | 平静型老师表达简洁、停顿清楚 |
| 跨课习惯、共同故事和承诺 | 真实记录交给 Octos，后续从 Octos 读取相关记忆 | 提起上次确实发生过的电梯例子 |

前两项仍是生成本次教学内容，不是让 Learning Coach 判断哪些信息要存进长期记忆。Learning Coach 不增加人格分析调用，也不在课程生成后再请求模型把整门课重写成某种性格。需要统一 tutor_context 等入口，使同一设定真正作用到课程生成的相关阶段。

提示词只能提高一致性，不能保证模型绝不偏离。因此规则要配例子、验证不同情境，并允许学生本次的明确要求改变表达方式。学生说“别开玩笑，直接讲”，风趣型老师就应该直接讲。

### 固定反应使用明确事件，不凭动作猜学生心情

程序知道“课程开始播放”“老师被打断”“指定任务已成功”等事实，可以据此选择对应反馈，不需要另调大模型。反应可以准备少量变化，并控制出现次数，避免同一句口头禅或庆祝动作反复打断学习。

例如，同一个经程序验证的任务成功后：

| 老师 | 台词草案 | 动作草案 |
|---|---|---|
| 阿澜 | “这一步，你自己验证出来了。” | 轻点头 |
| 豆豆 | “拿下！这次它没绕住你。” | 一次简短庆祝 |
| 教练型老师 | “这一关完成，准备下一步。” | 简洁标记完成 |

台词必须符合事件提供的事实。如果成功依赖提示，就不能套用“完全靠你自己”；播放结束也不能套用“你已经学会了”。反馈只引用当前事件能支持的信息，历史比较通过 Octos 的可靠记录提供。

暂停、沉默和退出不能直接触发“你很沮丧”等判断。需要分析具体错误或回应学生明确表达的挫折时，使用现有教学或辅助请求，不为每个操作自动调用一次情绪模型。

### 形象、声音和台词要一起表现性格

每位老师除外观外，还需要一份表达配置，约定等待时的表现、庆祝强度、打断后的回应和反馈长度。第一版从已有课堂状态和可用素材开始，避免为了表现性格引入持续高频动画。

当前老师组件已经支持听、想、讲等状态和点击反应，部分外观素材有动画映射，可以作为起点。但这些尚未形成完整的人格表现系统；Android 当前只将 3D 皮肤显示为静态预览，SVG 皮肤仍正常渲染，老师按钮也保留点击反应。新增表现需分别评估，不能直接承诺所有端都有相同的 3D 动作。

当前 BYOK 语音路径主要按音色合成。第一版先通过音色、措辞、句长和标点形成差异；语速、停顿和情绪参数的更细控制，需核实供应商及各端支持后再接入。额外的庆祝语音不能串行挡在首个可播放片段之前。

### 小习惯和仪式要有真实依据

老师可以喜欢收集好问题、在课后邀请学生总结一个发现，或用自己的方式颁发成就。但“这个问题值得收藏”与“这个问题已经保存”含义不同。没有完成相应保存操作，不能宣称已经收藏。

如果以后要展示“问题收藏夹”，需补真实记录和界面，记忆处理仍交给 Octos。跨课承诺也要通过 Octos 保存和取回，不能只靠固定台词表现得像记得过去。

开始和结束仪式应简短、适时出现，不给一个简单问题强加长篇开场。学生可以跳过，不把完成仪式当作已经理解知识的证据。

### 先验证性格稳定，再观察长期相处

先用两位差异明显的老师进行小范围验证，数量仍是建议。先不给它们不同的学生记忆，提供相同问题和课堂情境，检查基础性格本身是否清楚、稳定；然后在 Octos 的相应能力接通后，加入真实记忆验证跨课体验。

这样可以定位问题：如果没有记忆时两位老师就没有区别，应先改基础设定和表现；如果基础性格稳定、跨课行为却不连贯，再检查 Octos 的记录与读取，避免同时改动所有部分。

## 3. 老师之间怎样共享记忆，留待后续确定

**记忆统一由 Octos 处理。**下面讨论的是 Octos 需要理解的关系，不是在 Octos Learn 或 Learning Coach 中再建立记忆处理流程，也不预先决定要建几份存储。

有两个问题需要区分：一件事发生在哪位老师与学生之间，以及一条要求应该对哪些老师生效。

例如：

| 情况 | 后续需要确定什么 |
|---|---|
| 学生学过斜率、反复问过变化量 | 这些学习进展怎样提供给不同老师，具体提供哪些细节 |
| 学生对豆豆说“你以后少开一点玩笑” | Octos 怎样判断“你”指豆豆，以及这条要求的适用范围 |
| 学生说“以后所有老师都先给我看图” | Octos 怎样表示一条跨老师适用的要求 |
| 阿澜与学生一起想出电梯的例子 | 其他老师是否可以知道这件事；知道后怎样保留实际参与者，避免冒称亲历 |
| 学生与两位老师分别有不同约定 | Octos 怎样保留两项各有适用场景的约定，避免互相覆盖 |

这些例子说明要解决的问题，不代表共享规则已经定稿。尤其不能预先把所有师生经历都规定成“只有当前老师能读”，也不能默认所有老师都采用同一条偏好。

### 已确定的边界

- 不同学生的记忆不能混用。每个学生的老师分别成长。
- 老师的基础名字、形象、声音和初始风格，由 Octos Learn 提供。
- 学生与哪位老师互动，是 Octos Learn 应传递的课堂事实；长期记忆的归纳、适用范围判断和更新由 Octos 处理。
- Octos Learn 可以提供记忆查看和管理界面，但操作交给 Octos 执行，不在本地维护另一份会独立变化的学生画像。
- Learning Coach 使用 Octos 提供的相关记忆生成课程，不负责决定哪些话要长期保存。

第一版建议沿用现有登录账号下的 profile，也就是 Octos 区分用户配置和数据的个人空间。如果以后一个账号下有多个孩子，需要先确定真正的学生身份和访问规则，不能只相信网页传来的名字。

### 后续需要一起确定的内容

1. 学习进展、教学偏好和共同经历，分别怎样在老师之间共享。
2. “当时是谁参与”和“以后对谁生效”，在 Octos 中怎样表达。
3. 学生没有说清范围时，Octos 如何处理，什么时候需要问清。
4. 新要求与旧记忆冲突时，怎样更新；学生怎样查看、纠正和遗忘。
5. 当前 Octos 接口是否足够；若不足，需要在 Octos 中补充什么通用能力。

在这些问题确定前，方案不承诺某条要求一定只对当前老师生效，也不承诺新建一个记忆命名空间就能解决。我们先把需求说清，再选择 Octos 内部的实现方式。

## 4. 课堂里发生什么，才足以让老师改变

“课堂事件”只是对发生的事情做记录。例如学生暂停了、问了一句话、拖动了滑块。事件本身并不告诉我们原因。

学生暂停可能因为没听懂，也可能因为有人叫他。我们可以记录暂停，但不能直接据此认定“他讨厌这种讲法”。因此，每一步都要分清：**观察到了什么、可能意味着什么、是否已经有足够依据改变长期习惯。**

第一版建议采用下面的规则：

| 发生的事情 | 现在怎样处理 | 什么情况下影响以后 |
|---|---|---|
| “这次讲慢一点” | 调整这次后续讲解 | 只有进一步表达或其他证据，才考虑长期化 |
| “以后新概念先给我看图” | 本次教学按原话安排，完整记录交给 Octos | 长期提炼和更新由 Octos 完成；生效时间和适用范围待定 |
| “为什么这里除以二” | 解释这个步骤，并提交真实交互记录 | Octos 可据此形成相关经历，不能扩大成能力标签 |
| 多次回放某一段 | 作为一个值得关注的现象 | 单凭回放次数，不改变人格或认定没掌握 |
| 完成一道有可靠判分的新题 | 保留这道题的表现 | 后续接入作答能力后，支持具体知识点的学习判断 |
| 老师说“你已经懂了” | 视为老师的判断 | 不能代替学生作答或明确反馈 |
| 没有回答、安静看课、直接离开 | 继续正常教学，或结束本次课堂 | 不推断喜欢、讨厌或已经学会 |

表中“调整后续讲解”有一个实际限制：已经生成好的音频不会因为一句反馈自动改变。开发时要区分“播放慢一点”和“解释得细一点”。前者是播放控制；后者会影响后续生成内容，如果需要重讲已生成的一段，要明确提供重讲操作，不能让学生误以为整门课已经实时改写。

### 学生不反馈，也应该能正常使用

老师可以记住“上次我们讲了负数，用过电梯的例子”，即使学生从未评价老师。这能提供真实的连续感。

但“学生喜欢电梯例子”“学生已经掌握负数”需要更多依据。没有依据时，保留老师的初始风格和已有有效偏好即可，不必强行制造成长。

老师偶尔可以把反馈机会放进教学中，例如“这一步先看图，还是直接推导？”这种问题既帮助上课，也帮助了解学生。学生可以跳过，不回答时采用默认安排。频率需要通过实际体验确定，不预先规定每课必须回答几次。

### 从猜测到长期习惯，需要中间过程

以后扩展自动成长时，Octos 可以形成并保留一个待验证的理解：

> 最近几次，学生在公式推导后主动要求看图。新概念先给图，可能更适合他。

后续怎样使用这种理解，需要确定具体教学规则。新的反馈和学习表现仍交给 Octos；是否缩小范围或撤销判断，由 Octos 的记忆处理完成。不要在 Octos Learn 或 Learning Coach 中另做一套偏好合并规则，也不要把几个弱信号直接当成学生的固定性格。

第一版先验证 Octos 的现有记忆如何用于明确偏好和真实经历。更复杂的自动教学策略评估放到后续阶段；这不意味着第一版关闭 Octos 原有自动记忆，或改由 Learning Coach 处理其中一部分。

## 5. 给老师一份可靠的学习记录，也给知识地图和成就一份共同依据

这部分属于第一版的基础。主动安排学习、周报月报、月考试卷等属于后续方向，先把它们所需的记录准备好，不在当前阶段直接开启定时任务。

### 学习记录与长期记忆各有用途

“学生喜欢先看图”需要 Octos 对交互作出判断；“这门课在哪几天学过、每次停在哪里”则是具体事实。次数、日期和学习进度由程序从记录计算，不能让模型凭印象回忆，也不能只依赖可能被压缩或归档的对话摘要。记录提交、查询和长期记忆处理统一接入 Octos；学习界面可以暂存离线事件、显示统计，不因此另建语义记忆处理流程。

可以这样分工：

- **学习记录保留发生过的事实。**哪门课、哪个版本、哪次学习、学到哪里、相关知识点、实际作答。
- **知识地图展示这些事实说明的进展。**接触过什么，哪些还在练习，哪些已经有相应的理解证据。
- **长期记忆由 Octos 处理。**这个学生在哪种解释中容易找到感觉，师生有什么约定。
- **老师每次读取相关部分。**问到斜率时读取斜率的学习摘要，不把整个学习生涯全部装进提示词。

当前项目已有保存在设备本地的播放位置和互动任务进度，可以作为接入起点。但能继续播放，不等于老师已经知道学过什么，更不等于已经实现跨设备的完整学习档案。

练习必须单独采集，不能靠课程片段进度代替。当前任务在课程之后开放，练习不属于某个正在播放的 step 或 beat。需要与片段记录并列保存任务开始、尝试、使用提示、结果等实际可取得的事件，再关联课程和知识点；现有本地任务进度尚无供老师跨课查询的统一导出。这项能力属于第二步的明确工作范围。

### 同一份学习事实，从课程和知识点两个角度查看

一门课可能讲多个知识点；同一个知识点也可能出现在不同课程、学生自己的提问和局部解释中。因此，需要支持两种查询视角。这不要求各自维护一套独立历史，应从同一份可靠记录计算，具体形式待验证。

| 视角 | 至少要知道什么 | 例子 |
|---|---|---|
| 这门课的经历 | 课程编号与版本、预制或实时生成、何时开始、实际学到哪里、是否到达结尾、是否重新学习 | 《斜率和截距》学到第二节，隔天继续 |
| 这个知识点的经历 | 相关课程与片段、学习发生的时间、问过什么、是第一次学习还是复习、是否有作答依据 | 斜率在两门课中讲过，学生另追问过三次 |

预制课和实时生成课都要进入记录。即使播放预制课时没有调用任何模型，也应该在合适的时机保存进展，让老师下次知道。

“上过”需要说清含义：打开、开始播放、实际接触某段内容、到达课程结尾、完成练习是不同事实。拖到最后一秒不能当成完整学习；同一段反复播放也不能直接当成多门课程。

以后展示次数时也要分别说清：这是几次独立学习、几次提问，还是同一段的回放。打开五次不能自动变成“学了五遍”。怎样算一次有意义的学习，需要在实现时定规则，并保留原记录以便调整。

### 老师面对反复提问时，怎样使用这些信息

反复接触一个知识点，可能是复习、好奇、课前预习，也可能确实卡住。老师应该知道重复发生过，但对原因保持判断空间。

例如，老师拿到的是：“最近两周接触斜率三次，前两次追问集中在变化量，尚无独立作答记录。”它可以先针对这个环节提一个简短问题，或者改用另一种解释，而不是机械地重播整门课。

如果学生明确要求再从头学，就尊重这个选择。历史用来帮助教学，不用来阻止学生复习。推荐的回应是“这次我们换个角度”，而不是“这个你已经学过了”。

计数属于知识点时，还要分清具体内容。“三角函数”是较大的范围，正弦定义、周期、象限符号不是同一个问题。不能把五个不同问题合并成“同一个知识点问了五遍”。

### 用 os-taxonomy 做知识地图，先解决课程与知识点的对应

[os-taxonomy 的说明](https://github.com/withmarbleapp/os-taxonomy)提供了知识点编号、知识点之间的前置关系，以及描述理解表现的材料。它适合成为地图的内容基础；每个学生学到哪里，则要由我们自己的学习记录保存。

课程库已有文档把部分预制课与 Marble 知识点对应起来，但当前 CoursePack 格式尚没有统一的、可供播放器直接使用的知识点映射。这部分需要正式补上，不能只按课程标题模糊匹配。

具体建议是：

1. **先给现有课程建立映射表。**一门课的哪些片段讲哪些知识点，是引入、重点讲解还是顺带复习，由课程制作时审核。
2. **课程版本与映射版本一起记录。**以后课程增加内容，不能让旧学生的进度无依据地变成新版本全部学完。已发布课程包不直接改写，可以先评估独立映射文件，或在新版本中正式扩展格式。
3. **实时课也逐步使用同一套知识点编号。**能确定时连接到已有节点；不确定时保留待确认，不编造编号。自动匹配优先在已有课程生成结果中完成或放到后台，避免增加前台模型往返。
4. **固定所用的 taxonomy 版本。**上游知识点改名、拆分、合并时，保存旧对应关系并提供迁移规则，不让地图更新悄悄改写历史。
5. **检查实际学科覆盖。**已有节点可以复用；未覆盖的中学或更高阶内容，采用经过审阅的本地扩展并记录来源，不强行套用近似的小学节点。

图中的前置关系可以帮助建议学习顺序，但缺少某个节点的学习记录，不代表学生一定不会，也不应因此强制锁住后续课程。原有课程库文档也把 taxonomy 作为教研参考，而不是未经审阅即可执行的教学规则。

### “点亮”要有明确含义，既有激励，也不误报掌握

建议让学生看到几种不同进展，而不是只有亮与不亮。

| 地图表现的含义 | 依据 | 老师可以怎样说 |
|---|---|---|
| 还没有学习记录 | 暂无相关记录 | “我们还没在这里留下足迹。” |
| 已探索 | 实际接触过相关教学内容 | “这个点你已经探索过。” |
| 正在练习 | 有练习或继续学习记录 | “这个点我们还在练。” |
| 已有理解证据 | 完成了对应、经过验证的任务，或其他规定证据 | “这类任务你已经做出来过。” |

前两种也可以有点亮和探索的视觉奖励。只要文案说清它表示探索，就不需要假装已经掌握。

一个滑块任务完成，只能支持这个任务检查到的能力；不能据此点亮整章“熟练掌握”。外部 taxonomy 的理解标准可以帮助设计任务，但不能代替我们的实际任务验证。

“建议复习”可以另加标记，而不是把过去点亮的足迹抹黑。长时间没用并不证明忘记，学生曾经的努力也仍然成立。

老师读取的应是与地图相同的进展数据。例如地图显示“已探索、尚无作答证据”，老师就不能说“你已经完全掌握”。提供给老师的摘要需要注明截至时间；旧的对话记忆不能覆盖更新后的学习统计。知识点还没确认对应到哪里时，先保留原始经历，不把猜测计入重复学习成就或当成出卷依据。

### 成就可以有趣，规则与老师的说法要分开

用户提出的幽默、带一点调侃的成就，是这部分的产品方向。例如反复学习三角函数，可以有一个“又双叒叕见面了”或“三角函数常驻嘉宾”的徽章。反复回到同一个问题，也可以成为师生之间有意思的故事。

系统应先按明确规则决定是否达到条件，再由老师以自己的风格颁发。这样同一件事实不会因为模型心情不同，今天发、明天不发，或者断网重试发两次。

| 触发事实示例 | 徽章草案 | 风趣老师的颁发语示例 |
|---|---|---|
| 同一范围内完成五次符合规则的学习 | 三角函数常驻嘉宾 | “第五次见面，三角函数都想给你留个专座了。” |
| 第一次独立完成规定的变化题 | 这回真会了 | “这次没接我的梯子，你自己爬上来了。” |
| 已学内容中主动提出一个新的延伸问题 | 课本外探险家 | “课本刚翻到这里，你已经去敲隔壁的门了。” |

这些都是例子，不是已经确定的阈值和名称。尤其“终于会了”必须有相应作答依据；学五遍可以获得坚持或回访成就，不能仅凭次数颁发掌握成就。

调侃可以围绕题目、重复见面的情境和老师自己的反应，让学生感到两人有默契；措辞要避免把努力翻译成“你笨”。调侃程度应可调，学生不喜欢时采用普通鼓励，不要求他接受老师的玩笑。

成就是这个学生的成果。系统记录为什么获得、何时获得、是哪位老师颁发，换老师不丢失，也不重复计数。老师可以提及已有成就，不能声称自己颁发了别的老师的徽章。

### 后续的主动学习、报告和试卷，共用这些基础

这些是用户提出的后续候选功能，需要分别设计，尚未承诺第一版交付。

| 后续功能 | 依赖什么 | 老师怎样参与 |
|---|---|---|
| 主动建议学习某个知识点 | 已学进展、反复提问的位置、学习目标、前置知识关系 | 解释为什么建议，并给学生选择；先不擅自替换正在上的课 |
| 周报或月报 | 对应时间段的实际学习、提问、练习和成就记录 | 用老师的风格总结进步，说明尚无证据的部分，并提出少量可执行建议 |
| 月度练习或试卷 | 已学知识范围、题目难度、正确答案、判分依据 | 组织适合这个学生的复习；若含诊断新内容，要明确标明 |

报告中的次数、时间和完成情况由程序统计，模型负责组织说明，不能凭历史印象编数字。没有作答数据时，可以提供学习活动报告，但不虚构成绩或掌握率。每份报告保存所统计的时间范围和当时的数据版本，后续补传的离线记录可以说明补充或修订。

试卷需要独立检查题目、答案和判分规则；生成一份格式正确的文档，不代表题目都正确。它不能仅靠老师的人格提示或 OLL 文件校验来保证质量。

何时生成、是否通知、是否自动安排学习、使用哪个时区和费用预算，都需要由学生明确设置；这些产品功能以后再接入，不在本次文档更新中创建任何实际提醒或任务。

## 6. 一次课堂怎样进入 Octos 记忆，再用于下一堂课

**只保留一套记忆处理流程：Octos 接收记录，判断哪些信息值得长期留下，负责更新、合并、检索和遗忘。**Octos Learn 负责接入和界面，Learning Coach 负责使用记忆进行教学。

本节描述计划中的完整流程，其中有些接口已存在，有些接入还需要开发。它不是对当前产品能力的声明。

### 第一步：课堂照常进行，把真实记录交给 Octos

学生在 Octos Learn 提问，Learning Coach 按现有方式生成课程。Octos Learn 把学生原话、实际交付的回答和课程文件的对应关系写入 Octos。

现有 session/append_message 接口能在不启动 agent、不调用模型的情况下写入会话历史。主要直调技能的路径需要补上这一步；部分图片和白板引用路径已通过普通 turn 自动记录，不能再重复写。turn 是 Octos agent 接收请求并执行一次工作的过程。

“写入本身不调用模型”不代表写进去的内容不会影响后续记忆。当前提炼器不按 Message.source 排除外部记录，并按消息角色判断证据：user 角色会被认作 user_said。学生原话可以如实记录为 user；程序观察到的“播放到第二节”等事件不能为了方便就伪装成学生亲口陈述，也不能随意改用 assistant 冒充老师回应。事件存储与证据表达要在第一步定稿，必要的通用能力在 Octos 内补齐；source 文本本身不提供可信的来源权限。

预制课即使离线播放，也先在设备记录实际进展，联网后交给 Octos。开始、继续、学到某个片段、完成任务等是软件能够观察的事实，采集这些事件不需要大模型。“学过几次”的明确计数规则仍需定稿，数字由程序从记录统计，不能让模型凭印象编。

Octos Learn 还应提供当前学生、当前老师和消息来源等必要课堂信息，让 Octos 有判断依据。它只提供事实，不自行把一句话解释成长期偏好。

课程文件和播放状态仍按既有机制保存；写入问答历史不等于自动恢复了完整白板。学习事件用哪个 Octos 接口保存、怎样与会话和课程关联，需要在第一步验证。

### 第二步：由 Octos 的记忆流程决定长期留下什么

记录进入 Octos 后，复用它已有的记忆提炼流程：后台扫描符合条件的会话，调用模型提出有价值的信息，再由 Octos 的程序检查来源和允许的操作，合并进长期记忆。

这一步才是在判断“学生长期喜欢什么”“某次互动值得以后记住吗”。不在 Octos Learn 中另写一套语义判断器，也不让 Learning Coach 额外返回记忆更新建议。

Octos 现有普通 profile 流程默认等会话至少空闲 30 分钟，扫描本身也默认每 30 分钟一次，每轮最多提取 2 个会话、每天最多 20 次提取调用；还有逐会话失败计数和服务级指数退避。30 分钟是取得资格的条件，不是完成时间保证。有积压、预算限制或故障时可能明显更久，具体行为还要核验实际配置。已有 host/user_request 暂存笔记另有快速整合通道，但 append_message 不会自动把原话转换成这种笔记。因此：

- 保存原话成功，只代表原话已经进入历史。
- 原话进入历史，不代表已经提炼为长期偏好。
- 生成课程成功，也不代表学生已经上过这门课。
- 只有得到 Octos 对相应操作的成功结果，界面才能作出对应的保存或更新说明。

如果希望学生说“以后先给我看图”后，下一堂课很快就采用这条长期偏好，需要另外确定生效时间，并验证 Octos 是否需要支持更及时的处理入口。这仍然在 Octos 内解决，不能因为现有后台有延迟，就在 Learning Coach 中建立第二条记忆处理路径。

学生只提出记忆要求、没有新学习问题时，怎样交给 Octos 处理并回应，也是待验证的接入问题，不为了回应它强行生成一门课。

### 第三步：下一次上课，向 Octos 读取相关记忆

准备下一次课程时，Octos Learn 根据当前学生、当前老师和问题，向 Octos 请求相关信息。这里哪些信息可以共享、按什么老师范围查询，按第 3 节后续确定的规则实现。

Octos 返回的相关记忆，加上老师基础设定和当前问题，一起传给 Learning Coach。Learning Coach 用它们决定怎样讲这堂课，不再决定这些内容怎样进入长期记忆。

Learning Coach 已有 tutor_context 和 learner_context 两个参数，可以分别承接教学设定和学生背景。不同课程入口对参数的支持还不一致，需要统一；这些参数自身不会自动读取 Octos。

目前三个直调入口的具体缺口已确认：普通文字/语音课程 action 只允许 learner_context；摄像头和选区课程 action 两个都不允许，且会拒绝额外字段。还需要在相关系统提示中说明这些参数的用途、老师设定怎样影响当前教学，以及它们不能覆盖数学规则和学生本次要求。现有代码把上下文放进模型输入，并不等于已经实现稳定人格。入口与提示说明是第三步的前置工作，不能等到体验验证才发现字段传不进去。

计划中的课程输入可以理解为：

    老师的基础风格
    ＋ Octos 提供的相关学生记忆和学习背景
    ＋ 当前问题及当次要求
    → Learning Coach 生成课程

本次学生说“先画图”，Learning Coach 可以直接依据原话安排本次课程，这是正常教学。判断这句话是否应长期保存、以后对谁生效，则交给 Octos，不能把当前教学理解顺手变成另一套记忆更新机制。

### 哪些步骤调用模型，由谁触发

| 步骤 | 由谁负责或触发 | 是否需要模型 |
|---|---|---|
| 记录原话、回答和实际学习事件 | Octos Learn 采集，调用 Octos 接口 | 写入本身不需要 |
| 从历史中提炼、合并长期记忆 | Octos 已有记忆流程 | 会调用配置的模型 |
| 读取或搜索相关记忆 | Octos Learn 请求，Octos 执行 | 直接读取不需要；语义搜索可能使用嵌入模型 |
| 根据当前问题和相关记忆生成课程 | Learning Coach，在用户请求课程时执行 | 使用现有课程生成模型调用 |
| 判断长期偏好、更新或遗忘记忆 | Octos | 按具体操作使用 Octos 的模型和程序能力，不交给 Learning Coach |

Learning Coach 不启动定时记忆任务，也不增加专门提炼记忆的模型步骤。Octos 已有后台记忆服务会按配置运行；以后若增加周报、月报或试卷，再单独确定它们的运行方式，不与记忆服务混为一谈。

现有 Learning Coach 指令需要先对齐这一原则。仓库与本机安装副本的 SKILL.md 仍有跨会话记忆提升指令，references/session-state.md 也描述 Learning Profile 的归纳和更新。它们可能影响普通 agent 路径；直接运行技能入口并不等于每次都执行这些自然语言指令。第一步必须区分必要的当次课程状态与跨课画像，改写后者的指令并核对安装副本，避免旧提示继续要求 agent 代做长期记忆处理。不要把课程播放或任务状态文件一并误删。

“课程前台不增加模型往返”不等于“后台记忆免费”，也不等于“语义搜索没有成本”。这些调用分别记录和评估，继续使用本人配置与预算。

### 为什么还需要 Octos Learn 的代码

现成的 Octos 记忆能力不会自动知道白板上发生了什么，也不会自动出现在 Learning Coach 的输入里。因此 Octos Learn 需要把两端接起来：

- 采集真实课堂信息，可靠地提交给 Octos。
- 从 Octos 读取结果，并提供查看、纠正和遗忘的界面。
- 将 Octos 返回的相关内容传给 Learning Coach，不另外维护独立的偏好或人格判断。
- 展示由学习记录支持的地图和成就，让它们与老师看到的信息一致。

Octos 记忆能力缺少老师相关的表达或处理方式时，先说明需求，再在 Octos 内补齐。当前接口没有的能力不写成已经具备，也不绕过接口直接修改内部记忆文件。

### 各仓库在这里承担什么

| 仓库 | 职责 |
|---|---|
| octos | 统一处理记忆：接收记录、提炼、更新、合并、检索、纠正和遗忘，并执行相应身份与范围规则 |
| octos-learn | 学习界面、老师基础设定、课堂事实采集、调用 Octos、向课程传入相关结果，以及地图和成就展示 |
| learning-coach | 使用当前问题、老师设定及 Octos 提供的相关信息生成课程；不新增记忆处理流程 |
| octos-course-library | 预制课程、知识点映射、内容版本和来源说明 |
| octos-lesson-language（OLL） | 数学内容中可校验的语义、确定性课程结构与播放行为 |

## 7. 需要提前解决的几个实际问题

### 断网重试，不能让老师以为学生问了两遍

学生发出问题后，网络断了。重新连接时，网页不知道刚才的记录是否已保存，可能会重发。每个问题和回答都需要稳定编号，重试仍用同一个编号。

Octos 接口已经支持一定范围内的重复检查，但只检查它加载的那部分历史。Octos Learn 还需要记录交付进度，处理很久以前的重试。回答必须明确对应原问题；两道题同时完成时，不能仅靠“最近一个问题”猜归属。

### 手机上改过的偏好，不能被电视上的旧记录覆盖

同一个学生可能在手机和电视上使用。手机把偏好改成“直接推导”，电视还留着旧的“先看图”。如果电视晚一点保存，就可能把旧内容写回。

因此，Octos 要能够识别旧设备基于旧版本发来的操作，不能无条件接受覆盖。当前 Recall 记录的 schema_version 是格式版本，fingerprint 用于变化识别，都不是“基于第几版才能更新”的条件；现有相关记忆接口未提供这种条件更新能力。这是已确认的接口缺口，但不能据此声称当前已经发生电视覆盖手机偏好的故障：正式更新路径尚未接入，Octos 后台也有单进程持锁等保护。第一步应选择条件更新或追加操作等合适方案，不预先限定某一种实现；全部仍在 Octos 内处理。

### 学生删掉的记忆，不能过一会儿又出现

学生删除“以后先看图”时，可能恰好有一个后台任务正在处理旧对话。这个任务稍后完成，如果不检查删除状态，就会把偏好重新加回来。

用户已将这类少数时序情况降为可选处理：先检查现有顺序能否简单避免；需要较大改造时允许暂不处理，并说明实际限制。不能为此阻塞基本的记忆请求和遗忘接口接入。

记忆删除由 Octos 统一执行，检查当前记录、搜索用的摘要以及尚未完成的更新任务；Octos Learn 根据结果清理显示缓存，不只在界面上藏起一条记忆。重置某位老师时，清除哪些内容仍需后续确定：相处习惯、原始对话和学习进展不能含糊地混在一个“全部忘记”按钮里。

调查所用 main 没有网页可调用的 memory 遗忘入口；现已在 Octos 候选提供 memory/request，由应用提交本人选中条目的遗忘要求，再由已有整合流程处理，尚待上游审查。按 ID 硬删除已有匹配内容清理，并非只有 sensitive 模式才清理；但它不等于任意同义信息或稍后完成的任务都不能重新加入。候选的首次回执只表示已接收；单次处理结果查询留待以后增加。需继续列清“何时不再用于回答”和“何时完成各类清理”；第四步交付管理界面前必须验证完成，不把提交请求成功误报为删除完成。

重置某位老师的相处记忆，也不应默认清空学生上过的课、知识地图和成就。删除学习记录时，则要说明是否会重算相关地图、统计和成就，避免它们继续引用已经不存在的依据。

### 电视离线学过的课，联网后不能算成两遍

APK 预制课可能离线使用。设备要先保存带稳定编号的学习记录，联网后补交；重试提交仍是同一次学习。学生继续上次课程、重新从头学习和重复播放一段，要有不同含义。

未登录时的学习不自动归给以后第一个登录的人。是否接收这些记录，以及归到哪个学生，需明确处理。旧版本只保存了播放位置而没有完整过程时，只迁移能证实的事实，不能反推不存在的学习次数。

学习记录格式升级需要迁移或保留旧数据，不能套用过去开发缓存升级时经单独授权的清库做法。现有 LearnTraceRecorder 是关闭页面即丢的诊断时间线，不能直接当作持久学习记录；可以参考其去重思路。老师选择目前使用不区分账号的本地 skin 键，也不能直接复制来保存每位学生选定的老师。

### 换老师后，声音和正在生成的课不能混乱

阿澜的课程生成到一半，学生切换到豆豆，已经提交的课程仍应归阿澜。下一次请求再使用豆豆。否则同一门课可能前半段是一位老师，后半段变成另一位。

音频保存时也要区分音色。即使两位老师说了同一句话，也不能因为复用了旧音频，让豆豆发出阿澜的声音。老师的单次音色选择还应复用学生自己的 TTS 凭据，避免每次换老师就改写账号的全局语音配置。

已找到实时旁白的短期预取缓存：键由旁白编号和文字组成，不含音色；现有全局 TTS 配置变化会清理预取。它还不能证明未来按老师切换时必然串音，但新增单次老师音色选择必须覆盖缓存键、失效时机和网页/原生链路，不能假定原有全局配置事件会自动处理。

### 记忆没有加载出来，课程仍然要能开始

老师的基本设定和 Octos 已提供的相关记忆，应尽量在进入课堂时提前准备。相关旧经历通过 Octos 按需查找，不能为了搜索一段回忆，让学生迟迟听不到第一段课。显示层的临时缓存不能成为另一份独立更新的记忆。

如果额外记忆没读到，使用基本设定和已经可靠取得的信息；不要编造回忆，也不要声称拥有本次未读到的信息。具体等待多久、怎样提示，需要在接口验证后确定。

前台课程生成不增加一轮专门的“人格思考”模型调用。语义记忆的后台抽取和更新只在 Octos 中执行，仍可能花费学生自己的额度，需要与前台成本分别说明。今后新增教学效果评估时，另行明确用途与实现，不作为第二个记忆处理器。

## 8. 按什么顺序开发，每一步交付什么

建议第一版先做两位风格明显不同的老师，复用现有可用外观和音色。具体名字、造型、声音与性格范例先出草案，再确定；不把素材制作与记忆接入一次铺得太大。

| 阶段 | 要解决的问题 | 完成后能看到什么 |
|---|---|---|
| 第一步：确认现有能力与后续设计问题 | 验证 Octos 的记录、提炼和读取链路，以及现有课程怎样对应知识点；列明老师范围和生效时机的待定事项 | 一条具体请求和一节预制课从学习到 Octos、再到课程输入的完整说明；缺少的能力有明确清单 |
| 第二步：补上学习历史和进展 | 直调问答、预制课播放、实时课和重复提问怎样记录，断网怎样恢复 | 能查到上过什么、学到哪里、相关知识点问过几次；计数有依据，重试不重复 |
| 第三步：做出性格稳定的老师 | 为候选老师制作基础设定卡和情境范例，接通课程表达、固定反应、动作与音色 | 同一情境中的行为可辨识，数学仍正确；先验证建议的两位老师，具体名单待定 |
| 第四步：接入 Octos 记忆供老师使用 | 根据后续确定的范围规则，读取 Octos 的偏好、经历和相关进展 | 课程能使用真实背景；查看、纠正和遗忘经 Octos 执行，不增加独立记忆处理流程 |
| 第五步：知识地图与首批成就 | 把同一份学习记录转成可见进展，并让老师知道 | 小范围知识地图、规则明确的少量徽章；老师的说法与实际状态一致 |
| 第六步：主动建议、报告和试卷 | 在记录可靠后增加可选择的阶段服务 | 先明确具体场景和启用方式，再逐项实现，不一次上线全部功能 |
| 后续持续改进 | 怎样从更多教学反馈中形成可信判断 | 根据实际效果增加作答、策略评估和更多老师 |

第一步不需要先建设一个庞大的人格系统或全学科地图。先验证已有 Octos 能力，列出缺口；老师间如何共享、生效时机和具体表达方式，留待后续确定，不在接口接线时擅自固定。知识点映射先从经过审阅的一小组现有课程开始。

### 第一阶段已经知道要处理什么

以下项目已由源码核对，不能再只写成泛泛的“看看接口能不能用”。第一阶段交付清楚的处理方案、验证结果和最小扩展范围，不等于立刻一次实现全部能力。

| 已知事项 | 第一阶段应产出什么 |
|---|---|
| 外部历史记录会按角色进入记忆提炼 | 学生原话与程序事件的可信来源和角色方案，验证不会把程序观察伪装成 user_said；不预先决定程序证据一定高于或低于用户陈述 |
| 网页缺少正式遗忘接口 | Octos 接口与状态需求，列明匹配副本、迟到任务和不同措辞重现的处理边界 |
| 现存技能提示仍要求处理跨课记忆 | SKILL.md 与 session-state.md 的改写范围，保留当次状态而取消独立跨课归纳职责，并核对安装态 |
| 现有相关记忆接口没有条件更新版本 | 选定能防止旧操作覆盖新结果的 Octos 方案；不把格式版本或指纹当作并发保护 |
| 教学上下文的入口与提示说明不完整 | 三个直调 action 的字段改动清单，以及各生成阶段如何使用设定的明确说明 |
| 精确学习事实存储尚未选定 | 按下表比较候选能力；不先在错误的接口上建一套临时历史再迁移 |

比较 append_message、memory/ingest、现有认证文件或其他通用记录能力时，至少检查：能否按知识点与时间准确查询、能否稳定去重计数、怎样处理版本与旧操作、怎样与删除联动。写进去并能搜索到，不代表足以作为统计真源。namespace 是隔离能力，也不能单独解决查询和计数。如果现有能力确实不足，在 Octos 设计最小的通用记录扩展，不在 Learning Coach 或前端补一套记忆服务。

第一阶段已发现 Recall 会按容量策略清理冷记录，不适合作为永久学习账本。后续职责复核确认，Octos 现有架构允许业务应用持有原始记录，不能据此推出必须在 Octos 新增永久事实库。原始记录的存放方式仍需设计；记忆提炼和处理继续统一由 Octos 执行。已有 ingest 及带来源的晋升机制也需优先评估，具体结论见[Octos 缺口复核](personalized-teachers-phase1/OCTOS_GAP_REASSESSMENT.md)。

### 相关阶段开始前，需要完成的决定

- 第二步前：确定事实记录的存储和事件形式，练习任务事件与播放片段事件并列设计，知识点映射满足所选的小范围课程。
- 第三步前：明确预制课与实时课的声音策略。预制课播放包内预录音频，其音色不随老师或学生 BYOK 选择变化；实时课当前使用用户配置的单一音色。可选择明确标注课程原声、制作多音色版本或另行合成，但一致性、离线、延迟与费用各不同，本方案尚未替用户选择。
- 第四步前：确定老师范围、记忆生效时机与遗忘语义，并完成相应 Octos 能力；用户可见的删除界面不能只有本地隐藏效果。
- 第五步前：完成地图和成就所需的映射、事件统计与解释规则。不能等到此时才给第二步的学习记录补上基本知识点对应。

第二步要保存有教学内容的记录，例如实际交付的解释、旁白及课程文件位置。只写一句“课程生成成功”无法支持有意义的记忆；把整份 OLL 文件全部复制进消息又会增加噪声。具体记录格式应保留足够内容并控制体积。

第三步的具体交付包括基础设定卡、同一组情境下的回应范例、程序触发的反馈清单和各端可用的表达配置，另附性格一致性验证结果。先验证新生成的课程；预制课的旁白和音频已经固定，切换头像并不会改写它们。预制课是否增加老师专属开场、补充解释和课后交流，需要另行设计，不能在第一版中宣称整门课已经个性化。

第四步使用 Octos 已提供的相关记忆和能证实的学习记录，不在课程生成器里推断或更新长期偏好。即使地图界面还没完成，老师也应先知道学过哪些课，以及哪些知识点反复接触过。需要老师范围支持的部分，等相应规则确定后再实施。

## 9. 怎样证明做成了

验收要覆盖几次连续使用，不能只展示一句符合风格的旁白。建议用一套固定场景逐项检查：

| 场景 | 应当出现的结果 |
|---|---|
| 学生说“以后新概念先给我看图”，Octos 完成相应记忆处理后重新上课 | 能读到并采用有效记忆；不能把仅写入历史的成功误报成长久偏好已生效 |
| 学生只说“今天慢一点” | 当前后续教学适应，以后不被永久固定成慢讲 |
| 学生一直安静看课 | 老师正常教学，不虚构喜欢程度或掌握情况 |
| 阿澜与学生用过电梯比喻，下次讲相关内容 | 阿澜能恰当地联系这段经历，且能找到实际记录 |
| 学生换成豆豆 | 豆豆保留自己的风格，不冒称参与阿澜的经历 |
| 切换到另一个账号 | 看不到前一学生的偏好和师生经历 |
| 断网、刷新、两道题先后顺序颠倒 | 问答不重复、不配错，课程仍能按原机制恢复 |
| 删除偏好时恰有后台更新 | 补充检查这一情况；容易修复就处理，成本较高时可暂不覆盖，并保留其他有效资料 |
| 用不同风格讲同一道题及不同数学主题 | 风格可辨识，数学与互动仍通过既有验证 |
| 离线播放预制课，联网后重复提交进度 | 老师能读到实际进展，同一次学习不计成多次 |
| 两门课都涉及斜率，学生又在白板中追问 | 知识点记录汇总到正确节点，区分课程学习、提问和回放 |
| 课程同时讲斜率与截距，但学生只学到斜率 | 不能把尚未接触的截距也标成已探索 |
| 看完课程，没有独立作答 | 地图与老师都只表达相应学习经历，不虚构掌握 |
| 同一成就触发后刷新、断网重连、换老师 | 只获得一次，颁发来源和条件可查 |
| taxonomy 或课程版本更新 | 既有学习依据保留，新增知识点不会自动获得旧进度 |
| 程序提交“播放到第二节”等课堂事件，之后进入提炼 | 不被标成学生亲口陈述，不产生无依据的掌握或偏好结论 |
| 同一位老师先播放预制课，再生成实时课，期间切换老师 | 声音和说明符合已选择的产品策略，未选策略前不能宣称全程音色一致 |
| 学生在课程结束后完成任务 | 任务事件可独立查询并关联知识点，不因没有正在播放的 beat 而丢失 |
| 删除后出现匹配暂存内容、同义表述或迟到提炼结果 | 分别验证已声明的遗忘边界，不将仅清理当前文件当成完整保证 |

老师性格还需要一套共同情境，不能只挑最符合预期的一句话展示。用相同输入检查：学生答错、质疑老师、完成挑战、要求直接讲、没有回应、反复提问，以及老师自己的解释确实出错。检查老师是否保持各自的关注点和回应方式，同时尊重学生要求、认真纠错。

人工评价可以遮住名字和头像，只看几段回应，记录能否辨认老师，以及辨认依据。固定台词、动作和语音也要一起验收：任务只触发一次庆祝，重复事件不刷反馈，Android 表现可用，字幕与声音一致。文字像某位老师，但动作和语音表现出另一种性格，也不能算完成。

基础性格验证与长期记忆验证分开记录。性格表现的新增生成内容、动作和语音同样纳入下述速度检查；没有新增模型调用，也不能直接声称没有性能影响。

速度也是完成条件。首个可播放片段的生成速度不能回退，前台不增加模型往返。验证时交替运行原版本与新版本，比较一组请求的中位时间；这就是项目约定的“p50 对照交错基线”。检索耗时、增加的提示内容和音频生成都要计入，不能只凭“没有新增模型调用”判断足够快。

同时记录逻辑模型调用和实际供应商请求数。Learning Coach 现有模型路由包含延迟 hedge/fallback，默认 hedge 延迟为 12 秒；一次逻辑生成可能发出多个供应商请求。性能对比保持路由配置一致，分别说明时间和请求成本，不能用“零新增往返”掩盖实际请求数变化。

人工体验还要看三件事：学生是否愿意继续使用、是否理解得更好、是否越来越能独立完成。观看时长和互动次数可以辅助观察，但不足以单独证明老师教得好。

工程验证根据改动选择现有测试，并补必要的断线、混用、删除和并发回归。人工验收沿用 [本地开发交接](DEVELOPMENT_HANDOFF.md) 中的正常环境：HTTPS 5173、后端 50080、本机现有账号与正式安装的 Learning Coach。

## 10. 开发时查阅：已经确认的接口事实与尚待验证的部分

下面保留实现依据，便于开发核查。前面的产品设计不要求读者先理解这些接口名。

2026-10-20 同步 main 后的本机源码版本：octos-learn 4973499，Octos ed92309a，Learning Coach 4287729，OLL 15ee009，课程库 0781f74。此前审查的 octos-learn f89116a 与更早的 d875d51 为历史调查版本。第一阶段本机接口检查使用 Octos 2.0.3+ed92309a；其他运行和公网版本不能由源码版本推定。

| 已确认的事实 | 对实现的实际影响 |
|---|---|
| RFC #2355 已由 PR #2730 合并，提供 session/append_message | 可以保存消息而不触发 agent；保存后不会立即变成长期事实或经历摘要 |
| append_message 只在已加载的历史中检查重复 | Octos Learn 需要记录交付进度来补足长期重试；回答要明确携带原问题的 thread_id |
| 提炼输入不按 Message.source 排除外部消息，证据由消息角色决定 | 写入角色会影响后续记忆权威；程序事件不能随意套 user 或 assistant 角色 |
| 现有 WS 记忆方法没有遗忘接口，CLI forget 是请求笔记加整合流程 | 需要在 Octos 补应用可调用的遗忘能力，状态和清理范围单独定义 |
| Recall 的格式版本和 fingerprint 不是条件更新版本 | 不能宣称已经支持旧设备写入保护；实现方式待选，不把文件原子替换等同于跨设备语义冲突解决 |
| 通用记忆接口按认证 profile 选存储 | 查询时加一个老师来源标签，不能代替服务端检查归属 |
| Octos 有 memory_namespace 独立存储，但其中的自动提炼当前关闭 | 不能只给每位老师建一个 namespace，就期待它自动成长 |
| 自动提炼按消息角色判断证据，当前不完整理解 Octos Learn 的老师关系 | 不能假定 source 标签会自动成为可信的老师身份和分享规则 |
| memory/ingest 能提交外部检索记录，但不能直接写 Knowledge | 适合提交学习事件摘要；它不是任意修改长期老师设定的接口 |
| Recall 默认每来源上限 20,000 条，age 会实际删除超额冷记录 | 搜索库不能直接作为永久学习账本，精确事实需要另外的 Octos 保留契约 |
| bank 页面会同步到搜索索引，MEMORY.md 有另外的读取路径 | 核心偏好读取和相关经历搜索要分别验证，不假定一次 search 能找到全部记忆 |
| 普通课程 action 只收 learner_context，摄像头/选区 action 都不收这两个上下文字段；相关系统提示未明确定义它们的角色 | 统一三个入口并补充提示语义，是稳定性格实现的前置工作 |
| Learning Coach 仓库和本机安装副本仍有跨会话记忆提升指令 | 普通 agent 路径需对齐“记忆只由 Octos 处理”；不能据此认定每次技能直调都执行该指令 |
| 当前外观是本地 skin 选择，TTS 使用用户配置的音色 | 需要新增统一老师身份，以及按老师选择的语音调用方式 |
| 当前设备本地保存播放位置、学生操作和任务进度 | 可以接入学习事实，但还需跨课汇总、身份归属和老师读取能力 |
| 当前任务在课后开放，本地任务进度没有统一跨课导出 | 任务事件必须与片段事件并列采集，不能仅靠播放游标统计练习 |
| 预制课消费包内音频，实时课当前从用户 TTS 配置取音色 | 老师跨两类课程的声音不会自动一致，第三步前需确定策略 |
| CoursePack v1 有课程编号和版本，尚无统一的知识点对应字段 | 课程库需增加经审阅的映射，并与播放器和生成器约定使用方式 |

性格表现的现有代码起点还包括：src/learning/octos-teacher.tsx 中的状态、字幕与点击反应，src/hooks/use-teacher-skin.ts 中的外观和动作映射，以及 src/learning/learning-workspace.tsx 中的课堂状态文案。这些能力可复用，但目前还不是上文完整的老师设定与行为系统。新增配置不承担学生记忆提炼、合并或更新职责。

表中现有接口不意味着已经支持老师身份、经历参与者和适用范围等完整语义。需要按第 3 节后续确定的规则验证 Octos，不能只把老师名称写进普通正文，就宣称已经解决归属与共享。

os-taxonomy 此前调查的 main 为 e2b99bab045fb3a4f58004129ebea5b5943a0518；第一阶段已核对更新后的 533bab591b24c4024f0d70f9296aa4ee560fdd01，并固定该版本制作映射草案。它提供地图所需的知识点和关系，不提供 Octos Learn 学生的学习状态。课程库已有 docs/FIRST_COURSE_COLLECTIONS.md 记录部分来源知识点，并明确要求教研审阅；第一阶段的课程片段映射也仍需教研审阅，尚未发布。

本地依据还包括 src/learning/learning-document-store.ts、src/learning/oll/oll-playback-storage.ts、src/learning/learning-session-store.ts，以及课程库 packages/course-pack/src/types.ts。地图发布时沿用课程库既有的来源说明与许可处理，不在此文档中重新判断许可范围。

记忆统一由 Octos 处理是已确定原则。老师分享规则、参与者与适用范围的表达、反馈多久生效、跨设备操作及读取超时后的行为，属于后续待定事项；第一步先做能力核验和缺口清单。若现有 Octos 做不到必要能力，在 Octos 内设计扩展，不在 Octos Learn 或 Learning Coach 建设替代记忆流程。
