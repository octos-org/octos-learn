## 真人反馈与本次修正

初版真人试用反馈：缺少手部识别可视化；移动时会误判捏合；有时真实捏合未被识别；松开手指的离开方向被画入笔迹。

代码检查确认了以下原因或可疑因素：

- 初版只比较二维拇指尖/食指尖距离，忽略深度，且没有修正图像宽高分别归一化的差异。
- 初版要求食指保持伸展，可能拒绝实际捏合时自然弯曲的食指。
- 松开需连续两帧确认，在等待时仍提交移动；抬笔又使用当前食指位置，直接把松手位置加入笔画。
- 初版把 `handedness.score` 当作跟踪置信度，但它实际衡量左右手分类。当前通过 MediaPipe 自身的检测、存在与跟踪阈值控制，返回的左右手分数不再作为笔迹有效性条件。

参考：[MediaPipe Hand Landmarker Web 文档](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js)。模型给出的是关键点和左右手分类，本小样的落笔/抬笔判定由本地几何和状态机实现，不使用另一个预训练 Gesture Recognizer 分类模型。

### 实时骨架

摄像头画面叠加 21 个关节点和连接线，类似用户提供的参考图：

- 白线：骨架；红点：关节。
- 食指尖绿色：抬笔；橙色：落笔。
- 虚线框：摄像头书写安全区。
- 骨架与视频使用一致的 `object-fit: cover` 裁切及一次镜像，兼容实际摄像头宽高比例；容器变化后重绘。
- 手部丢失时清除旧关节；停止摄像头、识别异常时清空骨架并结束当前笔画。
- 模拟轨迹也展示骨架，但明确标为“模拟骨架 · 非摄像头识别结果”。
- 面板显示抬笔、落笔、确认中、等待先抬笔及越界状态；捏合模式额外显示归一化捏合距离。

### 当前默认：松握拳书写 / 张掌移动

2026-11-04 用户反馈上一轮 `fist` 模式存在三个问题：食指略弯就误断笔；真正收拳时前几帧仍画出尾线；握拳悬停和伸指落笔的位置不同。用户确认试用新候选 **张掌找位置、松松合手书写、再张掌停止**（`grip`），它已设为当前默认。

操作：

1. 张开手掌并保持片刻，使页面进入“抬笔 · 可以移动”，移动白板光标到起笔位置。
2. 四指自然弯回、拇指轻搭外侧，不要求用力握拳或捏合指尖。合手确认期间保持所瞄准的白板位置。
3. 等“落笔 · 正在绘制”后，移动整只手画线。单根手指稍微松动不触发抬笔。
4. 张开手掌停止，随后移动到下一处。手部丢失、越界或识别中断后需先张掌准备，不能闭手入镜就续画。

这是掌部带动虚拟笔尖的交互，与直接用食指尖描线的感觉不同，实际自然度和书写精度需要真人验收。

### 新模式的定位与过渡处理

- 悬停和书写都用同一掌部参考：手腕点占 0.5，四个指根关节各占 0.125，不用指尖定位。骨架上以掌部圆点提示该参考；实际落笔位置看白板光标。
- 使用连续相对位移跟随掌部，开合手过渡期间锁定光标并重建内部参考。起笔沿用屏幕上已显示的位置，不重新跳到收拢后的原始坐标。
- 起笔需稳定合手至少 3 帧、至少 90 ms；用四指总体弯曲程度识别自然合手，拇指不参与。
- 起笔后保持书写状态，单根手指略松或弯曲不立即结束。明确张掌至少 2 帧、持续 50 ms 才确认抬笔；约 30 FPS 时通常需 3 帧。
- 笔迹保留 100 ms 的未提交窗口，光标正常书写时仍跟随当前掌部。该窗口带来可见的笔迹跟随延迟。
- 通过未饱和的关节角度趋势查找开手起点，而不是每次抬笔一律删除最后 100 ms。确认张掌后丢弃属于过渡的未提交段，已有合法书写点保留。
- 暂时疑似开手时冻结显示、暂存轨迹；恢复握姿则将暂存轨迹并回同一笔画，不重建笔画。手形长时间不能明确（超过 450 ms）时安全结束。
- 手部丢失时丢弃尚未确认的尾部，避免跨丢失连接；主动“停止摄像头”时提交正常书写的剩余缓冲，但不提交未解决的开手动作。

上述机制可以验证程序在给定输入下的行为，不能保证所有真人过渡都能识别到真实意图的精确起点。掌部关键点也是模型估计，会受视角、遮挡、手部旋转影响。

### 保留的三种旧模式

- `fist`：伸食指（可带中指）书写、收拳抬笔；存在用户已报告的自然弯曲误断笔和形变位移问题，保留作对比。
- `point`：单指书写、双指移动。
- `pinch`：拇指与食指捏合落笔；三维距离阈值为 0.28 / 0.42，过渡区不追加移动。

旧模式继续使用原有指尖映射与状态机，新默认 `grip` 有独立掌部控制器与缓冲。模式选择在摄像头、模拟播放和清空运行期间锁定。所有模式使用现有 PointerEvent / Ink Runtime、撤销重做与保存链路。

## 数据与渲染链路

```text
getUserMedia（仅视频）
  → 30 FPS 调度 ImageBitmap
  → 本地 Worker / MediaPipe Hand Landmarker
  → 图像关键点 + 三维关键点
  → 手势状态机 + 坐标平滑 + 安全区映射
  → 合成 PointerEvent
  → 现有 InfiniteBoardView / Ink Runtime
  → 笔画、撤销、重做、IndexedDB 自动保存
```

摄像头帧不上传；模型和 WASM 使用项目自托管资源。当前只追踪一只手，不提供多人或多手仲裁。摄像头书写时为 draw 模式，停止后恢复 navigate；白板的 pan/zoom 转换仍由现有 Ink Runtime 处理。

界面中“模型处理”是 Worker 推理耗时，“端到端”是抓帧到主线程收到结果的耗时，不包含手势等待、显示延迟和持久化的全部时间。

## 文件边界

`src/learning/handwriting/`：

- `handwriting-capture.ts`：摄像头生命周期、采样、Worker 调度和延迟统计。

- `simulated-trajectory.ts`：四种模式的确定性模拟帧。
- `handwriting.test.ts` / `handwriting-grip.test.ts`：旧模式回归，以及新模式的定位、握姿容忍、过渡回看、误判恢复和缓冲处理。

## 后续验收

本轮自动验证和模拟摄像头验证不等于真人验收。请在 5175 页面先试默认的松握拳/张掌模式，并按需要对比旧模式：悬停移动、反复起停、短线/圆/箭头，以及慢速切换手形。观察骨架中指尖是否跳动、当前手形提示是否与动作相符、起笔等待能否接受，以及缓慢收拳是否仍有尾巴。新模式重点验证：张掌对准目标后合手是否原地落笔、自然握姿能否稳定保持、缓慢张掌是否拖尾、100 ms 跟随延迟能否接受，以及长时间使用是否疲劳。儿童手、弱光、侧向视角、长时间使用和 Android WebView 尚未通过实际验收。
