# 白板播放成本拆分：真机测量请求（2026-10-08）

背景：[四比例实测](ANDROID_RESOLUTION_COMPARISON_2026-10-08.md) 中，约 1440p（0.667）播放 gap 50.9ms、wait 26.6ms，应用 event 约 18.5ms；同比例的缓存滚动 wait 只有 6.4ms。用户希望在不影响性能的前提下提高分辨率。用户 2026-10-08 决定：**先测量，并去掉无变化的刷新；不做整块白板贴图缓存**（白板上有可拖拽缩放的函数图等交互卡片，以后还会增加交互，整板缓存的维护风险太高）。

本提交做了两件事：

1. **去掉播放时无变化的刷新**：
   - **旧行为**：播放时 60Hz 定时器每次都调用 `refresh()`，里面做 `set_state`（重算全部卡片，包括折线图重新采样），最后 `ui.redraw()` 整个界面。
   - **新行为**：每次定时器先比较 `refresh()` 依赖的全部输入，记录在 `TickKey`：播放位置、变量、旁白、滑块、任务、笔迹数、白板 revision 等。没有变化就跳过这次刷新，也不触发绘制。镜头过渡、高亮、老师指示点、加载卡这些动画由白板自己的 `advance` 继续每帧重绘。
   - **白板侧**：增加 `revision`。白板自己测量后重新布局，或 `set_state` 改变了构图或镜头规划时会加一，宿主下一帧随之刷新，直到状态稳定。
   - **附带修正**：内部重新布局时沿用宿主最近一次的 action，原来传的是 `None`。
2. **测量开关和计数**：用来拆分剩下的成本。

## Mac 结果（M 系列，1440×900，参考用；Mac 不是瓶颈）

同一 APP、同一课程从头播放，`OCTOS_BISECT=tickredraw` 为旧行为：

| 课程 | 旧：每秒 Draw / set_state | 新：每秒 Draw（典型） | 新：总帧数相对旧 |
|---|---|---|---|
| slope-and-intercept 18 秒 | 48 / 60 | 镜头过渡或高亮时 28–35，其余时间 0–4 | 约少 84% |
| surface-saddle-point-analysis 40 秒 | 48 / 60 | 同上 | 约少 85% |

画面对照：
- 每 3–5 秒截一张图，共 4 门课、32 个时间点。除镜头过渡途中的时间差和指示点脉冲的 2 个像素外，新旧逐像素一致。
- **有一处行为变化**：马鞍面课程第一张数学卡测量完成后，新版镜头比旧版低约 10 个世界单位，持续到下一个操作。
  - 原因是旧版在测量**生效前**就做了“测量后重新规划”，用的还是估算尺寸。这是帧时序造成的竞态。
  - 新版按代码注释的设计（也是 Web ResizeObserver 的行为），用测量后的尺寸重新规划。

## 请 GPT 在大屏真机上测

**APK**：基于本提交重新打包（同 [APK 构建交接](ANDROID_APK_BUILD_HANDOFF_2026-10-07.md)）。不改系统显示。

**通用条件**：
- intent extra 同上轮：`octos.OCTOS_PERF=1`、`octos.OCTOS_RENDER_SCALE=0.667`；`octos.OCTOS_BISECT` 按下表设置。
- 课程和播放区间与上轮相同：slope-and-intercept 从头播放约 24 秒；稳态剔除口径也相同。
- 如有时间，再用 surface-saddle-point-analysis（含 3D 卡片）跑 A、B 两组。

| 组 | `OCTOS_BISECT` | 目的 |
|---|---|---|
| A | （空） | 新默认：看播放时的帧数、gap、wait 降了多少 |
| B | `tickredraw` | 旧行为，作为同一 APK 的对照 |
| C | `nocards` | 不画任何卡片，只剩纸面、连线和笔迹：卡片总成本 |
| D | `noshadow` | 卡片无阴影：阴影的填充成本 |
| E | `nogrid` | 纸面不画点阵：点阵着色成本 |
| F | `novector` | 不画连线、指示点、笔迹和选区框 |
| G | `nocamanim` | 镜头直接跳到目标，不做 680ms 过渡：过渡帧占多少 |
| H | `nopulse` | 指示点不脉冲，不再每帧重绘 |
| I | （空）+ `octos.OCTOS_CENSUS=1` | 每秒按 shader 统计 draw call、实例数和覆盖面积，确定性数据，不依赖 GPU 计时 |

另外，A 组建议在 0.5 和 0.75 下各补一次，看提高默认分辨率的余量。

**请记录**：每秒的 `[perf]` 行。行尾新增了以下计数，每秒清零：

| 计数 | 含义 |
|---|---|
| `tick_unchanged` / `tick_refresh` | 定时器周期里跳过 / 实际刷新的次数 |
| `refresh` / `board_set_state` | 次数和总耗时 |
| `board_walk` | 白板遍历次数和总耗时，即 CPU 编码白板的成本 |
| `redraw_camera` / `redraw_highlight` / `redraw_pointer` / `redraw_loading` | 白板自己请求重绘的原因 |

**判读**：
- **A 和 B 对比**：看无变化刷新去掉后，剩余的帧主要由什么触发（看 `redraw_*` 计数），每帧 event 降了多少。
- **C 到 F 和 A 对比**：看剩余 wait 里哪一项占比最大，决定下一步：
  - 屏幕外卡片不画；
  - 只重画变化的卡片：给卡片独立绘制列表，并把指示点单独放一层；
  - 针对占比最大的那一项（阴影、点阵或文字）降低开销。
- **按可选的提高方案判断**：如果 A 在 0.667 下 gap 接近或低于 33ms，下一轮可直接讨论提高默认比例。

**请勿**修改默认比例，也不要合并或建 PR。测完请恢复无 extra 的正常启动。
