## 1. 决策摘要

采用以下架构作为方案基础：

**OLL 协议 → 平台无关的 OLL runtime → Web / Makepad 平台适配层。**

OLL 规定课程数据及其含义；OLL runtime 读取数据并执行课程；平台适配层负责把执行结果显示出来，并连接输入、存储、音频等平台能力。

用户已确定采用 B 路线：将共同 OLL runtime 迁移到 Rust，Makepad 直接调用，Web 通过 WebAssembly 调用同一份核心。保留 OLL 协议及已确认的执行语义，迁移现有算法、规则和测试，不另行设计两套平台专属课程规则。

Android 原生手写层作为可复用的输入/临时笔迹实现，先验证与 Makepad 共存；不把全部手写绘制改为 Makepad 作为前置条件。语音及应用外围以复用现有逻辑为原则，只改动必要的界面、执行环境和通信适配。

建议先完成分层与一条完整课程链路的验证，再逐步增加数学图形、公式、手写和外围功能。原报告中的“性能提升 3～10 倍”“35MB 内存”“8ms 手写”“12 周全部完成”等数字，均不作为本方案承诺。

本稿替代原调研文档中的迁移架构及实施路线建议；原文档保留作为历史资料，其中的性能数字和覆盖率不因保留而获得确认。

## 2. 名词与边界

| 名词 | 在本方案中的含义 |
|---|---|
| OLL | 课程协议：规定数据结构、指令含义、执行顺序及兼容规则。 |
| OLL runtime | 课程执行程序：读取 OLL，管理课程状态、动作、变量、播放进度和动画时间。本文不再用另一个未解释的“播放器”名称替代它。 |
| 平台适配层 | 把 runtime 需要的能力映射到 Web 或 Makepad；把设备输入转换成统一事件。 |
| polyfill | 为平台补齐缺失能力的兼容实现。本方案主要通过 Rust 接口及各平台实现完成，不为原生端模拟浏览器或引入 JavaScript 执行环境。 |
| WebView | Android 应用内嵌的浏览器环境，现有网页界面在其中运行。 |
| Makepad | 应用底层框架，提供绘图、窗口、文字与设备输入等能力。 |
| Octoscript-Makepad | 基于配套 Makepad 的组件与脚本工具集合，包含本方案要复用的两个绘图库。 |
| makepad-d3 | Octoscript-Makepad 中的绘图库，提供形状、比例尺、关系布局及部分三维图表能力。 |
| makepad-plot | 同一仓库中的绘图库，提供折线、散点、等高线、曲面等图表组件。 |
| PoC | 小范围可行性验证：交付可运行程序和结果，回答是否值得扩大投入。 |

“去 WebView”不等于“所有 Android Java 代码必须改写为 Rust”。原生端使用 Rust 共同核心，保留适用的 Android 原生代码；Web 端仍可使用 TypeScript 作为界面与 WebAssembly 调用层。TypeScript 不在 Octoscript 脚本环境执行，本方案也不新增 JavaScript 引擎来承载原生课程或外围逻辑。

### 3.2 现有 OLL 已经有分层基础

| 当前模块 | 本次看到的实际职责 | 方案处理方式 |
|---|---|---|
| `packages/core` | 协议类型、状态处理、数学表达式等。 | 保留协议，迁移需要在客户端执行的规则与表达式算法到 Rust；校验数值、错误和序列化行为。 |
| `packages/player-core` | `HeadlessLessonPlayer` 不创建界面；编排动作、推进状态、暂停继续、追加事件、保存恢复进度。 | 以现有规则和测试为迁移依据，实现共享 Rust 核心。源码类名中的 Player 对应本文的课程执行能力。 |
| `packages/web-runtime/src/runtime.ts` | 在上述核心上增加课程会话、播放调度、变量动画、学生操作等，同时包含浏览器存储。 | 将共同调度逻辑迁移到 Rust，把时间和存储等能力改成由适配接口提供。 |
| `web-runtime` 中的 camera、layout、plot 等文件 | 包含可复用的相机策略、布局和数学计算，也有面向网页显示的实现。 | 按函数实际依赖拆分，不能把整个目录都当作 Web 专属代码。 |
| `web-runtime` 中的界面、输入路由及资源处理 | 包含网页元素绘制和浏览器事件处理。 | 留在 Web 适配层，并为 Makepad 实现对应能力。 |

具体证据包括：已有 `PlaybackStore` 存储接口；其 `LocalPlaybackStore` 实现调用 `localStorage`；`BrowserLessonSession` 使用 `Date.now()` 和 `setTimeout()` 处理播放及动画。时间函数并非只有浏览器才有，但应通过接口提供，才能支持可控测试和不同宿主。

这意味着已有分层、算法和测试可以作为 Rust 迁移依据；复用的是协议与行为资产，不意味着 TypeScript 源码能原样在原生端执行。本次没有对全部传递依赖完成审计，也未运行相关测试，不能据此宣称提取工作已经完成。

## 4. 目标架构

```text
OLL 课程数据 / 持续到达的课程事件
                  │
                  ▼
平台无关的 Rust OLL runtime
协议处理、动作顺序、变量、教学时间、暂停继续、状态恢复
                  │
        显示状态与能力请求 ↓  ↑ 统一输入与完成事件
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 WebAssembly + Web 适配层   Makepad 适配层
网页绘图、浏览器输入     原生绘图、原生输入
浏览器存储与音频         设备存储与音频
        │                   │
        ▼                   ▼
浏览器 / Android WebView   Makepad 应用
```

runtime 不应持有网页元素、Makepad 控件或 Android View，也不应让某个图表组件自行解释 OLL 指令。

例如“一个点沿圆周运动”：OLL 描述运动；runtime 根据课程时间计算点的位置；适配层负责把点显示出来。暂停操作经适配层传入 runtime，由 runtime 冻结课程时间，不能只让绘图停止而内部课程继续推进。

### 4.1 谁负责哪些决策

| 工作 | 共同逻辑的职责 | 平台适配层的职责 |
|---|---|---|
| 动作与变量 | 指令顺序、表达式、状态变更、变量约束。 | 将更新后的状态应用到显示对象。 |
| 动画与时间 | 课程时间、进度、插值、暂停与倍速规则。 | 提供单调递增时钟与唤醒/帧通知；请求绘制。 |
| 布局与文字 | 使用测量结果安排课程内容，决定避让和对齐策略。 | 返回真实文字/公式尺寸、基线和可用显示区域。 |
| 画面移动 | 决定教学焦点，以及用户拖动画面与课程自动移动的优先级。 | 提供窗口尺寸、转换设备坐标、应用最终视图变换。 |
| 输入 | 判断写字、拖点、拖动画面等操作意图，按统一规则更新状态。 | 接收平台事件，归一化坐标、指针标识、时间及可选压感。 |
| 保存恢复 | 定义进度内容、版本与恢复规则。 | 将数据持久保存，报告成功或失败。 |
| 音频 | 决定何时请求播放，以及完成、失败、取消后如何推进。 | 调用实际音频服务并返回事件。 |

共同逻辑可以分模块，不必全部塞进一个类。字体度量和设备能力确实可能不同，跨平台目标是教学语义与操作结果一致，不要求所有像素完全相同。

### 4.2 建议的适配接口

以下是职责草案，不是已经存在的 API，也不是要求照着实现的最终签名：

| 接口 | 最少需要表达的内容 |
|---|---|
| 时钟与调度 | 当前单调时间、安排唤醒、取消唤醒；测试可使用人工推进的时间。 |
| 显示 | 对象创建/更新/删除、视图变换、重绘请求；首版可先传完整状态，再用实测决定增量更新。 |
| 测量 | 文字与公式的尺寸、基线；异步结果附对象版本，过期结果不得覆盖新内容。 |
| 输入 | 指针开始/移动/结束/取消，以及统一课程操作；明确设备坐标和白板逻辑坐标的转换位置。 |
| 存储 | 保存、读取、删除进度及用户操作记录；不要依赖同步浏览器存储才能运行。 |
| 资源 | 加载课程资产、字体和公式文件，返回加载状态及取消能力。 |
| 音频 | 播放、停止、完成、失败与取消；回调附请求标识，避免旧回调推进新课程。 |
| 能力声明 | 是否支持某类公式、三维、压感等，以及不支持时的明确行为。 |

首版只提取真实用例需要的接口，不先设计一套庞大的通用绘图系统。资源、音频或显示失败时，应明确反馈，不能静默跳过关键教学内容。

## 5. 已确定：B 路线，共享 Rust OLL runtime

用户已明确选择 B 路线。TypeScript 无法直接在 Octoscript 脚本环境执行；本方案不再探索内嵌 JavaScript 引擎的 A 路线。

目标为一份 Rust 课程核心、两种调用方式：

- **Makepad 端**：直接调用 Rust 核心，由 Makepad 适配层显示并连接设备服务。
- **Web 端**：将同一核心编译为 WebAssembly，即可在浏览器内执行的编译模块；现有 TypeScript/网页界面通过薄调用层使用它。
- **Android Java 服务**：通过 JNI（Java 与原生代码互相调用的接口）连接 Rust 适配层。音频和临时手写显示无需为了语言统一而重写。

### 5.1 迁移内容与不变项

OLL 数据及已确认的语义保持兼容；迁移协议处理、状态推进、表达式、变量、动作调度、暂停继续和恢复逻辑。现有测试与课程样本继续复用。若发现规范未定义的行为，先明确规则，不机械复制旧实现的缺陷。

Rust 核心不得直接依赖 Makepad、Android、网页元素或浏览器存储；计时、输入、资源及音频等通过适配接口连接。这样共享的是同一份源代码及规则，而非两个名字相同的 runtime。

### 5.2 迁移与切换步骤

1. 固定代表课程及预期状态，梳理表达式语法、数值边界、错误信息、标识符和恢复数据格式。
2. 实现最小 Rust 核心，用同样的课程与操作序列对照既有语义测试。显式处理 JavaScript 与 Rust 的数值及 JSON 表示差异。
3. 同时提供原生调用入口和 WebAssembly 调用入口。两个入口使用同一核心版本，比较同一输入下的状态结果。
4. Web 保留现有显示与产品逻辑，通过适配层逐步改为调用 Rust 核心；Makepad 直接接入。一个课程会话只能由一个 runtime 管理，不同时推进新旧核心。
5. 支持现有课程与进度的读取，或提供明确的数据迁移方案；完成一致性与回归检查后，将正式执行统一切换到 Rust。旧 TypeScript 实现仅在迁移期作为对照和回退，不长期维护第二套规则。

WebAssembly 的接口粒度、状态传输量、资源加载和错误映射仍需验证；这些属于已选 B 路线的工程验证，不再是 A/B 选型。共同 Rust 核心的完整迁移工作量，在边界盘点后重新估算。

## 6. Makepad 平台适配的能力方案

### 6.1 函数曲线与二维几何

复用 `makepad-plot` 的曲线和坐标轴能力，以及 `makepad-d3` 的几何生成能力。课程变量、表达式含义和教学动作由共同 runtime 管理。图表自身的拖动与缩放能力必须遵守统一输入和画面控制规则，避免一个操作同时移动图表与整张白板。

优先使用“单位圆生成正弦波”和“圆面积扇形重排”验证数据读取、变量更新、交互和动画的完整链路。不能只手写两个看起来相似的演示画面，就视为课程兼容。

### 6.2 数学公式：优先验证 Makepad 自带的原生排版

**审核纠正：配套 Makepad 已有 `makepad-latex-math` 和 `MathView`，此前审核遗漏了这部分。** 它们也存在于之前检查的本地 Makepad 中，不能将遗漏归因于版本过旧。先前把“需要另引排版引擎、优先预生成 SVG”当成主要路线的依据不完整。

现有实现链路为：公式 LaTeX 源码 → Rust 解析与排版 → 带位置的字形、线条等 → Makepad 原生绘制。`MathView` 使用数学字体，并缓存排版结果；公式内容或字体等发生变化时重新生成。它不依赖 WebView，也不要求事先在服务器生成图片。

建议优先验证这一能力。它更适合动态公式、端侧离线生成及当前共享 Rust 核心的方向。但公式排版仍是独立模块，不把 Makepad 控件直接引入平台无关 OLL runtime。runtime 提供公式内容，公式模块提供排版结果和尺寸，平台适配层负责显示。Web 端是否复用同一排版模块需要另验 WebAssembly 与绘制适配，不能据 Rust 实现就宣称已经支持。

已有分数、根号、上下标、部分矩阵等解析/排版实现和测试。以下源码边界需要特别检查：

- 未知命令可能被当作文字输出，未知字形可能留下空白，不能把“没有报错”当成公式正确。
- 上下大括号目前使用简化布局；字体样式切换还有简化处理。
- 解析器识别颜色，不等于组件支持公式内部逐段颜色。当前布局结果没有携带颜色字段，`MathView` 使用整体颜色，需要补齐相关链路。
- 现有组件使用展示公式样式；正文内公式、中文混排、宏及多行对齐需要实际样本验证。
- 字符命中、局部高亮及逐项变形不是天然获得的功能；若课程需要，应补充源表达式与显示部件之间的对应关系。

选型顺序建议如下，尚未经过完整课程与实机验收：

| 路线 | 适用定位 | 下一步 |
|---|---|---|
| Makepad 原生排版与 MathView | 首选验证，动态/离线公式可在设备处理。 | 扫描现有课程公式并逐条渲染对照，记录缺失及错误。 |
| MathJax 生成 SVG | 对未覆盖公式的兼容方案，以及测试参考。 | 已有课程随包提供；动态未知公式若依赖服务需明确网络限制。 |
| Typst + MiTeX | 若原生引擎缺口广泛，作为端侧替代候选。 | MiTeX 转换 LaTeX，Typst 排版；核实语法兼容、包体、耗时和 Makepad 绘制接入成本。 |

Typst 使用不同于 LaTeX 的公式语法，MiTeX 是转换工具；不能直接把现有 OLL 中的全部公式当作 Typst 语法执行。此路线只是候选，并非现成接入完成。

原生方案能减少预生成和网络依赖，但仍需明确支持的公式集合。不支持的命令应显式报告并选择可用后端，不能静默显示错公式。保留 SVG 兼容方案不等于否定原生排版，SVG 也只是输出格式，不必天然绑定服务器生成。

### 6.3 三维图形

最新图表库的三维曲面组件仍有 CPU 投影和排序；实际组件还包含 CPU 颜色/光照计算。不能仅凭 `DrawSurface3D` 的名字或片段光照代码，宣称已有完整 GPU 三维管线或十万面片性能保证。

当前已接入的图表组件并未调用 DrawSurface3D，现成组件路径没有接通报告所述的 GPU 三维实现；仅注册着色器不等于启用。不要扩大表述为整个 Makepad 没有 GPU 能力，也不要将公开导出的类型笼统判为不可用的“死代码”。

同时，配套 Makepad 本身另有三维场景与绘图实现。首轮先用已有图表实现测量真实课程；若不足，再评估将网格交给 Makepad 的三维能力处理。记录需要补的遮挡、裁剪、拾取和透明显示能力，分别验证正确性与性能。

### 6.4 手写与输入：允许 Makepad 与 Android 原生层共存

**可以设计为共存，且配套 Makepad 宿主已有接入基础；本项目尚未完成集成或真机验证。该入口在本地旧版 d4502ef 中不存在，必须在已固定的 825dbb4 配套组合上验证，不能直接使用当前旧目录构建。** Android 的原生 View 可以作为覆盖层与绘图 Surface 组合；配套 `MakepadActivity` 提供 `getApplicationOverlay()` 入口，可用于接入原生覆盖视图。实际层级、触摸分发和设备合成行为需要验证。

原稿“比较基线”只表示用现有应用比较效果，不表示已经完成共存。修订方案将“复用现有 Android 临时手写层”作为优先验证的实现路径，不要求先用 Makepad 重写全部手写。

当前源码中：

- `NativeInkOverlayView` 只显示正在书写的临时轨迹，不负责全部已完成笔迹。
- `NativeInkBridge` 采集 Android 触摸点，通过 `WebView.evaluateJavascript` 交给网页白板。
- 网页提交持久笔迹并确认后，原生覆盖层才清除临时轨迹。

因此复用方案不是直接复制两份 Java 文件，而是：

```text
Android 输入
   ├─→ 原生临时笔迹层：及时显示当前轨迹
   └─→ JNI / 输入适配 → Rust 笔迹状态与操作处理
                              ↓
                         Makepad 显示已提交笔迹
                              ↓
                    显示交接确认 → 清除临时轨迹
```

保留笔迹数据格式、采样过滤与可用绘制逻辑；将绑定 WebView 的配置、事件发送和确认改成平台接口。已完成笔迹的存储、擦除、撤销和回放由共同笔迹状态模块管理，Makepad 负责显示。该模块可与 OLL runtime 协作，不要求把所有笔迹逻辑塞入课程执行器。

必须验证：统一设备/白板坐标、缩放与平移同步、临时与持久笔迹无闪断/重影、快速连续落笔、取消事件、多指切换，以及写字与拖点的事件互斥。不能只因 Rust 接收数据就清除临时线条，应设计显示交接确认。原生预览只能在输入路由允许写字时启动，避免在按钮或拖点操作上留下临时线条。

此方式仍可完全去掉 WebView；它保留的是 Android 原生 View。其他平台由各自适配层实现手写。若共存测试暴露无法接受的问题，再评估 Makepad 直接绘制临时轨迹；不预设必须替换性能良好的原生层，也不承诺 8ms 延迟。

### 6.4.1 哪种手写方式更合适

共存有利于复用，不能据此认定性能最佳。现有 Android 层使用普通 Canvas/Path 和 invalidate，不等于已经采用专用低延迟前缓冲或预测绘制。

| 方式 | 优势 | 代价与建议 |
|---|---|---|
| Makepad 显示课程与全部笔迹 | 统一缩放、遮挡、擦除和截图，跨平台绘制更集中。 | 验证输入历史点、取消事件、压感及帧调度；不能保证仅因 GPU 绘制就更低延迟。 |
| Android 显示临时笔迹，Makepad 显示持久笔迹 | 复用现有快速显示路径，可以保留 Android 特定优化。 | 需处理坐标与显示交接；只有实测带来足够收益才值得承担额外复杂性。 |
| Android Ink API 等专用低延迟方案 | 可利用平台笔迹组件与预测等能力。 | 与 Makepad 的几何/显示交接不是现成功能；须核对设备与版本，不能当作简单替换库。 |

建议共同 Rust 模块统一笔迹数据、擦除/撤销/回放规则，平台层可选择显示路径。首轮给同一输入接上 Makepad 绘制与现有原生临时显示两种方式：若 Makepad 满足体验且不劣于现有路径，优先减少显示层；若 Android 路径在目标设备上有明确优势，则保留为平台加速实现。专用低延迟组件只在现有两条路径不足时进一步评估。

配套 Makepad 输入路径已通过 getPressure 读取压力；在审核提交的 Android JNI 转换中，没有历史点遍历，ACTION_CANCEL 落入默认返回分支、未转换为统一取消事件。这两项列为直接绘制路径的必修任务。getPressure 本身读取 AXIS_PRESSURE，不将其误列为压感精度缺陷。现有应用的 NativeInkBridge 已有历史点采集与过滤，因此输入采样逻辑也应评估复用，不只比较绘制代码。以上是源码观察，不是已完成的手写性能测试。

### 6.5 语音和应用外围：优先复用现有逻辑

这是用户明确的方案要求。保留现有业务行为、后端接口和可运行的平台代码，避免因更换界面技术顺带重做语音、登录或课程管理。

| 现有资产 | 复用方式 | 必要改动 |
|---|---|---|
| Android 录音、Agora 原生通话等 | 保留现有原生实现及已处理的设备兼容逻辑。 | 将 `NativeAudioBridge` 的 WebView 调用入口和 JavaScript 回调分离，改接 JNI/平台接口；保留 Android 主线程与生命周期处理。 |
| 服务端接口、登录及课程数据约定 | 保持现有协议、认证和业务流程。 | 适配网络、凭据存储、错误及取消事件；不改变接口来迎合新界面。 |
| TypeScript 中的语音会话、课程管理等业务逻辑 | 复用规则、算法、服务接口及测试；按模块迁移到可在目标端运行的 Rust 或适用的 Android 实现。 | TypeScript 不能原样交给 Octoscript；迁移实现语言不等于重设计业务。 |
| React/网页界面 | 保留交互需求和产品行为；Web 版本继续使用现有界面。 | 完全去 WebView 的 Makepad 版本需实现对应界面，网页组件不能直接作为原生控件使用。 |
| 权限、设备生命周期等已有 Android 逻辑 | 经盘点确认后优先保留，接入 Makepad 的 Android 宿主。 | 统一宿主入口与服务管理，防止两份 Activity/会话管理各自启动服务。 |
| 音频焦点（与其他应用协调声音占用） | 当前应用 Java 代码未见显式请求/释放焦点，不记为已有资产。 | 核实 SDK 是否代管及产品策略；补齐缺失的申请、失去焦点、恢复和释放行为，并验证通话/录音场景。 |

复用清单应逐项标记“源码直接复用”“改通信后复用”“迁移语言但保留逻辑”“仅替换显示界面”，并说明不能直接复用的具体原因。不能把所有 TypeScript 业务代码都归为“界面重写”，也不能把“保留逻辑”表述成“零改动直接运行”。

验收沿用现有登录、课程加载、语音会话、异常重连及后台恢复等行为，并补充新宿主的回归测试。第一阶段的独立验证应用不等于外围已经迁移完毕；完整原生交付时，不把保留 WebView 当作绕过外围适配的默认方案。

## 8. 验收方法

### 8.1 课程行为一致性

使用同一份 OLL、同一组输入和可控的课程时间，比较每个检查点的对象状态、变量、执行进度、暂停恢复结果和关键教学焦点。

以 OLL 规范与已确认的课程预期为准；旧 Web 版本仅作参考，已有缺陷不要求复制。未明确的语义先补规则和例子，再补测试。现有 `playback:conformance`（播放一致性检查）与其他相关测试可作为基础，但不把现有测试通过等同于跨平台完整验收。

至少覆盖：正常播放、暂停继续、跳转、保存恢复、课程逐段到达、重复或冲突事件、交互修改变量、动画取消、资源失败和过期异步回调。

### 8.2 显示与交互

验证公式完整性与基线、文字遮挡、几何位置、三维遮挡、点击目标与显示位置的一致性。允许字体抗锯齿等平台差异，不允许关键教学信息丢失。

测试白板缩放、窗口变化与显示密度变化后的输入坐标。绘制结果和命中判断必须使用一致的变换，不能分别猜测坐标。

### 8.3 性能与设备

同一台设备、同一课程、相同实际绘制分辨率、相同交互脚本下比较。4K 面板不等于应用正在按 4K 绘制，应记录实际显示缓冲尺寸与逻辑视口。

记录以下结果及测量方式：

- 帧耗时分布和明显卡顿，不仅记录平均帧率；60Hz 设备每帧约 16.7ms 作为分析参考，不作为未验证的达标承诺。
- 应用及关联进程的内存、图形内存统计方式和峰值；不同统计口径不直接比较。
- 输入到屏幕实际出现笔迹的延迟；软件事件时间不能冒充端到端延迟。
- 启动、课程加载、公式首次显示、连续运行至少 30 分钟后的稳定性。
- 真机型号、系统、构建模式、源码版本、课程规模与工具。录屏用作辅助，性能数据注明是否在录屏时采集。

阶段 0 在获得现有产品基线后，为代表场景确定明确的验收阈值；不要看到新方案结果后再倒推合格标准。首轮应证明行为正确、无关键体验退步，并在目标瓶颈上有值得投入的收益。

## 9. 关键风险与处理

| 风险 | 处理方式 |
|---|---|
| 平台逻辑未拆干净，共同核心仍依赖网页环境 | 审核传递依赖；用无浏览器执行测试发现隐藏依赖。 |
| Rust 迁移产生语义差异，或 WebAssembly 边界开销过高 | 对照协议和检查点测试；验证数值、序列化及恢复格式；实测 Web 状态传输粒度。 |
| 原生手写覆盖层与 Makepad 的交接/输入冲突 | 验证显示确认、坐标同步和事件互斥；复用不等于无需适配。 |
| 复用逻辑仍藏有 WebView 依赖 | 分离业务、平台服务和通信层；保留原生服务，迁移必要 TypeScript 规则与界面。 |
| 图表组件存在但不适合教学交互 | 逐课例验证，统一输入与画面控制；必要时复用底层几何能力。 |
| 公式方案只覆盖预制内容 | 明确离线播放、联网生成、离线生成三个范围，分别制定能力与失败行为。 |
| 新版本组合不兼容或无法复现构建 | 固定配套版本，在干净环境验证，升级时重跑代表课程。 |
| 手写或三维收益不足 | 保留现有实现作为对照，根据数据决定局部迁移或继续优化。 |
| 两个平台行为逐渐分化 | 使用统一语义规范与检查点测试，核心规则只维护一个正式来源。 |

### 12.3 历史进度与表达式迁移

**进度兼容列为阶段 0 独立盘点项。** 现有 checkpoint 是课程保存进度的数据，版本为 0.1，并用课程指纹强校验。当前指纹遍历 JSON.stringify 结果的 UTF-16 码元并做 FNV-1a 风格的 32 位运算，不是简单对 UTF-8 字节调用同名哈希函数。

必须建立包含中文、补充平面字符、数值边界、字段顺序、重复课程事件和恢复状态的样本，核对旧数据到新 runtime 的读取。可选实现策略：

1. 为旧版数据实现精确兼容读取与指纹算法；同时处理 JavaScript JSON 序列化差异。
2. 提供版本化迁移器，在可信的旧课程身份校验后转换为新格式，并保留可回退副本。

“必须永久逐位复制所有旧序列化行为”不是唯一方案；“不得静默丢弃用户进度”才是要求。也不能为了迁移直接关闭课程身份校验。新格式若采用规范化序列化，必须升级版本并明确转换边界。

表达式实现是范围较小的自研解析器，可复用语法和测试，但不能据代码行数承诺难度低。明确对齐：幂运算右结合、负号与幂的优先级、π/−/×/÷ 归一化、log 与 ln 的含义、归一化后的长度限制、变量缺失或非有限值、除零等非有限结果，以及 JavaScript Math.round 对负半数的行为。特别是运行时字符串长度与哈希使用的 UTF-16 计数，不能不经核对改成 Rust 字节长度。

### 12.4 WebAssembly 边界与协议治理

阶段 1 用代表课程的连续变量动画，测量每帧状态传输字节数、编码/解码与跨边界耗时、内存分配和总体帧耗时分布。以 60Hz 更新为一组测试负载，不把该负载称为已达成的性能。对比全量状态与必要的增量更新，达到阶段 0 约定的预算后选择简单可维护的方案，不预设必须做增量。

一致性样本及规范保存在 OLL 仓库。现有检查使用 node:test 等工具，迁移后为原生 Rust 与 WebAssembly 两个入口增加共同样本测试，并将相关测试作为持续集成（每次提交自动检查）的必过条件。协议行为变更必须同时提交规范、样本和双入口检查，不能只让 Web 或 Makepad 单独改变规则。

### 12.5 公式外观与历史文档勘误

MathView 使用 NewCMMath 数学字体，当前组件按 font_size × 1.75 设置排版尺寸，并采用展示公式样式；与现有网页公式的外观不保证相同。阶段 0 输出代表公式的对照要求，阶段 1～2 给出实图供审阅，确认可接受的字体、尺寸、行内基线和局部强调效果。离线生成任意新公式仍是待明确的产品要求，本次评审不代替用户决定。

原 README 顶部增加历史资料提示，保留原文以便追溯。以下数字与名称不得继续作为实施依据：

- 当前审核 OLL 的 AuthoringAction 为 9 种，状态执行分支对应 9 种操作；节点类型为 10 种。旧报告将动作写成 10 种有误。

### 12.6 未原样采纳的评审表述

- “getPressure 不是 AXIS_PRESSURE，可能损失精度”：纠正。Android 官方明确该方法返回 AXIS_PRESSURE 值；压力能力仍按设备验证。
- “手写桥有 8 个接口和 emitEvent”：纠正归属。当前 NativeInkBridge 有 3 个注解接口及 dispatchBatch；8 个注解接口及 emitEvent 对应 NativeAudioBridge。接口少有利于拆通信，但不直接证明集成难度中等偏易。
- “DrawSurface3D 是死代码、现成 GPU 路径不存在”：限定为当前活动图表组件没有接通该绘制路径；框架有其他 GPU 三维能力，旧示例也存在该类型引用，不将其扩大为全库能力否定。
- “Rust 必须逐位复现旧指纹，否则进度全部作废”：接受兼容风险，但允许经过验证的版本迁移方案，不以哈希差异直接断言所有存量数据必然丢失。

参考：[Android getPressure 官方定义](https://developer.android.com/reference/android/view/MotionEvent#getPressure(int))；其余事实对应本稿 §11 的固定源码版本与本地 OLL/Android 实现。以上评审吸收不代表任务已完成或自动批准实施阶段 0。
