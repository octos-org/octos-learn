## 1. 这一阶段要交付的结果

学生提问、学习一节课、退出后继续，系统能准确回答：问过什么，生成了哪节课，实际播放过哪些内容，做过哪些练习；这些记录能够联网补传，重复发送不会增加次数。

先选一小组课程，完成它们与知识点、具体教学目标的对应核对。完成后，才能回答：在哪些课中接触过、涉及哪个具体教学目标、提问多少次、在哪几次学习中播放过相关内容。每个数字都能展开查看原记录。当前只有待审草案，不能将这项核对写成已经完成的成果。

第二阶段准备可供老师读取的学习事实和查询接口。让 Learning Coach 在真实课程中使用它们，仍属于后续接入工作，不能用一次接口查询代替“老师已经记得学生”的验收。

## 2. 存在哪里：建议由 Octos Learn 服务端保存正式记录

**建议：Octos Learn 服务端使用 SQLite 保存正式学习记录；网页和 APK 用 IndexedDB 保留离线记录与待上传任务；Octos 继续统一处理长期记忆。**这项存储选择是本次建议，尚未视为用户已确认。

三者的职责用例子说明：

| 放在哪里 | 保存什么 | 能回答什么 |
|---|---|---|
| Octos Learn 服务端数据库 | 某次提问、某节课的身份与版本、实际播放和练习记录 | “这次学习播放到哪里？斜率相关讲解在哪几次学习中播放过？” |
| 设备上的 IndexedDB | 尚未上传的记录，以及本机继续播放所需的状态 | “电视断网时先记下来，联网后继续上传。” |
| Octos | 真实对话的记忆处理材料、提炼后的偏好和经历 | “这个学生长期偏好先看图；怎样合并、纠正或遗忘这项偏好？” |

这份学习数据库不保存另一套“学生性格画像”，不调用模型分析偏好，也不决定长期记忆该留下什么。它只保存和查询实际提交的记录，按明确规则算数。例如，把五个不同的学习编号数成五次，不涉及语义理解。

原始问答会有供 Octos 处理的对话副本；这些副本不参与学习次数统计。长期记忆的处理者仍然只有 Octos。

### 为什么不选另外几种做法

| 方案 | 判断与理由 |
|---|---|
| 只存在设备上 | 不建议作为唯一正式记录。换设备不能自然看到完整历史，清理浏览器数据也会丢失尚未上传的部分。保留它作为离线能力。 |
| 全部作为 Octos 会话消息 | 真实问答适合；“滑块提交一次答案”不应冒充学生说的话。会话接口也不是按知识点统计学习次数的接口。 |
| 全部放进 Octos Recall | 适合作为相关资料供检索；不适合作为完整计数依据。检索有数量限制，冷资料还可能按容量规则清理。 |
| 每次操作保存成一个 JSON 文件 | 可以做到，但精确查询、重复检查、并发修改和删除关联仍得自己实现。已有 Octos 文件接口没有替应用解决这些规则。 |
| Octos Learn 使用 SQLite | 当前推荐。支持明确字段查询、唯一编号及一组修改一起成功或失败；适合先在一个服务实例上完成这项产品能力。 |
| Octos Learn 直接使用 PostgreSQL | 若准备多台应用服务器同时写入，值得选择。当前先不为尚未确认的部署要求增加独立数据库服务。 |

SQLite 官方说明支持将它用作应用服务背后的数据库，也明确列出了高并发写入和多服务器场景的限制。这里是在“单个产品服务写入本机磁盘”的前提下作出的工程建议，不是已经测得容量充足的结论。依据：[适用场景与限制](https://www.sqlite.org/whentouse.html)、[事务保证](https://www.sqlite.org/transactional.html)。

### 服务怎样放置

代码放在本仓库，例如 `services/learning-history/`，独立于语音和 Key 处理模块。复用当前产品服务的进程入口和端口，开发环境由 Vite 挂载同一处理模块，不要求人工验收另起一套端口。

正式数据建议放 `/var/lib/octos-learn/learning/history.sqlite`，位于部署产物之外；本机使用专用持久目录，例如 `~/.octos-learn/learning/`。这些是应用记录目录，不是新建 Octos 账号或替换既有 `~/.octos`。目录位置通过配置指定，服务端配置仍放 `/etc/octos-learn/*.env`。

数据库不放 Git、`dist/` 或课程包中，不直接读写 Octos 内部记忆文件。现有 systemd 模板启用了只读文件系统保护，实施时只为新的数据目录增加写权限。备份必须覆盖应用数据，发布替换代码不能覆盖数据库。

具体接入点必须在第 2 批交付：Vite 挂载学习记录 handler，生产 `start.mjs` 及服务路由分发增加新 handler；现有 byok handler 只识别自己的前缀，不会自动处理新接口。Nginx 模板增加 `/api/learn/history/` 到 50081 的路由，否则会落入通用 `/api/` 并发往 Octos 50080。当前前端发布脚本只同步静态资源，计划同时补充产品服务和 Nginx 配置的发布、校验及回滚步骤；本阶段编写和验证这些步骤，不因此获得公网部署授权。

备份要落实到[公网运行手册](PUBLIC_DEPLOYMENT_RUNBOOK.md)的升级与回滚章节：增加 learning 数据目录，采用一致的数据库备份方式，实际恢复核对记录、删除标记与待交付任务；不能只拷贝正在写入的主数据库文件而忽略 WAL 中的数据。恢复时区分数据格式升级与代码回滚，不承诺旧代码可以读取任意新版数据库。

SQLite 具体 Node 绑定在实施的第一批确认：本机 Node 为 v24.16.0，生产 Node 版本本次未核实。仓库历史 `services/hosted-tts/server.mjs` 已使用 `node:sqlite`，可参考其事务与锁等待处理，不照搬语音额度业务，也不据此推断当前生产运行时。

**不预先强制增加 worker，也不预先断言同步查询不会影响语音。**先限制批量大小、索引和事务范围，测量普通写入、锁争用、历史查询及备份时的等待。历史实现设置过 5000 毫秒锁等待，同步数据库操作会让同进程的其他请求一起等待；“语音整块返回”不能消除这个影响。若无法保证同进程请求及时响应，再将数据库工作移到独立 worker 或采取其他可验证的隔离方式。选择由第 1、2 批的实验和性能验收决定。

## 3. 怎样保证记录属于正确的人

服务端沿用 Octos 登录认证：携带当前凭据向固定 Octos 地址确认身份，只使用 Octos 返回的 profile ID 作为归属。客户端传来的 `student_id` 或 `X-Profile-Id` 不能选择其他账号的数据。只复用身份校验，不为学习记录读取或复制用户的模型、语音 Key。

第一版建议以一个 Octos profile 为一个学习记录归属，不另建登录系统。这不证明同一账号背后只有一个自然人。如果需要家长账号下多个孩子，必须先增加明确的学生选择与隔离，不能把不同孩子的记录混在一起后称作个性化。

设备待上传记录也按“服务地址＋已确认的账号”分开。退出或切换账号时立即停止原队列上传；原账号的数据不能交给新账号。离线期间身份不明确的记录不能凭当前登录账号自动认领。

记录中可以保留当时已知的老师编号与设定版本，缺少时保持未知。这只说明参与者，不提前决定老师之间共享哪些记忆，也不允许后来的老师声称亲历过去的课堂。

## 4. 记录哪些内容

先记录会影响历史、进展和计数的事实，不收集每一帧动画或每一次指针移动。

| 记录 | 最少包含什么 | 不能据此宣布什么 |
|---|---|---|
| 学生提交问题 | 问题编号、学生原话、输入方式、原白板、附件引用 | 连问几遍不自动等于“基础差”或“喜欢这个话题” |
| 课程生成和交付 | 对应问题、实际文件与版本、成功/部分成功/失败；已交付的老师文字 | 生成完成不等于学生已经学习 |
| 开始或继续学习 | 本次学习编号、课程身份、设备及动作 | 刷新、继续播放不算新的一遍 |
| 实际播放片段 | 本次学习、课程版本、片段、是播放经过还是仅跳转查看 | 跳到最后一段不等于前面都学过 |
| 练习尝试与提示 | 任务、操作编号、答案或操作结果、提示使用情况及程序判定 | 拖滑块达成目标不等于独立掌握整类题 |
| 明确重新学习 | 新的学习编号、原课程及此前学习的关联 | 同一遍中回放一个片段不增加整课学习次数 |

图片和录音继续引用已有账号文件，不把大文件重复塞进学习库；不可变课程包按既有版本及散列引用。实时生成的课程文件可能持续追加或被后续版本覆盖，单留路径和指纹不能还原当时交付内容，因此实现时保存当次原始 JSON 字节，与交付事实一同持久保存和补传，具体上限及回退限制见实施进展。引用失效且没有原文时显示材料不可用，不能为了补全历史重新生成另一节课。

流式课程把“生成了多少、交付了多少、实际播放了多少”分开记录。用户已经听到前两段而生成后来失败时，前两段仍然是有效经历；未交付的计划、推理文本和未播放部分不能冒充完整课堂。

### 几个编号各自解决什么

- 问题编号：同一个问题的重发沿用编号；学生主动再次提问产生新编号。问题 A 的课程即使晚于 B 完成，也始终对应 A。
- 课程身份：预制课保留课程 ID、版本、包哈希；实时课保留生成请求、实际文件及内容版本。课程同名不等于同一份内容。
- 本次学习编号：与白板、问题和课程编号分开，是每条播放和练习记录的必填归属。刷新或继续沿用；明确重新学习才新建；可以记录只重新学某几个片段的范围。
- 操作编号：一次播放完成、一次作答只生成一次，重试沿用。Runtime 的 operation_id 保留为原始依据，不能当作跨设备、跨重学的全局唯一编号。导出记录还要带所属学习编号和持久的操作日志编号，避免两个设备或清空后重建的日志都从序号 1 开始时撞号。
- 发生时间与服务端收到时间：离线补传保留原发生时间，同时记录何时收到。客户端时间异常时注明不确定，不能拿它覆盖另一台设备的新记录。

现有播放器的重播、跳转和内部运行轮次不能直接当作新一次学习。需要在调用边界明确区分“重新学一遍”“查看某片段”“继续上次”，再接入记录。

目前 Runtime 的 `reset()` 只重置播放，不清除练习日志。重新加载保留的操作日志时，操作序号会接着增加，因此不能说“每次 reset 都会撞号”；真正的问题还包括旧练习成功状态随重播保留，以及日志清空或另一设备从头创建时复用序号。

明确开始新一次学习时，需要先持久保存新学习编号，再创建与其对应的播放和练习存储范围；不能把旧日志重新挂到新编号下。继续同一次学习保留原范围，查看或回放不清除历史练习。操作日志损坏或被清除后重建时分配新的日志编号，不静默将新操作覆盖到旧编号；无法恢复的旧尝试标为不完整。

### 怎样取得实际播放的依据

现有播放恢复文件只说明最后位置，跳转查看也会覆盖它；Runtime 的 seek、逐步推进和正常播放又会应用相同的底层操作。**不能事后从恢复位置、画面最终状态或完成标志反推出播放经历。**

第 1 批先验证最小采集方式，第 4 批落实：记录动作的原因（正常播放、查看、跳转、手动跳过、恢复），并在确实发生的播放推进和片段完成处保存依据。点击 play 只证明启动意图；`nextBeat` 会连续推进操作，也不能因此计成正常播完。跳过之前的内容仍保持未确认，恢复时不得重新导出已经提交的完成事件。

当前 hook 的 view/play 动作可以提供原因，但普通订阅只通知“发生变化”，不能假定它足以覆盖所有推进与中断。优先在产品适配层实现；若现有 Runtime 不能提供足够的操作来源与实际完成信号，就在 OLL 单独设计最小通用通知，不用轮询恢复位置或给特定课程打补丁。

旁白记录另外保留结束原因：播放设备报告正常结束、用户关闭语音、合成或播放失败后继续文字展示、取消或被新片段替换。当前 TTS 回调将这些情况的一部分合并为同一“完成”，需要在本仓库分开。没有语音时仍可记录真实图文播放，但失败兜底回调本身不能当作片段已完整展示的证据，更不能声称学生“听完”。

## 5. 怎样计算“反复学过”

**建议把提问次数、相关讲解播放次数、整课完成次数和练习结果分别展示。第一版不用一个含糊的“学习次数”涵盖它们。**

| 数字 | 建议规则 |
|---|---|
| 提问次数 | 按不同的问题编号计数；只有存在可靠知识点关联的问题才进入对应知识点统计 |
| 涉及某知识点的讲解播放次数 | 在每个学习编号内，只要有至少一个经核对、关联该教学目标的片段实际完成播放，记一次，并保留音频/图文方式；点击播放、跳过和失败兜底不算。同一遍多次回放该片段仍是一次 |
| 整课完成次数 | 不同学习编号分别判断必需讲解片段是否实际完成；直接跳到结尾不算。练习另列，不以课程播放完成代替练习完成 |
| 练习尝试与成功次数 | 在账号、本次学习及操作日志范围内，以任务＋实际操作编号去重，保留失败、提示及成功记录；按题型说明“成功”的具体含义 |

这些是产品口径建议，实施前需要确认，并给口径保存版本。一次操作重复提交十次只能产生一条有效记录；学生主动重新提问十次则是十个问题，不能按文字相同把它们合并。

例如：学生生成三角函数课程后没播放，记录为“提问一次、课程已生成”；实际播放一段后刷新继续，仍是同一次学习；之后明确重新学习并播放相关片段，才增加另一次相关讲解播放记录。

这种计数只能说明发生过什么，不说明学生专心听过、理解了或掌握了。给老师的背景也必须保持这个精度，例如“相关讲解在三次学习中播放过”，不能改写成“我教了你三遍，你还不会”。

## 6. 知识点怎样关联

知识点目录以用户此前提出的 [os-taxonomy](https://github.com/withmarbleapp/os-taxonomy) 为基础。它提供知识点编号、名称、范围、判断学习结果的参考及前置关系；不提供 Octos Learn 课程与片段的对应，也不提供学生学习记录。

三份信息各自来源明确：知识点来自该仓库；“我们的课程哪段讲到哪里”由课程制作和审核建立；“这个学生实际接触了哪里”来自本阶段采集的真实记录。查询通过知识点编号、教学目标和映射版本把三者关联，不在每次播放时调用模型重新分类。

从第一阶段的[《斜率和截距》映射草案](personalized-teachers-phase1/topic-mapping.draft.json)开始，先做一门经过教研核对的预制课。第一阶段只核对了引用存在，不代表教学覆盖已经审核通过。

“一小组”这样取得，不是上游直接提供的一份已审核课程清单：

1. 从已经有实际课程文件的预制课开始，例如《斜率和截距》，先限定范围。
2. 对照真实旁白、板书、动画和任务列出教学目标，不只看课程标题、生成计划或最初的课程要求。
3. 在固定版本的 topics.json 中筛选数学候选，按描述和学习结果参考匹配，写出相符与未覆盖的部分。找不到合适节点就保持未关联，不为了计数硬挂到相近节点。
4. 我或其他 agent 可先整理候选对应表并附依据；程序检查编号、片段、任务与版本确实存在；再通过课程库既有的内容审核确认教学范围。涉及正式发布的教学覆盖仍遵循既有人工审核约定。不能让编号存在检查或 agent 自评替代教学审核。

### 实时生成课程是主要场景：本轮讨论补充

用户进一步明确：主要内容来自学生自由提问后实时生成的课程。前面的人工对应表只适用于预制课和验证样例，不能作为所有课程的处理办法；不能要求用户逐堂审核生成课。本节以下是拟议方向，尚未实现，也未运行新增模型调用。

先保存已经发生的原始内容：学生原问题及必要的前文、实际交付的课程与片段身份、相关内容版本、真实播放和练习记录。即使知识点尚未辨认，也能回答某个问题何时提出、哪堂课由它生成、哪些片段实际播放；知识点归属失败不应阻止这些事实保存。

需要分别理解两件事：一是问题在问什么，二是实际生成的各段讲解讲了什么。老师可能补讲前置知识或拓展内容，不能把课程涉及的所有知识点反过来算成学生提问的知识点。“还是不懂”这类追问需要它所回应的原问题和上下文；图片问题需要实际图片或可用的识别结果。材料不足时保留未确定，不能只按标题、相邻白板或一句追问猜归属。

建议由 Octos 在后台完成这种理解与记忆处理。Learning Coach 正常生成课程，产品采集真实内容与播放记录并提供知识目录资料；不增加 Learning Coach 自己整理跨课记忆的流程。Octos 应依据实际旁白、公式、画面与任务判断内容，已有课程目标和章节用途可作为辅助，不能只依据“计划要教什么”。生成失败、只交付部分内容或流式内容后续变化时，只使用实际交付的版本及片段；不能把最终完整课程的所有标签套给较早播放的内容。

知识目录应提供经过检索的候选节点、范围与固定版本，允许一段对应多个节点，也允许无合适节点。目录覆盖不到的经历仍由 Octos 保留和检索，不为点亮地图强行挂到相近节点。自动判断应带上所依据的问题或课程片段、内容版本及关联结果的版本；程序可检查引用存在，但不能据此宣称语义判断必然正确。模型自行给出的高置信度也不能代替质量验证。

播放发生时先保存事实，不等待后台理解。之后若 Octos 确定某片段涉及斜率，可把它与早先保存的实际播放记录关联；这是重新解释已有记录，不是补造播放经历。统计应表明“按当前已关联记录”，保留未归属问题与片段；后来纠正归属时按新版本重算，不改写原问题、原课程和原播放事实。一次播放仍不能证明掌握。

现有代码已提供课程目标、章节用途、实际旁白、公式和画面操作，以及问题、课程交付摘要和播放事实；但尚无可靠的实时课程 taxonomy 自动对应。现有 Octos 记忆入口能接收资料、检索与整理记忆，不等于已具备“返回可追溯的逐片段知识点关联，并完整枚举用于计数”的接口；课程交付事实中的散列也不等于服务端已保存可读取的完整快照。下一步要核对原始课程材料的可读取方式与 Octos 的结果读取能力，再决定如何最小接入；不直接假设自动 ingest 就能完成。

后台处理不增加首个可播放片段之前的模型往返，但仍会产生模型费用，且可能与前台争用服务资源。需另行验证关联质量、成本、处理延迟和课堂性能，安排在课堂空闲时并能暂停重试。本次已有六次生成预算已用尽，不据此授权新的后台模型实验。

### 这项后台理解怎样执行：具体建议，尚未实施

本轮核对 Octos main `413b4b68`：内置记忆刷新直接使用固定提炼提示词调用模型，输入是当前记忆与对话内容，不加载技能，也没有知识目录分类结果的字段。因此，不能靠安装一个技能或提交 ingest，就宣称原有刷新流程会自动完成知识点归属。

建议优先验证一个由 Octos 智能体执行的“学习记录分析”技能：它规定怎样读取原问题、实际课程和知识目录，怎样分别判断提问及讲解归属，以及怎样返回依据。语义判断由 Octos 的智能体使用其本人 profile 模型完成；技能配套程序只做材料读取、目录检索和结果检查，不另建模型调用客户端或个人记忆系统。Learning Coach 仍只生成课程；产品只登记待处理任务、提供事实和按结果计数。

知识目录以固定版本文件及可检索索引提供，完整目录可供技能查阅，但每次模型只读取候选条目的名称、编号、定义和范围；找不到就扩大检索或返回未确定。现用快照有 1616 项，其中数学 529 项，无需整表反复注入提示词，也不放进每个学生的 MEMORY.md。中文课堂与英文目录的检索效果要验证；允许无合适节点，不以“编号存在”证明归类正确。

拟议运行过程：实际课程内容交付后保存待分析任务；待课堂空闲，由调度方请求 Octos 按该技能处理；Octos 按需检索目录并使用模型判断，输出问题和片段分别关联到哪些节点、所依据的原文与片段、课程及目录版本、未确定部分；程序检查引用和格式后保存结果。只有与真实播放记录相符的片段才产生学生接触经历。实际长期偏好与共同经历仍进入 Octos 既有记忆机制，知识点对应表不能代替个人长期记忆。

上文“保存待分析任务”的具体含义需要明确：此前建议的是在 Octos Learn 产品服务的 SQLite 中新增待办记录，保存所属账号、原问题与课程内容版本、分析规则版本、处理状态及 Octos 任务编号；同一份内容与规则只登记一次，重试不重复制造新任务。这只是拟议的任务账本，不调用模型、不处理记忆。目前代码中的 `delivery_tasks` 只服务于原始问答交付，不能说已经支持知识点分析；新的分析待办及派发程序均未实现。

Octos 目前已有 `skill/action/invoke` 创建后台技能执行、`skill/action/job/list` / `read` 查询持久状态。但这些是执行记录：服务重启前未完成的任务会显示为 `abandoned`，不会自动恢复执行；它也不等于“先登记分析意图，待课堂空闲自动按技能运行智能体、失败后持续补做”的完整接口。应用登记待办、Octos 创建执行任务，是两个步骤，不能混称为 Octos 已有登记能力。是否复用现有能力加产品派发即可，还是确有必要补 Octos 通用任务能力，仍属 P2-13 待验证；不能把待办行写入成功当作端到端执行已经解决，也不能假定无人在线时已有代表本人调用 Octos 的认证方式。

这里的“后台”是另外一次由 Octos 执行的任务，不是原有记忆刷新顺便做完，也不是技能安装后自动常驻。现有技能后台 action 只保证绑定工具的执行和任务状态，不自动代表“Octos 智能体按技能调用模型”；现有 cron 虽可触发智能体，但不直接视为本产品的最终调度方案。需验证合适的运行入口、账号与来源、忙时推迟、失败重试，以及完整结果的保存读取。维护任务不可伪装成学生说过的话，不能让分类结果被误学为学生掌握事实。

目前选择是“先验证技能方案，不先修改 Octos 记忆内核”。若已有能力无法安全触发任务、隔离来源或保存读取结果，再提出具体、通用的 Octos 补充；不把数学目录、知识点计数和学校课程规则硬编码进上游。新任务的费用与预算也需单独管理，不能假设它自动受记忆刷新的每日额度限制。本轮仅做源码核对和方案说明，未创建技能、定时任务或新增模型调用。

实时课程如果没有可靠关联，先记录原问题和课程，知识点保持未关联。不能通过标题关键词、向量搜索相似度或额外调用模型，偷偷给出“精确知识点次数”。第一版允许课程历史完整、部分知识点统计尚不可用。

提问关联也与课程覆盖分开：学生只问斜率，课程顺带讲了截距，不能因此把这次问题也计为一次“问截距”。只有问题与目标的关联可靠时才计入该目标；不明确的自由提问仍保存原话和课程，暂不报告精确知识点提问次数。

知识地图界面、点亮规则、徽章文案和自动安排复习不是本阶段交付，但它们以后使用相同记录，不能再各算一套数字。

## 7. 怎样保存、补传与查询

### 保存与补传

设备先把记录及待上传任务保存到 IndexedDB，网络恢复或重新打开应用后补传。上传失败保留原编号和内容，不能每次重试创建新编号。

服务端将“记录编号、内容及需要交付给 Octos 的任务”一起保存：同账号同编号同内容返回已有结果；同编号不同内容拒绝。数据库确认提交后才显示已同步。数据库繁忙、磁盘满或账号失效时，不显示成功。

设备收到确认后可以清理已上传任务，恢复位置等本机状态按现有机制保留。浏览器空间不足或未上传就清理应用数据，仍可能丢失离线记录；界面必须区分“本机已保存”和“已同步”，不能承诺设备被清空后仍可恢复。

记录写入不加入课程生成的前置等待，也不增加模型调用。课程可以正常开始；保存失败要有重试提示。若事件尚未成功保存就关闭页面，不宣称已经保存。

已有播放状态和新事件需要共同写入或能从稳定操作记录恢复，避免“本机进度已前进、待上传事实却丢了”。如果现有 Runtime 同步存储接口无法一起提交，就在本仓库的存储适配层保存待导出的事实；不能只用 React effect 的内存差异作为唯一记录来源。

目前存储层的待执行与失败列表只在内存中，页面关闭后不能靠它们重试。新队列必须先作为持久记录提交，明确区分“内存中待保存”“本机事务完成”“服务端已确认”。关闭页面钩子只能尽力补救，不能替代已完成的事务。自动化测试需在进度保存与事件保存的各个边界终止并重开，确认已提交数据可恢复；未提交就关闭时不承诺零丢失。

### 服务端查询

建议提供以下产品接口，名称在实施时统一，均属于 Octos Learn，不新增到 Octos 通用协议：

| 产品接口草案 | 用途 |
|---|---|
| `POST /api/learn/history/events` | 有上限地批量提交实际记录，逐条返回接收、已存在或冲突 |
| `GET /api/learn/history/runs` | 按课程与时间分页查看本人的学习历史 |
| `GET /api/learn/history/runs/:id` | 查看一次学习对应的问答、课程、已播放片段和练习 |
| `GET /api/learn/history/topics/:id` | 查看某知识点各教学目标的次数及原始依据，支持时间范围 |
| `GET /api/learn/history/changes` | 按服务端顺序增量同步新增及删除状态 |
| `DELETE /api/learn/history/runs/:id` | 删除一次学习记录，按下一节的范围处理 |

列表按服务端接收顺序使用稳定的下一页位置；一次查询固定“统计到哪些已收到记录”，避免翻页时新数据插入造成遗漏。日报、周报等未来使用的时间范围要明确时区，并说明迟到补传如何纳入。

次数由数据库按字段准确查询，不从搜索前几十条结果数出来。返回次数时同时返回对应记录或可继续查阅的入口、映射和计数口径版本，以及当前同步范围。

跨设备同步先交付历史、已播放片段和练习事实。有依据的实际播放片段按课程版本取合集；同一次尝试按学习、日志与操作编号合并。浏览位置、最远实际播放位置和已覆盖的片段分别保存：学生主动返回第一节复习，不应因为另一台设备播放得更远而被强行带走；最远位置中间也可能有未播放的空缺。可以展示最远进展，但不拿它覆盖各设备的继续位置或宣布整段全部学过。完整笔迹、白板布局和全部播放状态的跨设备恢复不在本阶段暗中扩建。

## 8. 怎样把真实问答交给 Octos

复用 `session/append_message`，不给每个程序事件伪造一条 user 消息。

- 学生真实原话使用 user；实际交付的老师文字使用 assistant，并明确绑定原问题的 thread_id。程序观察不混入学生原话。
- 每条对话副本有稳定的 client_message_id；较长的真实回应按固定边界分段，分段编号也稳定。附件保留原引用。
- 已经过普通 turn 自动记录的路径不再追加，按下表确定本次请求走的实际路径。source 字段可辅助核查来源，不作为唯一的防重复依据或授权凭据。
- 数据库中的交付任务只负责传递原文和核对回执，不生成摘要、不判断偏好、不调用模型。

本次核对的实际入口如下，第 3 批按“主要入口均需补记录”估计工作量：

| 入口与条件 | 当前执行路径 | 问答记录接入 |
|---|---|---|
| 常规语音，无额外媒体导致回退 | 直调课程 action；有当前相机画面时也走直调 | 补真实问答 |
| 纯文字、文字＋当前相机画面，无应用上下文与其他白板引用 | 直调课程 action | 补真实问答 |
| 选区课程、选区局部辅助及相应语音选区 | 直调课程或辅助 action | 补学生原话和实际交付的对应回应 |
| 独立图片上传提问 | `sendMessage` → 普通 turn | 不再补同一套会话消息 |
| 文字携带应用上下文，或引用未进入单选区直调分支 | `sendMessage` → 普通 turn | 不再补同一套会话消息 |
| 语音携带额外媒体而从直调分支回退 | 回到语音会话入口继续处理 | 第一批核对实际路由后标记，不能当作所有语音都直调 |

Octos 的直调 action 框架执行工具、保存任务结果并发出进度，不自动把学生原话和课程旁白追加成会话问答；Learning Coach 源码中也未发现这种追加。任务输出文件或日志不等于会话消息。普通 turn 的关联编号不能假定与 append_message 的 client_message_id 去重契约相同；按请求的确定执行路径分工，并用实际服务测试确认。

**已确认的缺口：应用数据库保证不重复，不等于 Octos 会话副本也拥有同样的保证。**现有 append_message 只在已加载的历史中检查重复；standalone 消息查询既受加载窗口限制，也不返回用于匹配的 client_message_id。消息分页封装没有提供切换完整历史的 source 参数。因此现有常用接口不能可靠核对旧消息是否已经写入。PR #2848 的 request_id 保护不适用于这个方法。

第 1 批不再重复泛查“是否有缺口”，而是复现“写入成功、回执丢失、超过加载预算、重启后重试”，验证最小修正。方向是在追加入口处理历史窗口之外的重复编号，并使核对与写入不会被并发请求打断；可以评估持久接收登记或在同一写入保护下核对完整历史。具体实现以实验和上游审查为准，不预定新增一个面向应用的业务记录库。

只给查询补 client_message_id/seq，仍看不到窗口外的记录；只给追加回执补 appended 标志，回执丢失后仍不知道结果。它们可以帮助观察，但不能单独完成修复。未可靠确认的任务保持“待核对”，不盲目重发、不假装已同步。

这项通用修正单独提交上游 PR，不混入 #2848。正式验收问答交付前必须解决限制，或由用户明确接受具体边界；其余学习记录开发可以继续。测试还需覆盖不同账号与消息生产者、相同编号不同内容、并发重试及原会话被删除后的行为，不把这些处理结果默认等同于 memory/request。

待交付任务不保存用户登录 token。首版建议由持有本人有效认证的在线设备领取任务，通过已有认证连接交付并登记回执；关闭应用或认证过期时保留任务，下次登录继续，不承诺无人在线时产品服务仍能自行代表用户写入 Octos。多个设备同时领取的处理也必须与上游重复保护共同验证。

本阶段不自动把全部播放事件送入 Recall，也不按提交事件次数自动调用 promote。这样不会把每次进度都变成待整理材料。未来要接入 ingest → promote 时，再明确有意义的资料单元、何时调用、预算和删除范围。

## 9. 删除、旧设备与历史迁移

删除一次学习后，产品数据库中的对应内容和统计依据移除；保留不含学习正文的必要编号拒绝标记，让旧设备补传同一批操作时不会重建已删除的记录。关联的待交付任务停止，其他设备收到删除状态后清理本地显示与待上传副本。

删除离线未知的新记录时，先处理所属学习编号是否已删除，再接受子事件。不能只阻止已知事件编号，而允许旧设备换一个子事件让整次学习复活。

这与“让 Octos 忘记一个偏好”不是同一个操作。已经保存的 Octos 会话和提炼出的记忆，不会因为 SQLite 少了一行而自动消失。第二阶段界面应明确写“删除这次学习记录”，不能写成“老师彻底忘记”。本阶段不提供含义含糊的一键全清。

若删除同时涉及现有白板/Octos 会话，沿用既有删除接口，逐项记录结果。尚未确认完成的部分显示待处理，不因产品数据库删除成功就声称所有副本和长期记忆已清理。更广的原对话删除与长期记忆联动，需要另行确定范围。

旧数据只迁移实际能够证明的状态。已有某课程的恢复位置可以显示“此前保存的进度”；不能据此补出过去完成的所有片段、历史发生时间或“五次学习”。仅在设备本地的数据，需在同一已确认账号下导入；无法证明归属的不自动上传。新功能启用时间之前的统计注明可能不完整。

## 11. 验收标准

| 场景 | 必须看到的结果 |
|---|---|
| 同一记录重发十次，含服务重启 | 正式记录和统计只增加一次；内容冲突不能被静默覆盖 |
| 问题 A、B 的课程按 B、A 顺序完成 | 两份课程仍各自绑定原问题；失败不会冒充成功回应 |
| 生成课程但从未播放 | 有问答与课程，没有对应知识点的讲解播放记录 |
| 跳到最后、静态查看、React 重挂载 | 不把跳过内容记成实际播放，不产生新一次学习 |
| 无声音、语音失败、外部旁白完成回调 | 分清程序播放进度与真实语音成功；不能把语音回调本身当作学生学过的唯一证据 |
| 只播放《斜率和截距》前两节 | 斜率目标有依据，截距目标没有；不宣布掌握整个上游节点 |
| 同一遍回放，另开新一遍 | 前者不增加独立学习次数，后者实际播放后按规则增加 |
| 旧一遍已做对题，明确开始新一遍；两设备或日志重建后都从序号 1 开始 | 旧成功不自动成为新成功；旧尝试不被重新导入；不同实际操作有不同日志归属，同次操作重试不重复 |
| 做题失败、看提示后成功、重复上传 | 各次真实尝试和提示保留；同次作答不会算两遍，不宣布独立掌握 |
| 离线学习、重开应用后补传、乱序抵达 | 原编号不变，时间信息保留，课程总数和次数正确 |
| 账号 A 的队列未上传就切换到 B | B 不显示、不接收 A 的记录；伪造账号字段不能越权 |
| 删除后旧设备继续补传 | 已删除的学习不复活，不进入统计；其他学习不受影响 |
| 数据库满、本地配额满、服务繁忙或认证失效 | 提示真实保存/同步状态，可重试，已有课程播放不被破坏 |
| 本地进度与待上传事实保存期间退出并重开 | 已完成的事务能恢复，未提交状态不伪装为已保存；不依赖页面关闭回调补齐事实 |
| Octos 已写入而回执丢失，旧消息超出加载预算后重试 | 通过最小上游修正得到可靠结果，不重复创建；未修正前保持待核对，不误报交付完成 |
| 仅通过正常产品路由访问新接口，数据库同时发生锁等待和历史查询 | 不走到 Octos 的未知接口；身份校验有效；测量语音和其他请求的等待，不用“已有同步 SQLite”代替结果 |
| 历史跨页时继续学习并补传旧记录 | 同批查询可完整核查；新数据在后续同步纳入，不导致翻页漏项 |
| 数据库备份恢复 | 记录、删除状态、计数和待交付任务可恢复，不覆盖本人 Key 或 Octos 记忆 |

服务端使用临时数据库和认证替身覆盖事务、并发、崩溃恢复、越权及删除；浏览器用 fake-indexeddb 和组件测试覆盖持久队列与事件来源，Playwright 覆盖真实播放器和断网流程。测试要验证实际行为，不能只检查内部函数被调用。

前端最低检查为 `pnpm test:unit`、`pnpm lint`、`pnpm build`，另加新产品服务测试命令与针对性 E2E。若确需改 Octos，按其上游要求另外验证和提交。各测试结果分别报告，不将重叠测试相加。

人工验收沿用 HTTPS 5173、后端 50080、本机既有账号及正式安装技能。虚构故障与其他账号的否定用例在自动化夹具中完成，不向本人真实记忆灌测试材料；需要付费模型的完整课程性能对照按已确认预算执行。

首个可播放片段速度按项目现有标准与对照交错比较 p50，检查实际供应商请求数，零新增模型往返；只说明“记录是异步的”不能代替性能结果。语音转发同进程时也要验证数据库忙不会拖慢它。

本文件记录计划与验收要求，不作为完成证明。实际测试见实施记录；生产容量测试和部署尚未完成。备份实施参考 [SQLite 在线备份说明](https://www.sqlite.org/backup.html)，需要真正恢复验证，不能只确认备份文件存在。

## 12. 开始前的决定与之后再决定的事项

建议先确认三项：正式记录由 Octos Learn 服务端 SQLite 保存；首版以 Octos profile 为归属；提问、讲解播放、整课完成和练习分别计数。它们影响数据结构和用户看到的含义，应先定清楚。
