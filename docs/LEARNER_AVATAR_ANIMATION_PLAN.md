# 学生动态头像：以 Memoji 体验为目标的实施方案

日期：2026-11-01。状态：方案已开始实施，实际进展和未验证范围见[实施进度](LEARNER_AVATAR_ANIMATION_PROGRESS.md)。

> **方向已经调整（2026-11-02）**：用户明确放弃追求苹果三维效果，改为保留细腻画风的二维头像，手臂暂缓。当前已交付[原画风二维互动可测试版本](LEARNER_AVATAR_PAINTED_INTERACTIVE.md)，后续按其验收边界继续；本文三维制作与 Memoji 目标作为历史方案保留。

已确认方向：以星狐为首个主形象；用户希望尽可能接近苹果动态头像效果，并考虑电视。本文的选型、指标、范围和排期是建议，不代表已验收或已承诺上线。

## 1. 推荐路线

采用“原创星狐三维角色 + 插画风渲染 + 精细面部绑定 + 多来源捕捉 + 独立表演时间线”。以高质量连续表情为优先，调整此前二维动画优先的建议。

保留已选星狐身份、蓝银学院服和导师关联，用三维结构实现连续转头、眼球与眼睑联动、嘴唇与下颌组合变化。已有三张 PNG 是设计参考和降级资源，仍需制作可动画模型。

两条捕捉路线共用角色：

- **质量参考路线**：受支持的 iPhone/iPad 原生 ARKit 捕捉；电脑/电视可以接收动作参数并显示角色。首批参考设备选经过实测的 TrueDepth 机型，运行时仍检查 `ARFaceTrackingConfiguration.isSupported`。
- **普及路线**：电脑、平板普通摄像头使用 MediaPipe；Android 大屏按实测选择网页或原生捕捉。捕捉质量与 ARKit 路线分别评价。

ARKit 公开 API 提供头部姿态与表情系数，可用于自有角色。这不意味着可以取得苹果 Memoji 的模型、绑定、内部动画调校，也不保证自有角色自动达到 Memoji 效果。[Apple ARFaceAnchor](https://developer.apple.com/documentation/arkit/arfaceanchor)，[设备支持](https://developer.apple.com/documentation/arkit/arfacetrackingconfiguration)

## 2. 质量目标

“接近苹果”同时指向：嘴型连续准确、眉眼能够组合、静止稳定且小动作能跟随、转头自然、低延迟、录制和发布一致，以及星狐在各种表情下仍保持美感。

首版聚焦头部、面部和上半身。手部与全身捕捉另行排期。

验收动作包括：正常讲话、闭唇发音、圆唇、微笑讲话、左右眨眼、抬眉、大小幅度转头、低头、眼镜、侧光、遮挡与重新出现。额外验证孩子站在大屏前侧身写字的实际拍摄位置。

Apple 参考与星狐分别记录相同动作脚本，比较响应、稳定性、表情可辨识度和破相/穿模。角色形象不同，不以像素相似度或未经定义的“苹果百分之几”验收。

## 3. 星狐模型制作

需要角色建模与面部绑定工作，生产级绑定属于美术交付。

| 交付 | 要求 |
| --- | --- |
| 形象定稿 | 正面、侧面、三分之二角；保留身份与学院配色，缩小显示仍可辨识 |
| 源模型 | Blender 或等效可编辑工程；合理拓扑、UV、贴图、骨架；明确商业使用权 |
| 面部绑定 | 以 ARKit 常用 52 通道口径建立兼容清单；眼球、眼睑、眉毛、嘴唇与下颌分别可控 |
| 组合修正 | 张嘴微笑、闭唇抬颌、眨眼转头等不穿模；狐狸口鼻专门调校 |
| 口腔 | 嘴唇、牙齿与口腔内部完整；舌部按实际支持与质量决定 |
| 次级动作 | 耳朵、发梢和衣领适量跟随；保证讲述稳定性 |
| 运行资产 | 版本化 GLB、通道映射、角色调校、预览图、标准与低负载版本 |

“52 通道”不是质量分数，单通道与组合都要验收。MediaPipe 与 ARKit 的通道清单、含义不能直接假定相同；缺失通道显式标注能力。

glTF 支持形变目标与权重动画，适合交付面部模型。[Khronos 说明](https://github.com/KhronosGroup/glTF-Tutorials/blob/main/gltfTutorial/gltfTutorial_017_SimpleMorphTarget.md)

## 4. 捕捉与角色播放

```text
本机摄像头 / iOS 捕捉伴侣 / Android 原生捕捉
                    ↓
        捕捉适配器：表情、姿态、置信度、时间
                    ↓
        统一通道 → 校准、稳定处理 → 星狐映射
                    ↓
              角色播放器与表演记录
```

### 网页与 Android

- 网页首选 MediaPipe Face Landmarker，单人跟踪；识别与界面线程隔离。CPU/GPU 路径分别实测，检查与白板争抢资源。
- Android WebView 或摄像头接口达不到目标时，建立原生捕捉桥；参考当前原生音频桥的集成方式，但摄像头需要独立实现。
- 每个来源报告实际支持的通道、失跟状态和采样时间，记录来源与映射版本。

MediaPipe 提供表情与姿态输出，官方也指出同步识别会阻塞界面线程，建议通过 Worker 隔离。[官方文档](https://ai.google.dev/edge/mediapipe/solutions/vision/face_landmarker/web_js)

### iOS 质量参考路线

- 原生 ARKit 捕捉；第一轮只做捕捉、校准与配对，不扩展为完整学习应用。
- 扫码配对使用短时会话凭据，限制当前账号/录制会话，可随时断开。
- 优先局域网，传输选型通过端到端延迟验证；首版不依赖公共中继作为必选项。
- 发送表情、姿态、时间与状态，默认不发送真实视频；同步时钟、丢弃过期帧，防止积压延迟。
- 手机负责音频时，音频与表情共享时基；电视负责音频时，测量并补偿设备间时差。避免双设备重复收音/转写。
- 手机摆在能看清孩子脸部的位置，电视负责白板。验证侧身、走动、距离与低头。

52 个 float32 系数在每秒 30 帧下约为 0.37 MB/分钟，另加头部姿态、时间和传输开销。这只是格式计算，不能据此推断网络延迟或设备性能。

### 动画调校与渲染

- 短时自然表情校准，可跳过用默认值；嘴型、眉眼与头部分别平滑，保持嘴型响应速度。
- 为狐嘴、尖耳和发型设置映射范围；失跟时平稳回到待机并提示调整位置。
- 捕捉动作与预设眨眼/呼吸有明确优先级，回放不使用不可复现的随机动作覆盖记录。
- React 应用增加独立角色舞台，首选 Three.js + GLB；采用插画风材质，限制材质数、透明层和动态灯光。
- 仅按角色实际显示区域渲染；4K 电视不等于摄像头与头像都要按 4K 处理。
- 与数学三维组件同时运行，测量共享 GPU 开销、上下文丢失与恢复。
- 当前 Three.js WebGLRenderer 要求 WebGL 2，旧 WebView 需能力检测和单独降级。[Three.js 文档](https://threejs.org/docs/pages/WebGLRenderer.html)

## 5. 录制与重新配音

### 录制时

- 每张讲解卡的 Take 引用独立表演轨，与白板操作共享录制时基。
- 保存角色通道、姿态、置信度、来源与映射版本；不把原始摄像头视频或人脸网格写入课程。
- 原始音频沿现有 ASR 边界处理。如对齐需要新增短时音频处理，明确期限与清理，继续保持不发布孩子原声的目标。
- 退出、切换账号或撤销权限时停止采集，取消未完成工作。

### 发布时

1. 孩子确认文本并完成已有隐私检查。
2. 按实际选择的音色生成配音；音色不可用时明确提示，不静默换成默认音色。
3. 根据新音频和确认文本生成发音时间与嘴型。先评估供应商时间信息，否则增加音频对齐/口型分析；中英文分别实测后选型。
4. 嘴和下颌由新配音驱动；眉眼、点头按语句锚点重新对齐。新旧讲话长度可能不同，不能直接沿用旧时间戳或只做整段等比例缩放。
5. 板书、声音与角色共享可暂停、跳转、变速的播放时钟；重录不串轨，暂停恢复不重复发声或漂移。
6. 孩子确认最终预览。正文、字幕、音色或资产版本变化后，重新生成相关缓存。

音量驱动开合只用于降级，高质量验收需要检查闭唇、圆唇、牙齿接触和连贯发音。

### 课程包

现有 `.olesson` 只有课程、笔迹、旁白与角色引用，需兼容扩展或明确升级版本。包内应含精确版本的模型、贴图、材质、映射、发布表演轨、配音与文件哈希；离线/跨设备播放不依赖作者设备的隐式资源。

先评估自包含角色资源，再优化共享缓存；旧读者对必需的新能力明确拒绝。公开角色动作仍需最小化、隔离、删除与访问控制，不宣称自动匿名化。

以下为工程落点；网页捕捉/表演片段、片段库与原生捕捉源码已建立，其余集成的实际状态见[实施进度](LEARNER_AVATAR_ANIMATION_PROGRESS.md)：

| 区域 | 工作 |
| --- | --- |

| `src/learning/avatar/`（新增） | 捕捉适配、校准、角色映射、渲染、表演时钟与能力检测 |

OLL 保持教学内容和白板语义，高频面部系数放独立表演轨。已有 before/during/after 阶段不能表达精确唇音同步，宿主需要语音媒体时钟接口，是否改 OLL 按原型证据决定。

默认不改 Octos 通用后端；仅在共享鉴权/配对/资源确有缺口时另立改动。普通 AI 课程按需加载角色模块，继续满足首段速度约束。

## 7. 电视策略

| 场景 | 建议 |
| --- | --- |
| 较新安卓触摸大屏 | 实测本机捕捉 + 渲染，也支持手机捕捉 |
| 现有 Android 8 大屏 | 检测 WebView/WebGL、摄像头、持续负载；优先手机捕捉减负，必要时原生渲染 |
| 无可用摄像头但能渲染 | 录制配对手机，观看播放包内动作 |
| 缺少可用三维渲染能力 | 可选预渲染角色小视频层，白板保持独立交互；编码、背景与同步实测，不假定透明视频通用 |
| 普通遥控器 Android TV | 另需导航/输入适配；现有 APK 要求触摸屏 |
| 其他智能电视系统 | 另列支持计划，不纳入安卓结论 |

USB 摄像头取决于厂商系统支持，需验证指定电视/摄像头组合。[AOSP 文档](https://source.android.com/docs/core/camera/external-usb-cameras)

## 8. 初始验收指标

以下是工程目标，原型后修订。固定设备与输入条件，报告帧耗时、尾延迟及持续负载，不能用平均 FPS 代替。

| 项目 | 目标 / 检查 |
| --- | --- |
| 高档角色渲染 | 60 FPS，报告 p50/p95 帧耗时、丢帧与长停顿 |
| 电视标准档 | 30 FPS，先验证指定设备能否稳定达到 |
| 本机动作响应 | p95 ≤ 120 ms；包含取帧、识别、渲染 |
| 手机辅助端到端响应 | p95 ≤ 150 ms；包含传输，单独报告时钟/网络误差 |
| 发布配音嘴型 | 人工标注测试段的音素—嘴型对齐误差 p95 ≤ 80 ms；同时评审自然度 |
| 持续录制 | 至少 20 分钟，书写、转写、数学组件同时运行，记录发热、内存及降频 |
| 学习核心 | 与关闭头像交错对照，白板不出现可复现延迟退化；AI 首段零新增模型往返 |
| 首个角色资源 | 压缩后 ≤ 10 MB 作为优化目标；报告贴图/形变展开后的实际内存 |
| 离线课包 | 断网播放模型/声音/动作；跳转、暂停、刷新恢复与损坏均有明确行为 |

先用经同意的成人内部测试验证链路；儿童实测覆盖脸型、距离、动作习惯，并按已有同意与数据边界执行。

## 9. 分阶段实施

| 阶段 | 交付 | 推进条件 |
| --- | --- | --- |
| A 技术与设备验证 | 合规测试模型、网页捕捉、ARKit 数据链、电脑/目标大屏报告 | 确定渲染与电视路线，形成自有模型制作规格 |
| B 星狐模型 | 原创三维模型、面部绑定、插画渲染、组合表情测试 | 产品确认正侧面与动态表情 |
| C 实时头像 | 校准、跟随、失跟处理、现场与持续负载报告 | 表情、稳定性与延迟达标 |
| D 录课与发布 | 每卡记录、合成配音嘴型、统一时钟、试听/预览、离线包 | 完整录制与修改流程通过，重录不串轨 |
| E 电视交付 | 指定设备本机/手机辅助路线、性能档、兼容清单 | 真实站姿书写与持续录课通过 |

工程验证与建模可部分并行；测试模型只作工程验证，不当作美术定稿。

资源假设：至少一名应用工程师、一名有面部绑定经验的三维制作人员，及 iOS/Android 集成能力。完整候选先按 **6–10 周**做工作量估算，阶段 A 后重估。设备、模型质量、嘴型对齐选型与返工会影响排期；不承诺固定上线日期或外包价格。

## 10. 最先需要的输入

1. 一台支持 ARKit 面部捕捉的 Apple 设备，作为高质量参考。
2. 目标电脑、大屏和摄像头/麦克风；优先读取已经连接的设备信息。
3. 星狐三维模型与专业面部绑定的制作资源。
4. 产品确认是否接受“手机捕捉 + 电视白板”作为高质量模式的常规使用方式；普及摄像头路线保留。
