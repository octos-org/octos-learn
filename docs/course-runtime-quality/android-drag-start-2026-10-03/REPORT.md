# Android 触屏拖拽起步诊断（2026-10-03）

用户确认问题来自电视直接触屏。设备、DPR、分辨率和 WebView 版本与前两阶段相同；测量时关闭 scrcpy。

## 两条开销路径

1. 无内容变化的 React 更新重新读取 Session 的克隆快照、重新创建课程目录，使白板渲染 Effect 重新执行。真机捕获到一次约 260ms 的完整 render；临时测量宽高和坐标写入后，所有节点最终位置仍与开始相同。说明静态课程仍做了重复重排。
2. 导航开始时才设置白板的 will-change，手势结束立即取消。再次开始拖拽需要重新准备合成层。Android 触屏注入采样中，单纯消除重复重排后仍有约 410ms 的首组长帧；临时提前准备合成层后，前三次最大 rAF 间隔为 112、108、284ms。这是单组实验，第三次仍有长帧，不能据此宣称问题全部解决。

## 修改

- 在 Session 通知版本变化时读取 playback、目录、焦点、3D 视图、任务和反思快照。普通 UI、笔迹和摄像头状态更新复用原快照；播放、增量追加、参数输入等 Session 通知仍更新。
- 对完整目录元数据建立内容键，内容相同的目录引用变化不再触发重排；所有目录字段和归属变化仍使其失效。
- 仅 Android 图形缓存路径在课程暂停、空闲且缓存就绪后准备白板合成层，并在连续独立手势之间保留。原始 SVG 仍在手势结束恢复；播放/自动导航、视口尺寸改变、最后一张缓存失效和销毁时释放层提示。
- 新回归检查界面更新及相同目录重新创建不会 render，真正的新 Beat 仍 render；检查触屏前已准备合成层、静止时恢复 SVG，以及暂停条件撤销/销毁时释放。

预热保留合成层可能增加静止时的图形内存驻留，实际分配由 WebView 管理；本次未测 GPU 内存。未更改数学课程内容、世界布局、控件、分辨率或密度。

## 测量边界

程序化拖拽在 Session 快照修复后未再记录到此前起步的 61、139、204ms JavaScript 长任务；稳定课程的重复探针没有调用 render，也没有节点样式变化。但仍有 130–220ms 的帧间隔，不能声称消除了绘制开销。

早期触屏探针每帧调用 getCameraState，会强制读取 computed style、干扰测量。触屏轻量探针改为只记录镜头目标数值和 rAF 时间；正式触屏对照以该探针为准。rAF 时间不是实际屏幕呈现时间，Android 注入也不覆盖物理触摸控制器自身延迟。
