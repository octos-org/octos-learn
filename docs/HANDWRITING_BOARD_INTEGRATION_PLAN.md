# 摄像头隔空书写接入白板的方案

日期：2026-11-04。状态：方案，尚未实现白板接入。

## 目标与第一版范围

把摄像头手势作为现有白板的一种书写输入来源。用户在同一块白板上完成书写、撤销、擦除、框选和向老师提问，手势笔迹使用当前白板原有的保存与恢复机制。

第一版先接 `/board` 的学生书写场景，通过实验开关提供显式入口，默认关闭。继续保留 `/handwriting-lab` 做手势、延迟和模型调试。讲课录制与头像同时驱动放到下一阶段，待普通白板接入通过后处理。

本轮只形成方案，没有修改白板主流程。当前小样仍位于独立 handwriting worktree，预览端口 5175；头像原 checkout 与 5173 保持其现有开发状态。

## 根据当前代码确认的接入点

- `src/learning/oll/oll-lesson-runtime.tsx` 的 `LearningWhiteboard` 已经拥有白板 viewport、Ink Runtime、模式、笔色、笔宽、撤销、框选及保存。
- 当前工具栏已经有浏览、书写、擦除、框选等按钮；手掌图标表示“浏览白板”，重复使用这个图标表示手势书写会造成混淆。
- 普通学生笔迹保存在 `octos-learning-ink:v1:${inkSessionId}`，文档标识为 `learning-session:${inkSessionId}:student-ink`。实验页的独立 storageKey 不带入正式白板。
- 当前开始/继续课程播放会把 Ink Runtime 切到 `navigate`。手势输入需要在这个切换前收尾。
- `src/learning/learning-workspace.tsx` 目前的摄像头入口属于语音/视觉问答，预览标为“老师看到的画面”；开启它后，提问链路可以抓取并发送图像。
- `src/home/voice/use-camera-frame.ts`、头像的 `FaceCapture`、手势 `HandwritingCapture` 当前各自申请和释放摄像头，尚无统一的消费者管理。
- 主 checkout 的讲课录制已通过 `src/learning/teach/use-take-camera.ts` 使用头像采集；`teach-board.tsx` 另外拥有按 take 保存和冻结的 Ink Runtime。
- 头像 Worker 的身体/手部检测路径约每 100 ms 更新一次，并输出转换后的身体姿态。书写当前需要较高频率的原始手部关键点；不能直接用这一份低频姿态代替书写输入。

## 用户操作

在书写笔旁增加带文字的“隔空书写（试用）”入口，与现有“浏览”和“给老师看画面”的摄像头入口区分。

1. 点击入口，请求摄像头并加载本机模型，切换到书写工具。
2. 角落出现可收起的小预览，包含骨架、抬笔/落笔状态、暂停/继续及关闭。
3. 默认使用当前“松握拳书写 / 张掌移动”，第一次展示简短动作提示。其他实验手势保留在实验页，不在白板主界面列出四种模式。
4. 用户写出的笔迹使用当前笔色和笔宽，可直接撤销、擦除、框选、提问。
5. 明确关闭时结束当前笔画并释放手势使用的资源。刷新后保留笔迹和偏好，摄像头保持关闭。

正式浮窗不保留“播放模拟轨迹”、全量性能统计或实验页的一键清空。正式白板继续使用原有选择/删除和撤销机制，避免误把练习页的重置操作带入有课程和真实笔迹的白板。

浮窗及其展开菜单接入现有 `data-learning-board-occlusion` 遮挡机制。光标不能向浮窗、工具栏、输入框和课程交互控件派发笔迹或点击；悬停进入这类区域时抬笔，回到可写区域后需重新张掌准备。折叠浮窗只隐藏预览，不改变是否正在采集；采集状态始终有可见提示。

## 输入状态与收尾顺序

将“输入来源”和“笔迹工具”分别管理：来源包括直接输入与摄像头手势；Ink Runtime 继续使用原有 navigate/draw/erase/select 模式。第一版仅允许手势产生自由笔画，擦除、框选、平移缩放继续使用现有操作。

| 事件 | 建议行为 |
| --- | --- |
| 启动隔空书写 | 验证当前白板可写、模型与摄像头就绪，再进入 draw；张掌准备后接受落笔 |
| 张掌 / 松握拳 | 在当前工具与输入许可内控制悬停、落笔、抬笔 |
| 点浏览、擦除、框选 | 先结束手势笔画，暂停手势输入，再切工具；不因手形变化自动抢回 draw |
| 真实手写笔/触摸开始编辑 | 直接输入优先，先结束合成笔画并暂停手势；需显式继续，防止摄像头手形又接着写 |
| 平移、缩放、窗口尺寸变化 | 结束当前笔画，停止输出；画面稳定后重新建立掌部参考、张掌准备，不跨坐标变化连接 |
| 自动聚焦课程区域 | 聚焦前暂停手势并收尾，再移动画面；不能在尚未处理的画面变化中继续派发旧坐标 |
| 开始/继续播放课程 | 随现有规则进入 navigate，暂停手势输入；默认不在播放中自动恢复 |
| 打开设置、弹窗或系统文件选择器 | 暂停手势输出，屏蔽覆盖区域，不把手势变成点击 |
| 手部丢失或识别失效 | 使用现有安全断笔与尾段丢弃策略，重新出现后先张掌准备 |
| 明确暂停/关闭 | 提交已经确认的正常书写缓冲，丢弃未解决的开手过渡，pointerup 后保存 |
| 切白板、离开页面、后台隐藏 | 清理当前输入，先完成必要的笔迹收尾，再释放资源；不会向下一块白板投递迟到帧 |

暂停输入与关闭摄像头要有明确区别：用户主动暂停可短暂保留采集以便继续；离开页面、后台隐藏、播放课程等默认释放不再需要的手势采集资源。继续输入需重新准备，恢复资源必须遵守浏览器和设备要求。

Ink Runtime 销毁、take 冻结或模式切换之前，先让手势控制器输出终止事件。单独等待 `ink.saveNow()` 不会提交仍留在手势控制器中的 100 ms 缓冲。

## 技术结构

复用现有识别和控制器，提取实验页中的生命周期与事件适配，形成一个只绑定当前 viewport 的输入适配层。`LearningWhiteboard` 保持对 Ink Runtime、工具和文档的唯一管理。

```text
摄像头原始帧 → 手部识别 Worker → 手势/掌部控制器
                                      ↓
                          当前白板的输入许可与遮挡判断
                                      ↓
                          viewport PointerEvent 适配
                                      ↓
                     已存在的 Ink Runtime → 当前学生笔迹文档
```

建议拆分一个 `useHandwritingInput` hook 与小型浮窗组件，避免把采集、时钟、异常清理继续堆入大型白板组件。适配层接收当前 viewport、是否允许输入、结束与保存回调、画面变换通知；不再挂载自己的无限白板或 Ink Runtime。

摄像头异步请求、模型初始化、帧结果都附带本次启用的代次标识。切换会话或关闭后，即便权限请求稍后成功或 Worker 迟到回包，也只释放资源，不重新启动输入。

画面平移缩放依然由现有 viewportToBoard/Ink Runtime 转换。手势控制器保存的是屏幕光标参考；画面变换前必须断笔并重建该参考，不能只依赖笔迹渲染层的相机同步。

## 摄像头用途与头像协作

这是整合中的实际风险点：本机识别与给老师发送画面，不能由同一个布尔值控制。

- 隔空书写开启后只授权本机手势识别，不能把 `conv.cameraActive` 或 `autoCamera` 自动设为 true。
- 给老师看画面仍需用户单独开启，继续沿用现有抓帧和发送规则。
- 公用同一个物理摄像头时，底层原始视频源可共享，但发送图像、手势识别、头像驱动分别拥有自己的用途状态和释放句柄。
- 一个消费者停止时，只释放自己的使用权；最后一个消费者停止后才关闭物理轨道。
- 只有设备、朝向等要求兼容时才共享。拍题的文档裁切、旋转和放大不应直接应用到手部识别坐标；手部和头像各自使用明确的镜像规则。
- 模型只在需要时加载。手势只识别手部，头像按需识别脸和身体，不因为打开书写就启动整套头像推理。

第一阶段优先理清 `/board` 上手势与问答摄像头的资源和用途关系；现有头像录制在另一页面，其消费者随后迁移到同一资源约定。需要同页并行时再接入统一帧调度与性能测试，不能把“浏览器能同时打开两路”当作跨设备兼容保证。

若头像与手势共用 Hand Landmarker 推理，应共享带时间戳的原始关键点，由头像单独做动画平滑、书写单独做笔迹过滤；不采用头像平滑后或低频身体动作来驱动书写。

## 实施顺序

1. **接入普通白板**：显式实验入口、小浮窗、当前 Ink Runtime、笔色笔宽、撤销与保存；完成工具、播放和画面变化的输入切换与终止顺序。
2. **整合摄像头用途**：与现有问答摄像头一起验证共享、开关、设备冲突和独立发送意图；移入资源管理约定，完善资源释放与迟到回包处理。
3. **真实设备验证**：在用户设备测试位置、断笔、帧率、课程播放和问答并用；Android WebView 单独验收，按实际能力开放入口。
4. **讲课录制与虚拟形象**：适配 `teach-board` 当前 take 的 Ink Runtime，结束 take 前提交手势缓冲再冻结笔迹；与头像共用摄像头及时间基准，验证并行负载。不要复用学生白板 storageKey。

录制讲课是独立业务流程，不能只把 `/board` 按钮复制过去就视为完成。先把学生白板打通，可以明确哪些能力可复用，再扩展录制。

## 验收重点

- 在空白板及有课程的白板上都能写；颜色、笔宽与当前工具一致，撤销/重做、刷新恢复和框选提问可用。
- 用户瞄准点与第一笔一致；在缩放、平移、自动聚焦、窗口变化后不连接旧坐标。
- 真笔/触摸与手势之间交接不会产生双重输入；工具切换后不会被识别回调自动切回画笔。
- 播放课程、打开弹窗、切会话、离开页面、停止或模型失败时，当前笔画正确结束，没有后台误画和迟到写入。
- 摄像头只用于手势时，不产生问答图像上传；关闭问答摄像头不会意外停止仍授权的手势，反之亦然。
- 正常停止会保存尚在缓冲中的合法笔迹；未确认的开手动作不当作正常尾段写入。
- 第一次加载普通白板不预先加载模型或请求摄像头；评估开启手势对课程渲染、语音和首个可播放片段速度的影响。
- 真人手势质量、WebView 权限与性能、头像并行质量分别记录，自动回归通过不代表这些项目已经验收。

当前方案尚未执行以上集成验证。下一步的可交付成果应是 `/board` 中默认关闭的实验入口，以及真实会话笔迹的完整闭环。
